# 01. PRD — Financial Document Intelligence

**문서 상태:** Draft  
**프로젝트 유형:** 기업 문서 기반 RAG 질의응답 시스템  
**개발 대상:** Basic 데이터셋 우선  
**개발 원칙:** 필수 구현 완료 후 개인 확장 실험 진행

---

## 1. 프로젝트 개요

### 1.1 서비스 목적

기업 및 금융 관련 PDF 문서를 대상으로 사용자의 질문에 필요한 정보를 검색하고, 검색된 근거를 바탕으로 답변하는 문서 기반 질의응답(RAG) 서비스를 개발한다.

단일 문서뿐 아니라 여러 문서에 분산된 정보를 검색하고, 기업·사업부문·제품·기간·지역·적용 범위 등의 관계를 구분하여 답변하는 것을 목표로 한다.

검색된 근거가 충분하지 않거나 질문에 필요한 조건이 누락된 경우에는 임의로 답변하지 않고 추가 정보를 요청하거나 답변을 보류한다.

### 1.2 프로젝트 목표

#### [필수]

1. PDF 문서를 처리하고 검색 가능한 데이터로 변환한다.
2. Naive RAG, Hybrid Retrieval, Hybrid + Reranking 세 가지 검색 방식을 구현한다.
3. 검색 결과를 바탕으로 GPT-6 Luna를 이용해 답변을 생성한다.
4. 근거 문서명과 페이지 번호를 답변에 표시한다.
5. 답변, 추가 확인, 답변 보류를 구분하여 처리한다.
6. FastAPI를 이용해 RAG 기능을 API로 제공한다.
7. Langfuse를 이용해 실행 과정을 추적하고 기록한다.
8. 공식 평가 기준에 따라 검색 및 답변 품질을 비교한다.
9. 실험 결과를 저장하고 재현 가능한 형태로 관리한다.
10. 최종 비교 결과와 기술적 의사결정을 문서화한다.

#### [확장]

1. 추가 검색 및 답변 평가 지표를 도입한다.
2. 청킹, 검색, 프롬프트 등의 개선 실험을 진행한다.
3. 되묻기 및 답변 보류 전략을 개선한다.
4. 검색 품질과 답변 품질의 관계를 분석한다.
5. 성능 및 비용 최적화를 시도한다.
6. 사용자용 Q&A 화면을 구현한다.
7. 실험 결과 공유 대시보드를 구현한다.

## 2. 주요 이용자 및 사용 시나리오

### 2.1 주요 이용자

기업 내부의 문서 기반 업무 담당자.

- 경영기획 및 경영관리 담당자
- 재무·회계 담당자
- 사업관리 담당자
- 대외 커뮤니케이션 및 정보 확인 담당자

기업 관련 문서를 확인하고 근거를 바탕으로 정보를 전달해야 하는 업무 담당자를 주요 이용자로 정의한다.

### 2.2 핵심 사용 시나리오

| 유형 | 사용 사례 |
|---|---|
| 사업 정보 조회 | 기업의 사업부문 및 제품·서비스 관계 확인 |
| 실적 비교 | 기간별 매출 및 영업이익 비교 |
| 보고 범위 확인 | 기업별 수치의 보고 범위 및 연결 여부 확인 |
| 조건 확인 | 제품의 적용 조건 및 범위 확인 |
| 정정 내역 확인 | 정정 전후 수치 및 정정 적용 범위 확인 |
| 외부 문의 대응 | 문서 근거를 바탕으로 회신 초안 작성 |

## 3. 기능 요구사항

### 3.1 PDF 문서 처리

#### [필수]

- PDF 문서 로딩 및 텍스트 추출
- 검색 가능한 단위로 문서 분할(Chunking)
- 문서명과 페이지 번호 보존
- 문서 식별자 및 메타데이터 관리
- 문서 처리 오류 기록
- 원본 PDF와 추출 결과의 연결 관계 유지

#### [확장]

- 다양한 Chunk Size 및 Overlap 비교
- 표 및 복잡한 레이아웃 처리 방식 개선
- Parent-Child Retrieval 적용 검토
- 문맥 보존형 청킹 방식 비교

### 3.2 검색 시스템

#### [필수]

다음 세 가지 검색 방식을 구현한다.

1. Naive RAG (Dense Retrieval)
2. Hybrid Retrieval
3. Hybrid Retrieval + Reranking

세 방식의 비교 조건을 통제한다.

- 동일 PDF 데이터셋
- 동일한 PDF 추출 결과
- 동일한 질문
- 동일한 임베딩 모델
- 동일한 생성 모델
- 동일한 답변 프롬프트
- 동일한 생성 설정
- 동일한 청킹 결과
- 동일한 최종 검색 청크 수(k)
- 동일한 문맥 토큰 한도

검색 결합 및 리랭킹 설정은 별도로 기록한다.

#### [확장]

- BM25 및 Dense 검색 가중치 최적화
- 검색 Top-k 변경 실험
- Query Expansion
- Query Rewriting
- Reranker 종류 비교
- Contextual Compression
- Parent-Child Retrieval

### 3.3 답변 생성

#### [필수]

- GPT-6 Luna를 생성 모델로 사용
- 검색된 문서를 근거로 답변 생성
- 근거 문서명 및 페이지 번호 표시
- 여러 문서의 근거를 결합한 답변 지원
- 기업·제품·기간·지역 등의 조건 구분
- 답변 생성에 실제 사용된 최종 문맥 보존

#### [확장]

- 프롬프트 구조 및 지시문 개선
- 문맥 길이와 생성 설정 비교
- 답변 형식 및 인용 방식 개선
- 부분 답변 전략 실험

### 3.4 되묻기 및 답변 보류

#### [필수]

- 필수 조건이 누락된 질문에 추가 정보 요청
- 근거가 부족한 질문에 답변 보류
- 문서 간 관계나 적용 범위를 확인할 수 없는 경우 임의 추론 방지
- 답변·추가 확인·보류 상태 구분
- 일부 정보만 확인 가능한 경우, 확인 가능한 범위는 답하고 확인할 수 없는 부분은 이유와 함께 보류 (기본 동작)

#### [확장]

- 검색 결과와 근거 충분성에 따른 보류 전략 실험
- 부분 답변 전략의 개선 실험
- 추가 질문의 적절성 개선
- 불필요한 보류 및 잘못된 답변 감소 실험

### 3.5 API

#### [필수]

FastAPI를 이용해 핵심 RAG 기능을 API로 제공한다.

- 질문 입력 및 답변 요청
- 검색 결과 및 출처 반환
- 답변 상태 반환
- Pydantic 기반 요청 및 응답 검증
- 오류 유형 구분
- 예외 처리

API 상태값은 다음과 같이 구분한다.

| 서비스 행동 | API 상태 |
|---|---|
| 답변 | answered |
| 추가 확인 | needs_clarification |
| 답변 보류 | abstained |
| 시스템 오류 | error |

`error`는 모델 호출 실패, 출력 검증 실패, 시간 초과 등 처리 실패를 뜻하며 LLM이 아니라 API 코드가 판정한다. 근거 부족에 따른 `abstained`와 구분한다.

API 응답은 답변, 출처(문서명·페이지), 처리 상태(`status`), 사유(`reason`), 요청 ID(`request_id`)를 포함한다. 상세 계약은 `09_DATA_SCHEMA.md`를 따른다.

실행 전에 모델 호출 timeout, 최대 호출 수, 재시도 횟수를 정한다. API 키와 개인정보는 저장소·로그·발표 화면에 남기지 않는다.

### 3.6 관측 및 로깅

#### [필수]

Langfuse를 이용해 주요 실행 과정을 기록한다.

- 사용자 질문
- 검색 과정 및 검색 문서
- 실제 모델 입력 및 출력
- Trace 및 Span 연결
- 모델 및 프롬프트 버전
- 응답 시간
- Input / Output Token
- 오류 및 실패 정보

각 요청의 실행 과정은 동일한 Trace에서 추적할 수 있어야 한다.

#### [확장]

- 사용자 정의 Score 추가
- 추가 평가 지표와 Langfuse 연결
- 실험별 성능 및 품질 비교
- 관측 데이터 기반 문제 분석

### 3.7 평가 및 실험 결과 관리

#### [필수]

공식 평가 안내에 따라 다음을 실행한다.

**검색 평가**
- Hit@k
- Recall@k

**답변 평가**
- RAGAS Faithfulness
- LLM-as-a-Judge의 사실, 조건, 근거, 판단 네 항목

**운영 지표**
- 응답 시간
- 오류율
- Input / Output Token 사용량

추가 요구사항:

- 질문 ID 기반 결과 연결
- 검색 결과, 최종 문맥, 답변, 인용 및 평가 결과 저장
- 세 가지 RAG 방식의 동일 조건 비교
- 실패한 실행 포함
- 해당 없음 및 평가 불가 처리
- 대표 자동 평가 결과의 원문 대조
- 비교표 및 최종 결과 문서화
- 최종 RAG 방식 선택: 공식 실험 전에 확정한 선택 규칙(`12_ACCEPTANCE_CRITERIA.md`)에 따라 하나를 선택하고 이유와 한계를 기록

**확장**

- MRR, MAP, NDCG@k, Precision@k
- Context Precision, Context Recall
- Answer Relevancy, Answer Correctness
- Citation Precision, Citation Coverage
- 기타 검색 및 답변 품질 지표

확장 지표의 기준 목록과 정의는 `10_ADDITIONAL_METRICS.md`를 따른다. 추가 지표는 공식 평가 지표를 대체하지 않으며 별도의 확장 실험으로 관리한다.

### 3.8 보안 평가

#### [필수]

과제에서 제공하는 보안 평가 안내(step7)에 따라 보안 질문 및 사례를 실행하고 결과를 기록한다.

- 선택한 RAG 구성 하나에서 제공된 업무 질문 2개를 기본 지시와 방어 지시로 각각 실행하여 답변 4개를 확인한다.
- 질문마다 한 번만 검색하고, 저장한 동일한 최종 문맥을 두 프롬프트에 사용한다(재검색 금지).
- 공격 문장의 모델 입력 포함 여부, 공격 지시 준수 여부, 업무 답변 정확성, 불필요한 거절 여부를 분리해 기록한다.
- 세부 기준은 `02_EVALUATION_PLAN.md`를 따른다.

#### [확장]

공식 보안 평가 완료 후 추가 공격 유형 및 방어 전략 실험을 검토한다.

### 3.9 사용자용 Q&A 화면

#### [확장]

Streamlit을 이용해 간단한 질의응답 화면을 구현한다.

- 질문 입력 및 답변 확인
- 출처 문서명 및 페이지 표시
- 검색 근거 확인
- 추가 확인 및 보류 상태 표시
- 대화 내역 확인

핵심 RAG 로직과 분리하고 FastAPI를 통해 기존 기능을 호출한다.

### 3.10 실험 결과 공유 대시보드

#### [확장]

Streamlit을 이용해 실험 결과를 확인하고 비교할 수 있는 대시보드를 구현한다.

- RAG 방식별 검색 및 답변 품질 비교
- 질문별 평가 결과 확인
- 응답 시간 및 Token 사용량 비교
- 보안 평가 결과 비교
- 개별 실험 상세 기록 확인

실험 결과는 공통 JSON 스키마로 저장하며 대시보드에서 이를 읽어 시각화한다.

## 4. 데이터 범위

### 4.1 제공 데이터셋

| 구분 | PDF 수 | 총 페이지 |
|---|---:|---:|
| Basic | 15 | 360 |
| Intermediate | 50 | 3,750 |
| Advanced | 120 | 18,000 |

### 4.2 개발 범위

#### [필수]

- Basic 데이터셋을 우선 개발 및 평가 대상으로 사용
- 원본 PDF와 평가 데이터 분리
- 문서명과 페이지 번호 보존
- 평가 데이터의 정답과 채점 기준이 검색 및 생성 입력에 유입되지 않도록 관리

#### [확장]

- Intermediate 및 Advanced 데이터셋으로 확장 검증
- 데이터 규모에 따른 검색 성능 변화 분석
- 대규모 데이터 처리 및 인덱싱 성능 실험

### 4.3 평가 데이터

제공 평가 자료의 구성은 다음과 같다.

| 데이터셋 | 개발 | 추가 확인 | 확장 검증 |
|---|---:|---:|---:|
| Basic | 30 | 30 | 12 |
| Intermediate | 30 | 30 | 없음 |
| Advanced | 30 | 30 | 없음 |

제공 문항 수와 실제 실행 문항 수는 구분한다. 질문 선택은 평가 계획에서 별도로 정의한다.

공개된 참고 정답을 활용한 결과는 비공개 테스트 성능으로 표현하지 않는다.

## 5. 품질 및 비기능 요구사항

### 5.1 필수 품질 평가

공식 과제 평가 지표와 계산 방식을 우선 적용한다.

| 구분 | 지표 |
|---|---|
| 검색 | Hit@k, Recall@k |
| 답변 | RAGAS Faithfulness |
| 답변 | LLM-as-a-Judge: 사실, 조건, 근거, 판단 |
| 운영 | 응답 시간, 오류율, Input / Output Token |

공식 평가에서 지정한 예외 및 오류 처리 규칙을 준수한다.

### 5.2 확장 품질 평가

필수 평가 완료 후 다음 지표를 선택적으로 추가한다.

- MRR, MAP, NDCG@k
- Context Precision, Context Recall
- Answer Relevancy, Answer Correctness
- Citation Precision, Citation Coverage
- 추가적인 안전성 및 답변 행동 지표

### 5.3 비기능 요구사항

- 신뢰성: 근거가 부족하면 임의로 답변하지 않음
- 추적 가능성: 질문부터 답변까지 실행 과정 추적
- 재현성: 동일한 실험 조건 재실행 가능
- 유지보수성: 검색, 생성, 평가, 관측 기능 분리
- 확장성: 데이터셋과 검색 방식 확장 가능
- 사용성: 답변과 근거를 명확하게 확인 가능

| 생성 모델 | GPT-6 Luna (`gpt-6-luna`) | 선정 |
| 임베딩 모델 | multilingual-e5-large 또는 BGE-M3 (STEP 3 소규모 비교 후 동결) | 초기값 |
| Reranker | BAAI/bge-reranker-v2-m3 | 초기값 |
| PDF 처리 라이브러리 | 추후 선정 (STEP 1에서 실제 PDF로 확인) | 미확정 |
| 결과 저장 | JSON | 선정 |
| 사용자용 화면 | Streamlit | 확장 |
| 공유 대시보드 | Streamlit | 확장 |

구체적인 모델 및 라이브러리 선정 기준과 초기값은 `06_MODEL_SELECTION.md`에서, 확장 후보는 `11_MODEL_SELECTION_GUIDE.md`에서 정의한다. 승인된 결정과 이유는 `DECISIONS.md`에 기록한다.
