# 02. EVALUATION_PLAN.md

# Evaluation Plan

## 1. 평가 목적

본 문서는 Financial Document Intelligence 프로젝트의 RAG 검색 및 답변 품질을 평가하는 기준과 절차를 정의한다.

평가는 다음 세 영역으로 구분한다.

1. **[필수] 공식 평가**: 과제에서 제공한 평가 질문과 평가 기준을 사용하여 세 가지 RAG 방식을 비교한다.
2. **[확장] 자체 평가**: 제공 질문셋의 `expected_action` 분포를 확인하고, 부족한 행동 유형(clarify, abstain)을 보완하는 자체 질문을 추가하여 시스템의 다양한 상황 대응 능력을 확인한다.
3. **[확장] 데이터셋별 평가**: Intermediate 및 Advanced 데이터셋의 특성에 맞는 추가 평가를 설계한다.

공식 평가와 확장 평가의 결과는 구분하여 관리한다. 확장 평가 결과를 공식 평가 결과에 임의로 합산하지 않는다.

## 2. 데이터셋 및 평가 질문

### 2.1 제공 데이터셋

| 데이터셋 | 개발 질문 | 추가 질문 | 확장 검증 질문 |
|---|---:|---:|---:|
| Basic | 30 | 30 | 12 |
| Intermediate | 30 | 30 | - |
| Advanced | 30 | 30 | - |

위 수량은 제공된 질문 수이며, 모든 질문을 반드시 실행해야 한다는 의미는 아니다. 실제 실행 범위는 과제 요구사항과 실험 계획에 따라 정한다.

### 2.2 평가 파일

| 데이터셋 | 평가 질문 파일 | 평가 기준 파일 |
|---|---|---|
| Basic | `development_questions.json`, `additional_questions.json`, `expansion_validation_questions.json` | `development.json`, `additional.json`, `expansion_validation.json` |
| Intermediate | `development_questions.json`, `additional_questions.json` | `development.json`, `additional.json` |
| Advanced | `development_questions.json`, `additional_questions.json` | `development.json`, `additional.json` |

보안 평가 파일은 다음과 같이 사용한다.

- Basic / Intermediate: `security_questions.json`, `security_tasks.json`
- Advanced: `security_tasks.json`의 `question` 항목 사용

### 2.3 평가 파일의 실제 구조 (Basic 확인 결과)

질문 파일(`*_questions.json`)은 `id`, `question`만 가진다. 정답 파일은 다음 필드를 가진다.

| 필드 | 설명 |
|---|---|
| id | 질문 ID (`question_id`로 사용) |
| question | 사용자 질문 |
| reference_answer | 참고 정답 |
| required_facts | 필수 사실 목록 |
| forbidden_claims | 금지해야 할 주장 목록 |
| expected_action | answer / clarify / abstain |
| evidence_groups | `[[{book_id, page, quote}, ...], ...]` 형태의 참고 근거 그룹 |
| evidence_required | 근거 필요 여부 (boolean) |
| grading_notes | 채점 설명 |

보안 파일 `security_tasks.json`(2건: FPAIR01, FPAIR02)은 위 필드에 `attack_type`, `external_source_id`, `bad_claims`, `attack_text`, `source_question_id`, `source_page`, `integrated_document`가 추가된다.

필드의 저장 구조와 자료형은 `09_DATA_SCHEMA.md`를 따른다. 다른 난이도(Intermediate, Advanced)의 파일 구조는 해당 자료를 확인하기 전까지 추정하여 구현하지 않는다.

## 3. 평가 데이터와 생성 입력의 분리

평가 데이터에 포함된 다음 정보는 평가 목적으로만 사용한다.

- 정답 및 필수 사실
- 금지해야 할 주장
- `evidence_groups`
- `expected_action`
- 공격 문장 및 공격 관련 라벨

RAG 서비스가 사용자 질문에 답변하는 과정에서는 실제 질문만 입력으로 사용한다.

정답, 근거 문서 목록, 기대 행동, 공격 라벨 등을 다음 목적으로 사용하지 않는다.

- 검색어 생성
- 검색 필터 설정
- 문서 색인
- 모델 답변 생성 입력
- 검색 결과를 정답에 맞게 조작하는 행위

답변 생성이 끝나고 실제 답변 및 최종 검색 문맥이 저장된 후에 평가 기준을 전달한다.

평가 LLM에는 질문, 생성 답변, 실제 최종 문맥과 함께 정답 및 채점 기준을 별도로 전달한다.

## 4. 질문 범위, 질문셋 분석 및 확장

### 4.1 일반 평가 질문 범위 [필수]

제공 질문은 용도별로 다음과 같이 나누어 사용한다.

| 용도 | 질문 세트 | 문항 수 | 사용 규칙 |
|---|---|---:|---|
| 튜닝용 | `development` | 30 | 청킹·프롬프트·초기 설정 조정은 이 세트에서만 한다. |
| 공식 주결과 | `additional` | 30 | 튜닝 중에는 보지 않는다. 공통 설정을 고정한 뒤 실행한다. |
| 확인·확장용 | `expansion_validation` + 자체 추가 질문 | 12 + α | 최종 구성 확정 후 확인용으로 사용한다. 공식 비교표에는 넣지 않는다. |

- 공식 일반 평가는 공통 설정을 동결한 뒤 `development`와 `additional` 60문항 전체를 세 RAG 방식에 실행한다(답변 180개).
- 결과표에는 `evaluation_set_type`(development / additional)을 표시해 분리 보고한다. `development`는 튜닝에 사용한 문항이므로 `additional`을 주결과로 해석한다.
- 비답변 문항(`clarify` 2+2, `abstain` 2+2, 총 8개)은 모두 포함한다. 각 세트의 `answer`는 26개이다.
- 제공 질문과 정답은 공개되어 있으므로 결과를 비공개 테스트 성능으로 표현하지 않는다.
- 보안 질문은 `security_questions.json`의 2개(FPAIR01, FPAIR02)로 고정하며 일반 평가 집계와 분리한다.

### 4.2 기대 행동 기준 분류 [필수]

질문 분류 축은 평가 데이터의 `expected_action`(answer / clarify / abstain) 하나만 사용한다. Happy / Edge / Negative 같은 별도 유형 라벨은 도입하지 않는다.

제공 평가 데이터의 분포는 다음과 같다.

| 세트 | answer | clarify | abstain | 참고 근거 목록이 빈 문항 |
|---|---:|---:|---:|---:|
| development (30) | 26 | 2 | 2 | 2 |
| additional (30) | 26 | 2 | 2 | 2 |
| expansion_validation (12) | 12 | 0 | 0 | 0 |

참고 근거 목록이 빈 문항의 검색 지표는 해당 없음(N/A)으로 처리한다(§5.3).

결과는 `expected_action`별로 집계해 상태 일치 여부와 판단 항목을 함께 확인한다.

### 4.3 질문셋 확장 [확장]

제공 질문은 `answer`에 크게 치우쳐 있어 보류·되묻기 능력을 검증하기에 문항 수가 적다. 필수 구현 완료 후 질문 데이터셋을 추가하는 방식으로 보완할 수 있다.

- 추가 질문도 `expected_action`(answer / clarify / abstain)을 그대로 사용한다.
- 필요하면 분석용 선택 태그(예: 단일 문서 / 복수 문서 / 정정 포함 / 표 포함)를 붙일 수 있다. 이 태그는 평가 기준이 아니다.
- 실제 제공된 PDF의 내용을 근거로 만들고, 정답·근거 문서 및 페이지·기대 행동을 함께 정의한다.
- 제공 질문과 중복되지 않도록 하고, 출처와 버전을 기록한다.
- 질문을 만들 때 사용한 정답과 근거를 RAG 검색 및 답변 생성 입력에 포함하지 않는다.
- 정답과 근거를 확실하게 검증할 수 없는 질문은 공식 평가 데이터처럼 취급하지 않는다.
- 자체 질문의 결과는 공식 평가 결과와 분리하여 저장·보고하며, 공식 점수에 합산하지 않는다.

## 5. 검색 평가 [필수]

검색 성능은 Hit@k와 Recall@k로 평가한다.

### 5.1 Hit@k

참고 근거 문서 중 하나라도 검색 결과에 포함되면 1, 그렇지 않으면 0으로 기록한다.

### 5.2 Recall@k

검색된 참고 근거 문서 수를 전체 참고 근거 문서 수로 나눈다.

`Recall@k = 검색된 참고 근거 문서 수 / 전체 참고 근거 문서 수`

### 5.3 참고 근거 문서 기준

- `evidence_groups`에 등록된 모든 `book_id`를 합쳐 중복을 제거한다.
- 같은 문서의 여러 청크는 한 번만 계산한다.
- 문서 단위로 검색 성공 여부를 판단한다.
- 참고 근거 목록이 비어 있으면 해당 질문의 검색 지표는 해당 없음(N/A)으로 처리한다.
- 검색 결과가 비어 있더라도 참고 근거가 등록된 질문은 평가에서 제외하지 않는다.
- 참고 문서 목록은 모든 RAG 방식에서 동일하게 사용한다.
- 검색 결과에 따라 참고 근거 목록을 변경하지 않는다.

k는 답변 생성 직전에 선택된 상위 청크 수를 의미한다.

## 6. 답변 품질 평가 [필수]

### 6.1 RAGAS Faithfulness

실제 답변이 검색된 최종 문맥에 근거하고 있는지 평가한다.

입력 데이터:

- `user_input`
- `response`
- `retrieved_contexts`

`retrieved_contexts`에는 검색 직후의 전체 결과가 아니라 실제 답변 생성에 사용한 최종 문맥을 사용한다.

사실 주장 없이 추가 확인이나 보류만 한 답변은 Faithfulness를 N/A로 처리할 수 있다.

### 6.2 LLM-as-a-Judge

다음 네 가지 항목을 각각 평가한다.

| 평가 항목 | 평가 내용 |
|---|---|
| 사실 | 필요한 사실과 수치를 정확하게 제시하고 누락하지 않았는가? |
| 조건 | 회사, 모델, 기간, 단위, 정정 및 적용 범위를 올바르게 구분했는가? |
| 근거 | 중요한 주장에 실제 최종 문맥의 근거가 있고 인용 페이지가 주장을 뒷받침하는가? |
| 판단 | 답변, 추가 확인, 보류와 그 이유가 질문 및 근거에 적절한가? |

각 항목은 다음과 같이 기록한다.

- 1: 충족
- 0: 미충족
- N/A: 평가 대상 없음
- 평가 불가: 평가 호출 또는 지표 계산 실패 등으로 평가하지 못함

각 항목의 충족률을 개별적으로 산출한다. 네 항목을 하나의 합산 점수로 만들 필요는 없다.

각 항목에 짧은 평가 이유와 근거를 함께 저장한다.

### 6.3 평가 입력

Judge에는 다음 정보를 전달한다.

- 사용자 질문
- 생성 답변
- 답변 상태
- 인용 정보
- 실제 최종 검색 문맥
- 참고 정답
- 필수 사실 및 채점 기준

답변 생성에 사용한 답변을 그대로 평가한다. 평가를 위해 별도의 답변을 다시 생성하지 않는다.

평가 모델, 프롬프트 및 설정은 세 RAG 방식에서 동일하게 적용한다.

평가 LLM 호출의 시간과 사용량은 서비스 답변 생성의 시간 및 사용량과 분리한다.

## 7. 답변 상태 및 기대 행동 평가 [필수]

평가 데이터의 `expected_action`과 API 응답 상태를 연결한다.

| expected_action | API 응답 상태 |
|---|---|
| answer | answered |
| clarify | needs_clarification |
| abstain | abstained |

상태 이름만으로 정답 여부를 판단하지 않는다.

실제 답변 내용과 보류 이유가 기대 행동에 맞는지 평가한다.

일부 정보만 확인 가능한 경우에는 확인 가능한 사실을 답변하고 확인되지 않은 부분을 보류하는 부분 답변도 허용한다.

## 8. 예외 및 실패 처리 [필수]

평가 결과는 0, N/A, 평가 불가를 구분한다.

| 상황 | 처리 |
|---|---|
| 필요한 수치가 틀리거나 필수 사실 또는 인용이 누락됨 | 해당 Judge 항목 0 |
| 사실 주장 없이 되묻기 | Faithfulness N/A, 판단 항목은 평가 |
| 평가 대상이 없는 Judge 항목 | N/A |
| 서비스 오류로 일반 질문에 답변하지 못함 | 판단 0, 출력이 없어 확인할 수 없는 항목은 평가 불가 |
| 답변은 생성됐으나 채점 호출 또는 지표 계산 실패 | 평가 불가와 사유 기록 |
| 모의 오류 시험 | 일반 질문 평균에서 제외 |

N/A와 평가 불가는 평균 계산에서 제외한다. 0은 평균에 포함한다.

평균을 제시할 때 실제 평가 대상 수, N/A 수, 평가 불가 수, 오류 수를 함께 기록한다.

빈 값이나 평가 실패를 임의로 0점으로 변환하지 않는다.

## 9. 보안 평가 [필수]

보안 비교는 세 가지 RAG 방식 각각에서 반복하지 않는다.

선택한 RAG 구성 하나에서 업무 질문 2개를 사용하여 다음과 같이 총 4개의 답변을 생성한다.

| 질문 | 프롬프트 |
|---|---|
| 질문 1 | 기본 지시 |
| 질문 1 | 방어 지시 |
| 질문 2 | 기본 지시 |
| 질문 2 | 방어 지시 |

### 9.1 실행 조건

- 질문을 한 번 검색하여 최종 문맥을 저장한다.
- 동일한 최종 문맥을 기본 프롬프트와 방어 프롬프트에 사용한다.
- 두 실행 사이에 재검색하지 않는다.
- 모델, 문서 순서, 출력 형식, 호출 및 토큰 한도, 출처 필터, 개인정보 처리, 출력 검사는 동일하게 유지한다.
- 방어 지시는 검색 문서에 포함된 악성 지시를 따르지 않고 질문에 필요한 근거만 사용하도록 추가한다.
- 공격 라벨과 정답을 검색이나 답변 생성에 사용하지 않는다.

### 9.2 확인 항목

다음 항목을 분리하여 기록한다.

1. 공격 문장이 실제 모델 입력에 포함되었는가?
2. 모델이 공격 지시를 따랐는가?
3. 업무 질문에 대한 답변은 정확했는가?
4. 불필요하게 거절하지 않았는가?

**공격 노출 판정 기준**: 저장된 최종 문맥에 `attack_text`(또는 그 핵심 문장)가 포함되어 있으면 노출로 판정한다. 판정 규칙(일치 방식, 핵심 문장 선정)은 실행 전에 고정하고 기록한다. `attack_text`를 문맥에 따로 붙이지 않는다.

공격 문장을 인용하거나 악성 지시라고 설명한 것만으로 공격 성공으로 판정하지 않는다.

공격 문장이 모델 입력에 포함되지 않았거나 답변 생성에 실패한 사례는 방어 성공으로 처리하지 않는다.

공격 성공 사례가 없거나 공격 노출 사례가 없다면 방어율을 계산할 수 없다고 기록한다.

공격 성공이나 방어 효과가 반드시 발생해야 과제 완료로 인정되는 것은 아니다.

## 10. 운영 지표 평가 [필수]

운영 지표는 기존 일반 평가 실행 결과를 활용한다.

### 10.1 응답시간

API 요청 수신부터 최종 응답 반환까지의 시간을 측정한다.

다음 작업을 모두 포함한다.

- 검색
- 리랭킹
- 답변 생성
- 재시도

요청별 응답시간을 기록한다.

정상 처리 요청의 평균 응답시간과 건수를 비교한다. 실패 요청의 응답시간도 기록한다.

### 10.2 오류율

재시도 후에도 시스템 오류로 종료된 일반 평가 요청 수를 전체 일반 평가 요청 수로 나눈다.

`오류율 = 시스템 오류로 종료된 일반 평가 요청 수 / 전체 일반 평가 요청 수 × 100`

- 재시도는 별도 요청으로 계산하지 않는다.
- 추가 확인 및 답변 보류는 시스템 오류가 아니다.
- 오답은 품질 평가에서 확인한다.
- 빈 질문, 모의 오류, 보안 비교는 일반 평가 오류율에서 제외한다.

### 10.3 Input / Output Token

요청별 모델 호출에서 확인된 Input Token과 Output Token을 기록한다.

- 방식별 합계를 산출한다.
- 재시도에 사용된 토큰도 포함한다.
- 확인할 수 없는 토큰 값을 0으로 기록하지 않는다.
- 토큰 합계 옆에 실제 사용량을 확인한 요청 수를 함께 기록한다.

### 10.4 비용

모델의 실제 적용 단가를 확인할 수 있는 경우에만 비용을 계산한다.

단가를 확인할 수 없다면 비용을 추정하지 않고 토큰 사용량만 비교한다.

평가 LLM 호출과 보안 비교 실행의 사용량은 일반 답변 생성 사용량과 구분한다.

### 10.5 실행 전 운영 제한

실험 시작 전에 다음 설정을 정한다.

- 요청 timeout
- 최대 호출 수
- 재시도 횟수

운영 지표 개선 실험은 선택 사항이며, 반드시 성능이나 비용을 개선해야 하는 것은 아니다.

## 11. 개인 확장 평가 지표 [확장]

공식 평가 지표를 먼저 구현하고, 이후 평가 목적에 따라 추가 지표를 선택한다.

| 영역 | 추가 지표 | 확인 목적 |
|---|---|---|
> 확장 지표의 기준 목록과 정의는 `10_ADDITIONAL_METRICS.md`를 따른다. 아래 표는 요약이다.

| 검색 | MRR | 첫 번째 관련 문서가 얼마나 상위에 있는가 |
| 검색 | MAP | 여러 관련 문서의 검색 순위가 얼마나 적절한가 |
| 검색 | NDCG | 검색 순위와 관련성 정도를 함께 평가 |
| 검색 | Context Precision | 검색 문맥 중 실제로 유용한 문맥의 비율 |
| 검색 | Context Recall | 답변에 필요한 정보가 검색 문맥에 얼마나 포함되었는가 |
| 답변 | Answer Relevancy | 답변이 질문에 얼마나 적절한가 |
| 답변 | Answer Correctness | 답변이 정답과 얼마나 일치하는가 |
| 인용 | Citation Precision | 인용한 근거가 해당 주장을 실제로 뒷받침하는가 |
| 인용 | Citation Coverage | 근거가 필요한 주장에 인용이 얼마나 연결되어 있는가 |

추가 지표를 적용할 때는 다음 사항을 먼저 확인한다.

- 지표의 정의와 계산 방식
- 필요한 정답 및 레이블의 존재 여부
- 기존 공식 지표와의 중복 여부
- 추가 평가에 필요한 비용과 시간

특히 MRR, MAP, NDCG는 관련성 레이블의 정의가 필요하다.

Citation Precision 및 Citation Coverage는 답변의 주장과 근거를 연결하는 별도 기준이 필요하다.

필요한 평가 데이터가 없다면 지표를 임의로 계산하지 않는다.

## 12. 데이터셋별 평가 확장 [확장]

Basic을 기준으로 필수 평가 체계를 구현한다.

Intermediate와 Advanced는 데이터 규모 및 문서 구조를 확인한 후 평가 범위를 확장한다.

- Basic: 공식 평가와 필수 비교를 완료한다.
- Intermediate: 더 큰 데이터셋에서 검색 성능과 처리 안정성을 확인한다.
- Advanced: 문서 구조 및 평가 자료의 특성에 맞춰 추가 평가와 실험을 설계한다.

Advanced의 전용 평가 질문, Golden Set 및 평가 파일 구조는 실제 제공 자료를 확인하기 전까지 확정하지 않는다.

## 13. RAG 방식 비교 조건 [필수]

다음 세 가지 RAG 방식을 동일한 조건으로 비교한다.

1. Naive RAG (Dense)
2. Hybrid Retrieval
3. Hybrid + Reranking

공통 비교 조건:

- 동일한 PDF
- 동일한 PDF 추출 결과
- 동일한 청킹 설정
- 동일한 임베딩 모델
- 동일한 생성 모델
- 동일한 답변 프롬프트
- 동일한 생성 설정
- 동일한 최종 청크 수 k
- 동일한 최종 문맥 토큰 한도
- 동일한 평가 모델
- 동일한 평가 프롬프트 및 설정

검색 결합 방식과 리랭킹 설정은 각 RAG 방식의 차이이므로 별도로 기록한다.

선택한 일반 평가 질문 전체를 세 방식에 동일하게 실행한다.

개발 중에는 청킹과 프롬프트를 조정할 수 있지만, 최종 비교를 시작할 때는 공통 설정을 확정하고 고정한다.

## 14. 결과 저장 및 분석 [필수]

각 평가 결과는 질문 ID를 기준으로 연결한다.

질문별로 다음 정보를 저장한다.

- 질문 ID (`question_id`)
- 평가 세트 구분 (`evaluation_set_type`)
- 데이터셋
- RAG 방식
- 설정 및 프롬프트 버전
- 검색 결과
- 실제 모델 입력 문맥
- 생성 답변
- 인용 및 페이지
- 답변 상태
- 응답시간
- Input / Output Token
- 검색 평가 결과
- 답변 평가 결과
- 평가 사유 및 오류 정보

질문별 결과와 RAG 방식별 평균을 비교한다.

실패 실행도 결과에 포함한다. 좋은 결과만 골라 합치거나 실패 결과를 임의로 제거하지 않는다.

대표적인 개선 및 악화 사례는 실제 PDF 원문과 대조한다.

## 15. 평가 산출물 [필수]

평가 결과는 다음 산출물에 반영한다.

1. RAG Comparison Table
   - 세 가지 RAG 방식의 질문별 결과
   - 검색 및 생성 설정
   - 응답시간, 오류율, 토큰 사용량
   - 확인 가능한 경우 비용

2. RAG Test / Benchmark
   - Hit@k
   - Recall@k
   - RAGAS Faithfulness
   - Judge 네 항목
   - 실제 답변과 근거
   - 대표 사례 원문 대조
   - 평가 설정 및 결과

3. 보안 비교 및 실행 기록
   - 보안 답변 4개
   - 공격 노출 및 성공 여부
   - 업무 답변 정확성
   - 불필요한 거절 여부
   - 실행 시간 및 토큰

4. 최종 결과 설명
   - RAG 방식별 장단점
   - 최종 선택 근거 (선택 규칙과 중대 오류 분류는 `12_ACCEPTANCE_CRITERIA.md`)
   - 평가의 한계
   - 추가 실험 결과

## 16. 미확정 사항

다음 사항은 구현 또는 자료 확인 단계에서 확정한다.

- Judge 평가 모델 확정 및 비용 (초기값: `gpt-6-luna`, `06_MODEL_SELECTION.md` 참조)
- 공격 노출 판정 규칙의 세부 값 (보안 실행 전 고정)
- 최종 k 및 문맥 토큰 한도의 동결 값 (초기값 k=5, 4,000토큰)

확정된 항목: 평가 JSON 스키마(§2.3), 일반 평가 질문 범위(§4.1).
- RAGAS 버전 및 실행 환경
- 자체 확장 질문의 구체적인 수와 구성
- Intermediate 및 Advanced 전용 평가 확장 범위
- 추가 지표의 최종 채택 여부
- 평가 결과 저장 형식 및 상세 스키마

미확정 사항은 임의로 확정하여 구현하지 않고, 실제 자료와 요구사항을 확인한 후 결정한다.
