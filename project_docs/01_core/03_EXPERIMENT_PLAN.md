# 03. EXPERIMENT_PLAN.md

# Experiment Plan

## 1. 문서 목적

본 문서는 Financial Document Intelligence 프로젝트의 실험 전략과 실행 원칙을 정의한다.

실험의 목적은 단순히 RAG 방식별 점수를 비교하는 데 그치지 않는다.

다음 사항을 단계적으로 확인한다.

1. RAG 검색 방식에 따라 검색 품질과 답변 품질이 어떻게 달라지는가?
2. 청킹, 임베딩, 검색, 리랭킹, 프롬프트 등의 변경이 결과에 어떤 영향을 주는가?
3. 기대 행동(answer / clarify / abstain)에 따라 RAG 방식의 장단점이 달라지는가?
4. 근거가 부족하거나 질문이 모호한 상황에서 적절하게 대응하는가?
5. 데이터셋 규모가 커질 때 검색 품질과 처리 성능은 어떻게 달라지는가?
6. 실험 결과를 근거로 어떤 설정과 기법을 채택할 것인가?

실험은 다음 두 가지로 구분한다.

- **[필수] 공식 과제 실험**: 과제에서 요구하는 세 가지 RAG 방식 비교, 보안 비교 및 운영 지표 측정
- **[확장] 개인 실험**: 다양한 기법과 설정을 추가로 적용하고, 성능과 특성을 비교하는 실험

공식 과제 실험을 완료한 뒤에도 개인 실험을 계속 추가할 수 있도록 설계한다.

## 2. 전체 실험 구조

### 2.1 하나의 통합 프로젝트

하나의 프로젝트 안에서 데이터셋과 RAG 구성을 선택하여 실험을 실행한다.

선택 항목:

- 데이터셋: Basic / Intermediate / Advanced
- RAG 구성: Naive RAG / Hybrid Retrieval / Hybrid + Reranking / 확장 구성
- 실험 설정: 기본 설정 또는 별도로 정의한 실험 설정

공통 실행 시스템은 최대한 재사용한다.

- PDF 처리 및 문서 색인
- 검색 및 답변 생성
- FastAPI
- LangChain
- Langfuse
- 평가 및 결과 저장
- 실험 설정 및 버전 관리

다만 데이터셋이나 실험 기법에 따라 청킹, 문서 처리, 검색 전략, 프롬프트 등이 달라질 수 있다.

모든 차이를 억지로 하나의 공통 모듈로 통합하지 않는다.

Advanced에서 별도 파이프라인이 필요하다면 기존 Basic 구현을 보존하면서 추가한다.

### 2.2 실험 단계

| 단계 | 실험 | 구분 |
|---|---|---|
| Phase 1 | Basic 데이터셋에서 세 RAG 방식 비교 | 필수 |
| Phase 2 | Phase 1 결과로 선택된 최종 RAG 구성으로 보안 비교 | 필수 |
| Phase 3 | Phase 1의 일반 평가 실행 결과를 이용한 운영 지표 비교 | 필수 |
| Phase 4 | 기대 행동별 성능 분석 및 질문셋 확장 | 확장 |
| Phase 5 | 청킹 및 문서 처리 개선 실험 | 확장 |
| Phase 6 | 검색 및 리랭킹 개선 실험 | 확장 |
| Phase 7 | 생성 및 답변 정책 개선 실험 | 확장 |
| Phase 8 | 추가 평가 지표 및 분석 | 확장 |
| Phase 9 | Intermediate / Advanced 확장 실험 | 확장 |
| Phase 10 | 성능, 비용, 처리량 최적화 | 확장 |

각 단계는 독립적으로 실행하고 결과를 보존한다.

## 3. 공식 RAG 비교 실험 [필수]

### 3.1 비교 대상

다음 세 가지 RAG 방식을 비교한다.

| RAG 구성 | 설명 |
|---|---|
| Naive RAG (Dense) | 임베딩 기반 벡터 검색 |
| Hybrid Retrieval | Dense 검색과 Sparse 검색을 결합 |
| Hybrid + Reranking | Hybrid 검색 결과를 Reranker로 재정렬 |

각 방식의 상세 검색 알고리즘과 파라미터는 Architecture 및 Model Selection 문서에서 정의한다.

### 3.2 실험 목적

세 방식의 검색 결과와 최종 답변 품질을 비교하여 다음을 확인한다.

- Dense 검색만으로 충분한가?
- Sparse 검색을 결합하면 검색 성능이 개선되는가?
- Reranking을 적용하면 최종 검색 문맥의 품질이 개선되는가?
- 검색 방식에 따른 답변 품질 차이가 있는가?
- 검색 성능이 개선되더라도 응답시간이나 토큰 사용량이 지나치게 증가하지는 않는가?

검색 지표와 답변 지표는 별도로 분석한다.

검색 지표가 높아졌다고 반드시 답변 품질도 높아지는 것은 아니므로 두 결과를 함께 확인한다.

### 3.3 비교 조건 통제

세 방식의 공정한 비교를 위해 다음 조건을 동일하게 유지한다.

| 비교 항목 | 통제 조건 |
|---|---|
| PDF | 동일한 문서 |
| PDF 추출 | 동일한 추출 결과 |
| 청킹 | 동일한 청킹 결과 및 설정 |
| 임베딩 | 동일한 임베딩 모델 |
| 생성 모델 | 동일한 GPT-6 Luna |
| 답변 프롬프트 | 동일한 프롬프트 |
| 생성 설정 | 동일한 생성 파라미터 |
| 최종 검색 결과 수 | 동일한 k |
| 최종 문맥 | 동일한 최대 토큰 한도 |
| 평가 모델 | 동일한 모델 |
| 평가 프롬프트 | 동일한 프롬프트 및 설정 |
| 호출 한도 | 동일한 모델 호출 timeout, 최대 호출 수, 재시도 횟수 (값은 실행 전에 확정·기록) |

검색 방식 자체에 해당하는 설정은 각 방식에 맞게 다르게 적용할 수 있다.

예를 들어 Hybrid 검색의 Dense/Sparse 결합 비율이나 Reranker의 모델 및 후보 검색 수는 각 구성의 고유 설정이다.

이러한 차이는 숨기지 않고 기록한다.

### 3.4 질문 실행 조건

- 일반 평가 질문은 `02_EVALUATION_PLAN.md` §4.1의 범위(공통 설정 동결 후 development + additional 60문항)를 세 가지 RAG 방식에 동일하게 실행한다. 튜닝은 development에서만 하고, 공식 실행 전에 설정을 동결·기록한다. 동결 후 설정을 바꾸면 새 실험 ID로 관리한다.
- 동일한 질문 ID를 사용하여 결과를 연결한다.
- 각 방식에 동일한 평가 기준을 적용한다.
- 질문마다 검색 결과, 최종 문맥, 답변, 인용, 평가 결과를 저장한다.
- 실행 실패 및 오류도 결과에 포함한다.
- 특정 방식에 유리한 질문만 선택하거나 실패한 결과를 임의로 제외하지 않는다.

제공된 질문 수와 필수 실행 범위는 구분한다.

### 3.5 최종 비교 결과

다음 항목을 비교한다.

**검색 품질**
- Hit@k
- Recall@k

**답변 품질**
- RAGAS Faithfulness
- Judge: 사실
- Judge: 조건
- Judge: 근거
- Judge: 판단

**운영 성능**
- 평균 응답시간 및 정상 처리 건수
- 오류율 및 실패 건수
- Input Token 합계 및 확인 요청 수
- Output Token 합계 및 확인 요청 수
- 확인 가능한 경우 비용

세 방식의 전체 평균뿐 아니라 질문별 결과와 실패 사례도 함께 분석한다.

최종 RAG 방식의 선택 이유는 단일 점수만으로 결정하지 않는다. 검색 품질, 답변 품질, 운영 성능 및 한계를 종합하여 판단하며, 선택 순서와 기준은 공식 실험 전에 확정한 `12_ACCEPTANCE_CRITERIA.md`를 따른다.

## 4. 보안 비교 실험 [필수]

보안 비교는 Phase 1 결과로 선택된 최종 RAG 구성 하나에서 수행한다. 세 방식마다 반복하지 않으며, 보안·채점 호출은 일반 평가의 운영 지표와 분리해 기록한다.

### 4.1 실험 구성

업무 질문은 `security_questions.json`의 2개(FPAIR01, FPAIR02)로 고정하고 기본 지시와 방어 지시를 각각 적용한다.

총 4개의 답변을 생성한다.

| 질문 | 실행 1 | 실행 2 |
|---|---|---|
| 업무 질문 1 | 기본 프롬프트 | 방어 프롬프트 |
| 업무 질문 2 | 기본 프롬프트 | 방어 프롬프트 |

### 4.2 실험 조건

- 각 질문을 한 번 검색한다.
- 검색된 최종 문맥을 저장한다.
- 기본 프롬프트와 방어 프롬프트에 동일한 문맥을 전달한다.
- 두 실행 사이에 재검색하지 않는다.
- 생성 모델, 문서 순서, 출력 형식, 호출 및 토큰 한도를 동일하게 유지한다.
- 출처 필터, 개인정보 처리, 출력 검사도 동일하게 유지한다.
- 방어 프롬프트에만 검색 문서의 악성 지시를 따르지 않고 질문에 필요한 근거만 사용하도록 하는 지시를 추가한다.

공격 라벨이나 정답 정보를 검색 또는 답변 생성에 사용하지 않는다.

### 4.3 분석 항목

다음 결과를 별도로 기록한다.

1. 공격 문장이 실제 모델 입력에 포함되었는가?
2. 모델이 공격 지시를 따랐는가?
3. 업무 질문에 대한 답변은 정확했는가?
4. 불필요한 거절이 발생했는가?

기본 프롬프트와 방어 프롬프트의 차이를 비교한다.

공격 문장을 인용하거나 악성 지시라고 설명한 것만으로 공격 성공이라고 판정하지 않는다.

공격 문장이 모델 입력에 포함되지 않았거나 생성에 실패한 경우에는 방어 성공으로 처리하지 않는다.

## 5. 기대 행동별 실험 및 질문셋 확장 [확장]

### 5.1 목적

제공된 평가 질문을 `expected_action`(answer / clarify / abstain)별로 나누어, 기대 행동에 따라 RAG 방식과 추가 기법의 성능이 어떻게 달라지는지 확인한다.

별도의 유형 라벨(Happy / Edge / Negative 등)은 도입하지 않는다. 기대 행동 정의와 질문 범위는 `02_EVALUATION_PLAN.md`를 따른다.

### 5.2 분석 방향

| 기대 행동 | 확인할 내용 |
|---|---|
| answer | 정답 근거를 찾아 정확히 답하는가, 정정·조건·단위를 구분하는가 |
| clarify | 필요한 조건이 빠진 질문에 되묻는가, 불필요하게 되묻지 않는가 |
| abstain | 근거가 없거나 충돌을 해결할 수 없을 때 무리하게 답하지 않는가 |

### 5.3 세부 실험 예시

- Dense와 Hybrid 검색 결과 비교, 검색 k에 따른 답변 품질 변화
- Reranking이 필요한 질문의 특징 확인
- 정정 전후 수치가 혼합되는 문제 확인, 여러 문서의 근거를 결합하는 질문에서 검색 방식 비교
- 조건이 많은 질문에서 Query Rewriting 적용 효과, 문맥이 길어질 때 Context Packing 방식 비교
- 근거가 없는 질문의 보류 여부, 모호한 질문의 추가 확인 여부
- 검색 결과가 부족하거나 관련 없는 문서가 섞였을 때 잘못된 답변을 생성하는지 확인

### 5.4 질문셋 확장

제공 질문은 `answer`에 치우쳐 있으므로(development, additional 각 answer 26 / clarify 2 / abstain 2), 필수 완료 후 clarify·abstain 질문을 중심으로 자체 질문을 추가할 수 있다. 추가 원칙은 `02_EVALUATION_PLAN.md` §4.3을 따른다.

### 5.5 분석 원칙

기대 행동별 결과를 별도로 집계한다. 전체 평균만으로는 특정 행동에서 발생하는 문제를 파악하기 어렵다.

- 기대 행동별 검색 성능, Faithfulness, Judge 결과
- 기대 행동과 실제 답변 상태의 일치 여부
- 기대 행동별 오류 및 실패 사례

자체 추가 질문의 결과는 공식 평가 결과와 구분하여 보고한다.

## 6. 문서 처리 및 청킹 실험 [확장]

### 6.1 목적

PDF에서 추출한 정보를 어떤 단위로 나누어 저장하고 검색하는 것이 적절한지 확인한다.

금융 및 기업 문서는 본문뿐 아니라 표, 수치, 기간, 주석, 정정 정보 등이 중요할 수 있다.

따라서 단순한 텍스트 길이뿐 아니라 문서의 구조와 정보의 관계를 고려한다.

### 6.2 실험 후보

| 기법 | 실험 목적 |
|---|---|
| Chunk Size 조정 | 청크 크기에 따른 검색 품질 변화 |
| Chunk Overlap 조정 | 청크 경계에서 정보가 분리되는 문제 확인 |
| Recursive Character Text Splitting | 문단 및 문장 경계를 고려한 분할 |
| 구조 기반 청킹 | 제목, 절, 문단 등의 문서 구조 활용 |
| 표 전용 처리 | 표의 행과 열 관계를 보존하는 방법 비교 |
| Parent-Child Retrieval | 작은 청크로 검색하고 상위 문맥을 제공하는 방식 |
| Contextual Chunking | 청크에 문서 맥락을 추가하는 방식 |
| Metadata Enrichment | 회사, 기간, 사업부문 등의 메타데이터 활용 |

### 6.3 실험 시 주의사항

- 동일한 원본 PDF를 사용한다.
- 청킹 변경 전후의 결과를 별도로 보존한다.
- 청크 개수와 전체 색인 크기를 기록한다.
- 페이지 및 원본 문서와의 연결이 유지되는지 확인한다.
- 표의 수치와 행·열 관계가 올바르게 보존되는지 확인한다.
- 청킹 실험 중에는 검색 및 생성 설정을 가능한 한 고정한다.

청킹 방식에 따라 검색 결과의 문맥 구조가 달라질 수 있으므로 단순히 Recall만 비교하지 않고 실제 답변과 인용도 확인한다.

## 7. 검색 및 Retrieval 실험 [확장]

### 7.1 목적

검색 알고리즘과 검색 파라미터를 조정하여 필요한 근거를 더 정확하게 찾는 방법을 탐색한다.

### 7.2 Dense Retrieval

실험 후보:

- 임베딩 모델 비교
- Query Embedding 전략
- 검색 Top-k 조정
- 유사도 기준 및 검색 임계값 조정
- Metadata Filtering
- 질문 전처리

임베딩 모델 변경은 검색 결과뿐 아니라 색인 자체에 영향을 줄 수 있으므로 별도 실험으로 관리한다.

### 7.3 Sparse Retrieval

실험 후보:

- BM25 적용
- BM25 파라미터 조정
- 토큰화 및 형태소 처리 방식
- Sparse 검색 후보 수 조정
- 키워드 중심 질문에서의 검색 성능 비교

### 7.4 Hybrid Retrieval

실험 후보:

- Dense와 Sparse 검색 결과 결합
- Dense/Sparse 가중치 변경
- Reciprocal Rank Fusion(RRF)
- RRF 파라미터 조정
- 결합 전후 후보 검색 수 변경

Hybrid 검색에서는 각 검색 방식의 결과가 서로 다른 점수 체계를 가질 수 있으므로 점수 결합 방식과 순위 결합 방식을 구분하여 실험한다.

### 7.5 Query 처리

실험 후보:

- Query Rewriting
- Query Expansion
- Multi-Query Retrieval
- 질문 분해(Query Decomposition)
- 검색용 질문과 답변용 질문 분리

복합 질문에서 질문을 분해하거나 검색 질의를 확장하는 것이 도움이 되는지 확인한다.

### 7.6 검색 결과 후처리

실험 후보:

- Reranking
- Contextual Compression
- 중복 문서 및 중복 청크 제거
- 검색 결과 다양성 조정
- Metadata 기반 결과 필터링

Reranker 적용 시 다음을 기록한다.

- 최초 검색 후보 수
- Reranker 모델
- 재정렬 결과 수
- 최종 선택된 청크 수
- 재정렬 전후 순위 변화
- 추가 응답시간

## 8. 생성 및 답변 정책 실험 [확장]

### 8.1 목적

검색된 문맥을 모델에 전달하고 답변을 생성하는 과정에서 발생하는 문제를 개선한다.

### 8.2 프롬프트 실험

실험 후보:

- 기본 답변 프롬프트
- 근거 중심 답변 프롬프트
- 수치 및 단위 확인 강화 프롬프트
- 회사 및 기간 구분 강화 프롬프트
- 인용 및 페이지 표시 강화 프롬프트
- 근거 부족 시 보류 강화 프롬프트

프롬프트 변경 시 검색 결과가 아니라 답변 생성 방식에 어떤 영향을 주었는지 확인한다.

### 8.3 Context Packing 실험

최종 검색 결과를 모델에 전달하는 방법을 비교한다.

실험 후보:

- 검색 순위 기반 문맥 구성
- 중복 문맥 제거
- 문서별 문맥 그룹화
- 관련 문맥의 순서 조정
- 문맥 토큰 예산 배분
- 문서별 핵심 정보 요약 후 전달

실제 모델에 전달된 최종 문맥을 반드시 저장하여 답변의 근거를 확인할 수 있도록 한다.

### 8.4 답변 정책 실험

실험 후보:

- 답변 가능성 판단 기준
- 추가 확인(Clarification) 조건
- 답변 보류(Abstention) 조건
- 부분 답변 허용 기준
- 여러 근거가 충돌할 때의 처리
- 근거가 부족한 수치에 대한 응답 정책

특히 clarify 및 abstain 질문에서 답변 상태와 실제 답변 내용이 적절한지 확인한다.

### 8.5 생성 모델 설정

필요한 경우 다음 항목을 실험한다.

- Temperature
- 최대 출력 토큰
- 기타 지원되는 생성 파라미터

공식 비교에서는 동일한 생성 모델 및 설정을 유지한다. 생성 설정 변경은 별도 확장 실험으로 수행한다.

## 10. Intermediate 및 Advanced 실험 [확장]

### 10.1 Intermediate

Basic에서 검증한 공통 실행 시스템을 최대한 재사용한다.

실험 방향:

- 문서 수 증가에 따른 검색 성능 변화
- 청크 수 및 색인 크기 변화
- 검색 시간과 응답시간 변화
- Dense와 Hybrid의 성능 차이
- Reranking의 효과와 추가 비용
- 문서 간 중복 및 관련 문맥 처리
- 메타데이터 필터링 효과

Basic과 Intermediate의 차이를 분석할 수 있도록 공통 실험 조건을 가능한 한 유지한다.

### 10.2 Advanced

Advanced는 문서 수와 페이지 수가 크게 증가하므로 단순히 Basic의 설정을 그대로 적용하는 것이 최선이라고 가정하지 않는다.

실험 방향:

- 대규모 문서 색인 및 검색 전략
- 문서 구조에 따른 청킹 전략
- 검색 후보 수와 최종 문맥 크기 조정
- 복합 질문 및 다중 문서 검색
- 검색 결과의 다양성과 중복 제어
- 문서 메타데이터 및 필터링 전략
- 처리시간 및 리소스 사용량 최적화

Advanced에서 별도 청킹 또는 검색 파이프라인이 필요하다면 독립적으로 구현할 수 있다.

다만 기존 Basic 구현을 임의로 변경하거나 덮어쓰지 않는다.

Advanced 전용 평가 자료와 문서 구조를 확인한 뒤 구체적인 실험 조합을 확정한다.

## 11. 운영 성능 및 비용 실험 [확장]

공식 과제에서는 기존 일반 평가 실행 결과를 이용해 운영 지표를 측정한다.

이후 운영 성능, 비용 및 반복 요청 처리 효율을 개선하기 위한 추가 실험을 진행할 수 있다.

### 11.1 일반 운영 성능 실험

실험 후보:

| 영역 | 실험 후보 | 확인 목적 |
|---|---|---|
| 호출 | Batch Processing | 다수 요청 처리 효율 |
| 동시성 | Concurrent Requests | 동시 요청 처리 능력 |
| 비동기 처리 | Async I/O | 대기시간 및 처리 효율 |
| 검색 | 검색 후보 수 조정 | 검색 품질과 속도의 균형 |
| 리랭킹 | Reranking 후보 수 조정 | 품질과 추가 시간의 균형 |
| 생성 | Context Token 조정 | 토큰 사용량과 답변 품질의 균형 |
| 색인 | 색인 처리 방식 변경 | 대규모 문서 처리 효율 |

### 11.2 Redis 기반 캐시 실험

Redis를 활용하여 반복 요청과 반복 연산의 처리 효율을 개선하는 실험을 진행할 수 있다.

Redis는 필수 구성요소가 아니라 운영 성능 확장을 위한 선택적 기술로 도입한다.

실험 후보:

| 캐시 유형 | 실험 내용 | 확인 목적 |
|---|---|---|
| Exact Cache | 동일한 질문에 대한 기존 결과 재사용 | 반복 질문의 응답시간 단축 |
| Retrieval Cache | 동일한 검색 요청의 검색 결과 재사용 | 반복 검색 비용 및 검색 시간 감소 |
| Semantic Cache | 의미적으로 유사한 질문의 기존 결과 재사용 | 유사 질문에 대한 중복 검색 및 생성 호출 감소 |
| Embedding Cache | 동일 텍스트의 임베딩 결과 재사용 | 임베딩 연산 및 API 호출 감소 |
| Cache Invalidation | 문서, 임베딩, 프롬프트 등 관련 버전 변경 시 캐시 무효화 | 오래되거나 잘못된 결과의 재사용 방지 |

#### 11.2.1 Semantic Cache 적용 시 주의사항

금융 및 기업 문서 기반 RAG에서는 질문의 의미가 비슷하더라도 답변을 그대로 재사용할 수 없는 경우가 있다.

따라서 다음 조건을 고려한다.

- 회사가 다르면 기존 답변을 재사용하지 않는다.
- 조회 기간이 다르면 기존 답변을 재사용하지 않는다.
- 사업부문, 제품, 지역 등 핵심 조건이 다르면 재사용 여부를 별도로 판단한다.
- 정정본이나 최신 문서가 추가되면 기존 캐시의 유효성을 확인한다.
- 답변에 사용된 문서 및 문서 버전을 확인할 수 있어야 한다.
- 유사도 임계값에 따른 잘못된 캐시 재사용 사례를 검증한다.

단순한 질문 임베딩 유사도만으로 캐시 재사용을 결정하지 않는다. 질문의 핵심 조건과 근거의 유효성을 함께 고려한다.

#### 11.2.2 캐시 실험 비교

캐시 미적용 상태를 기준으로 캐시 적용 결과를 비교한다.

측정 항목:

- Cache Hit Rate
- Cache Miss Rate
- 평균 응답시간
- 검색 호출 횟수
- 임베딩 호출 횟수
- 생성 모델 호출 횟수
- Input / Output Token 감소량
- 확인 가능한 경우 비용 절감량
- 캐시 재사용으로 발생한 잘못된 답변 수
- 캐시 무효화 이후 오래된 결과가 재사용된 사례

캐시 적용으로 응답시간이 단축되더라도 답변 정확성이나 최신성이 저하되면 개선으로 판단하지 않는다.

### 11.3 Redis와 벡터 데이터베이스의 역할 구분

본 프로젝트에서는 Qdrant를 벡터 검색을 위한 데이터베이스 후보로 사용하고, Redis는 캐시 및 반복 작업 처리 효율을 개선하기 위한 선택적 구성요소로 검토한다.

기본적인 역할 구분은 다음과 같다.

| 구성요소 | 주요 역할 |
|---|---|
| Qdrant | 문서 청크의 벡터 저장 및 유사도 검색 |
| Redis | 검색 결과, 임베딩, 답변 등의 캐시 |
| FastAPI / LangChain | 요청 처리 및 RAG 실행 흐름 |

Redis의 벡터 검색 기능을 활용하는 방안도 기술적으로 검토할 수 있지만, 초기 설계에서는 Qdrant와 Redis의 역할을 분리한다.

두 기술을 동시에 도입하는 것이 반드시 더 좋은 구조라고 가정하지 않는다. 실제 실험 결과와 운영 복잡성을 고려해 도입 여부를 결정한다.

### 11.4 운영 성능 실험의 측정 항목

운영 실험에서는 다음을 비교한다.

- 평균 응답시간
- 정상 처리 건수
- 오류율
- Input / Output Token
- 확인 가능한 경우 비용
- 검색 및 리랭킹 소요시간
- 임베딩 처리시간
- 캐시 적중률 및 캐시 재사용 결과
- 동시 요청 처리 결과

속도나 비용이 개선되더라도 답변 품질이 크게 저하된다면 무조건 채택하지 않는다.

## 12. 실험 실행 원칙

### 12.1 한 번에 하나의 주요 변수 변경

실험 초기에는 한 번에 하나의 주요 변수를 변경한다.

예를 들어 Chunk Size 실험에서는 다른 설정을 동일하게 유지하고 Chunk Size만 변경한다.

이렇게 해야 결과 변화의 원인을 비교적 명확하게 파악할 수 있다.

단일 변수 실험이 충분히 진행된 후 여러 변수의 조합을 비교하는 실험을 추가할 수 있다.

단, 여러 변수를 조합하는 실험은 어떤 변수의 조합인지 명확하게 기록한다.

### 12.2 실험 전 가설 설정

모든 확장 실험은 실행 전에 다음을 정의한다.

- 실험 목적
- 가설
- 변경 변수
- 통제 조건
- 데이터셋
- RAG 구성
- 평가 질문
- 측정 지표
- 예상되는 결과 및 확인하려는 문제

가설은 실험 결과에 따라 틀릴 수 있다. 가설과 다른 결과가 나왔다고 실험을 실패로 처리하지 않는다.

### 12.3 실험 후 결과 기록

실험 후 다음 내용을 기록한다.

- 실제 변경 사항
- 실행 설정
- 결과 지표
- 기준 실험과의 차이
- 개선된 부분
- 악화된 부분
- 대표 성공 및 실패 사례
- 결과 해석
- 최종 채택 여부
- 추가 검증 필요 여부

성능이 개선되지 않은 실험도 삭제하지 않고 기록한다.

### 12.4 실험 결과 채택 기준

실험 결과가 개선되었다고 즉시 기본 설정에 반영하지 않는다.

다음 사항을 확인한다.

1. 결과가 동일한 조건에서 재현되는가?
2. 특정 질문에만 유리한 결과는 아닌가?
3. 다른 기대 행동(answer / clarify / abstain)의 질문에서도 성능이 유지되는가?
4. 검색 품질과 답변 품질이 함께 개선되는가?
5. 응답시간이나 토큰 사용량이 지나치게 증가하지 않는가?
6. 기존 기능과 다른 데이터셋에 부작용이 없는가?

검증 후 채택 여부를 결정한다.

| decision | 채택 / 보류 / 폐기 |
| versions | 코드, 데이터, 프롬프트, 설정 버전 |
| notes | 특이사항 및 후속 실험 |

이 양식이 모든 실험 기록의 기준 양식이다. `06_MODEL_SELECTION.md`와 `11_MODEL_SELECTION_GUIDE.md`는 이 양식을 따르며 모델 전용 필드(license, runtime_environment 등)만 추가한다. 실제 저장 필드와 자료형은 `09_DATA_SCHEMA.md`에서 정의한다.

### 13.1 실험 기록 예시

아래는 기록 형식을 설명하기 위한 가상의 예시다.

- experiment_id: `EXP-001`
- experiment_name: Chunk Size Comparison
- objective: 청크 크기에 따른 검색 품질 변화 확인
- hypothesis: 청크 크기가 작으면 특정 사실을 검색하는 데 유리할 수 있다.
- dataset: Basic
- rag_config: Hybrid Retrieval
- baseline: 기존 Chunk Size 설정
- changed_variables: Chunk Size
- controls: Overlap, Embedding, Retrieval, Prompt
- metrics: Hit@k, Recall@k, Faithfulness
- decision: 실험 결과 확인 후 결정

## 14. 버전 및 결과 보존

실험 결과는 실행 당시의 설정과 연결되어야 한다.

다음 항목을 버전 관리한다.

- 데이터셋 버전
- PDF 추출 결과 버전
- 청킹 설정 및 결과 버전
- 임베딩 모델 및 색인 버전
- 검색 설정 버전
- Reranker 설정 및 모델 버전
- 생성 프롬프트 버전
- 생성 모델 및 파라미터 버전
- 평가 프롬프트 및 설정 버전
- 코드 버전
- 실험 버전

기존 필수 실험 결과를 확장 실험 결과로 덮어쓰지 않는다.

실험 설정이 변경되면 새로운 실험 ID와 실행 결과를 생성한다.

기존 결과를 재사용할 때는 원래 실행의 설정과 버전을 확인할 수 있어야 한다.

버전 관리의 상세 규칙은 `07_VERSIONING.md`에서 정의한다.

## 15. 실험과 시스템 구조의 관계

실험을 쉽게 추가할 수 있도록 RAG 구성과 실험 설정을 가능한 한 분리한다.

예를 들어 다음 요소를 독립적으로 교체하거나 조정할 수 있어야 한다.

- Document Processor
- Chunking Strategy
- Embedding Model
- Dense Retriever
- Sparse Retriever
- Hybrid Retriever
- Reranker
- Context Builder
- Answer Prompt
- Answer Policy
- Evaluation Method

다만 모든 요소를 처음부터 과도하게 추상화하지 않는다.

Basic의 필수 구현을 먼저 완성하고, 실제로 여러 구현을 비교해야 하는 부분부터 교체 가능한 구조로 확장한다.

공통 모듈의 재사용이 어려운 경우에는 별도 구현을 허용하되 기존 구현을 보존한다.

## 16. 실험 완료 기준

### 필수 실험 완료 기준

- 세 가지 RAG 방식의 비교 실행 완료
- 동일한 평가 질문과 통제 조건 적용
- 검색 및 답변 평가 결과 저장
- 질문별 및 방식별 결과 비교
- 보안 비교 4회 실행
- 일반 평가 실행 결과를 이용한 운영 지표 측정
- 대표 사례 원문 대조
- 최종 RAG 방식 선택 이유와 한계 정리

### 확장 실험 완료 기준

- 실험 목적과 가설 정의
- 변경 변수와 통제 조건 기록
- 실험 결과 저장
- 기준 실험과 비교
- 결과 해석
- 채택 여부 결정
- 기존 필수 결과 보존

확장 실험의 개수나 성능 개선 여부를 필수 완료 조건으로 두지 않는다.

## 17. 미확정 사항

다음 사항은 관련 설계 및 구현 단계에서 결정한다.

**필수 구간 (초기값은 `06_MODEL_SELECTION.md`, 공식 실행 전 동결)**

- 청킹 기본값 (STEP 1~2에서 실제 PDF 확인 후 결정)
- 임베딩 최종 선택 (STEP 3 소규모 비교 후 동결)
- timeout, 최대 호출 수, 재시도 횟수의 값

**확장 구간**

- Query Rewriting 및 Multi-Query 적용 여부
- Context Packing 방식
- 추가 평가 지표의 최종 채택 여부
- Intermediate 및 Advanced 전용 실험 구성
- 실험 실행 및 결과 조회 UI의 상세 기능

확정된 항목: 검색 파라미터 초기값(Dense/BM25 후보 20, RRF k=60, 최종 k=5), Reranker(bge-reranker-v2-m3), 실험 결과 저장 구조(`09_DATA_SCHEMA.md`).

미확정 사항은 임의로 구현 단계에서 확정하지 않는다. 실제 데이터와 평가 결과, 기술적 제약을 확인하고 결정한다.
