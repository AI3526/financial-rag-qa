# 08. DEVELOPMENT_PLAN.md
# 개발 단계 및 구현 계획

## 1. 문서 목적

본 문서는 RAG 프로젝트의 설계 내용을 실제 구현으로 옮기기 위한 개발 순서, 작업 단위, 테스트 방법, 완료 조건 및 변경 승인 절차를 정의한다.

주요 목적은 다음과 같다.

1. 승인된 설계 문서를 기준으로 단계별 구현을 진행한다.
2. 한 번에 하나의 작은 작업 단위로 개발한다.
3. 구현 전 작업 범위와 완료 조건을 확인한다.
4. 구현 후 테스트 결과를 확인하고 다음 작업으로 넘어간다.
5. 설계 변경이 필요한 경우 사용자 승인 없이 임의로 적용하지 않는다.
6. Basic 데이터셋을 이용해 공식 필수 과제를 먼저 완성한다.
7. Intermediate, Advanced 및 추가 실험은 기본 기능을 보존하면서 확장한다.
8. 개발 과정과 실험 결과를 기록해 재현할 수 있도록 한다.

본 문서는 전체 개발 진행 계획을 정의한다. 개별 기능의 상세 요구사항은 각 설계 문서를 따른다.

## 2. 개발 기본 원칙

### 2.1 설계 우선 원칙 [필수]

1. 승인된 설계 문서를 구현의 기준으로 사용한다.
2. 설계 문서에 명시되지 않은 기능이나 기술을 임의로 추가하지 않는다.
3. 기술적 문제가 발생해도 기존 설계를 임의로 변경하지 않는다.
4. 설계 변경이 필요하면 먼저 사용자에게 원인과 대안을 보고한다.
5. 사용자가 승인하기 전에는 변경 사항을 적용하지 않는다.
6. 구현 과정에서 설계 문서 간 충돌을 발견하면 임의로 해석하지 않고 보고한다.

### 2.2 작은 작업 단위 원칙 [필수]

- 한 번에 하나의 작업만 수행한다.
- 한 작업에서 지나치게 많은 파일을 수정하지 않는다.
- 요청하지 않은 다음 단계 작업을 미리 구현하지 않는다.
- 작업 범위를 벗어나는 리팩터링이나 코드 정리를 하지 않는다.
- 작업 완료 후 테스트와 결과 확인을 진행한다.
- 사용자 확인이 필요한 단계에서는 확인을 기다린다.

### 2.3 사용자 확인 원칙 [필수]

사용자는 코드 구현을 직접 세밀하게 검토하기 어려울 수 있으므로, Claude Code는 코드 변경뿐 아니라 구현 결과와 테스트 의미를 이해할 수 있도록 설명한다.

- 전문 용어는 간단히 설명한다.
- 오류 발생 시 원인과 해결 방향을 설명한다.
- 테스트가 통과했다는 사실만 보고하지 않고 무엇을 확인했는지 설명한다.
- 실행하지 않은 테스트를 통과했다고 보고하지 않는다.
- 확인하지 못한 사항은 확인하지 못했다고 명시한다.

### 2.4 필수와 확장 구분 [필수]

모든 개발 작업은 다음과 같이 구분한다.

- [필수]: 공식 과제 완성과 기본 프로젝트 실행에 필요한 기능
- [확장]: 기본 기능 완성 이후 추가하는 개인 실험 및 개선 기능

확장 기능은 필수 기능을 대체하거나 훼손하지 않는다.

## 3. 개발 단계 전체 구성

STEP 번호는 작업 단위의 식별자이며, **실행 순서는 아래 "실행 순서"를 따른다.**

### 실행 순서

먼저 Naive RAG를 질문부터 답변까지 끝까지 연결한 뒤, 같은 API에서 `rag_method`만 바꿔 Hybrid와 Reranking을 추가한다(과제 원본 step5의 안내).

```text
STEP 0 -> 1 -> 2 -> 3 -> 4 -> 7 -> 8 -> 9      (Naive RAG가 질문 -> 답변까지 동작, Langfuse 기본 기록 포함)
       -> 5 -> 6                                (BM25·Hybrid, Rerank 추가)
       -> 10 -> 11 -> 12 -> 13 -> 14 -> 15      (통합 검증, 평가, 공식 비교, 보안, 운영 지표, 문서화)
```

STEP 16~18은 필수 완료 후의 [확장]이다.

## 4. STEP 0. 개발 환경 및 프로젝트 초기 설정

### 목적

개발에 필요한 환경과 프로젝트의 기본 구조를 준비한다.

### 작업 항목

### 0. 개발 환경 구성 및 기본 관측 환경 구축

**목표:** 프로젝트 실행 환경을 구성하고, 초기 개발 단계부터 Langfuse에 실행 기록을 남길 수 있는 기반을 마련한다.

**[필수]**
- Python 3.12 및 프로젝트 가상환경 구성 (`uv` 사용. Windows Store의 `python` 별칭은 사용하지 않는다)
- Git 저장소 초기화 (`git init`, `.gitignore`: `.env`, 벡터 DB 데이터, 모델 가중치, 캐시 제외)
- 환경변수 및 API Key 관리
- OpenAI API 연결 확인 (`gpt-6-luna` 호출, 지원 파라미터 확인)
- Langfuse Cloud 프로젝트 생성 및 연결 설정 (계정과 API 키는 사용자가 직접 발급해 `.env`에 입력, SDK 버전은 공식 문서로 확인)
- Langfuse 인증 확인
- 테스트용 Trace 생성 및 Langfuse 화면에서 기록 확인
- 프로젝트 공통 관측 초기화 코드 구성
- `trace_id`, `request_id` 등 식별자 관리 원칙 적용

**완료 조건**
- 프로젝트가 정상적으로 실행된다.
- OpenAI API 연결을 확인한다.
- Langfuse 연결 및 인증이 정상적으로 동작한다.
- 테스트 실행의 Trace가 Langfuse에 실제로 기록되는 것을 확인한다.
- API Key 등 민감정보가 기록에 노출되지 않는 것을 확인한다.

**주의사항**
- 이 단계에서는 전체 기능의 상세 계측을 구현하지 않는다.
- 이후 각 기능을 구현할 때 해당 기능의 실행 기록을 함께 추가한다.
- Langfuse 연결 실패가 문서 추출이나 기본 개발 테스트까지 불필요하게 차단하지 않도록 장애 처리 방식을 고려한다.

#### 0.1 개발 환경 확인 [필수]

- Python 버전 확인
- 운영체제 및 실행 환경 확인
- Git 설치 및 사용 가능 여부 확인
- Claude Code 실행 환경 확인
- 필요한 패키지 설치 가능 여부 확인
- OpenAI API 및 Langfuse 계정·키 준비 상태 확인
- Qdrant 실행 방식: `qdrant-client` 로컬(내장) 모드로 시작한다(Docker 없음). 설정값으로 서버 모드 전환이 가능하게 작성한다.
- 로컬 모델 실행 환경: RTX 5060(Blackwell)용 PyTorch(CUDA 12.8 이상) 설치를 확인한다. 문제가 있으면 CPU로 대체한다.

확인한 환경과 버전은 `DECISIONS.md`에 기록한다(추측 버전은 적지 않는다).

#### 0.2 프로젝트 디렉터리 구성 [필수]

`04_ARCHITECTURE.md` §10의 구조를 기준으로 필요한 디렉터리부터 만든다. 빈 모듈을 미리 만들지 않으며, 구조를 임의로 변경하지 않는다.

#### 0.3 환경변수 관리 [필수]

- API 키 및 비밀정보를 환경변수로 관리한다.
- `.env` 파일은 Git에 포함하지 않는다.
- `.env.example`에는 필요한 변수 이름만 작성한다.
- 실제 API 키를 코드나 로그에 출력하지 않는다.

#### 0.4 기본 실행 테스트 [필수]

- Python 실행
- 패키지 설치
- 환경변수 로딩
- 기본 프로젝트 실행
- Git commit

### 완료 조건

- 개발 환경에서 프로젝트를 실행할 수 있다.
- 비밀정보가 Git에 포함되지 않는다.
- 기본 디렉터리 구조가 생성되어 있다.
- 설치 및 실행 방법이 기록되어 있다.

## 5. STEP 1. PDF 데이터 확인 및 문서 처리

### 개발 단계별 Langfuse 계측 원칙

**[필수]**

Langfuse는 초기 개발 단계에서 연결하고, 이후 각 기능을 구현할 때 해당 기능의 관측 기록을 함께 구현한다.

| 개발 단계 | 함께 구현할 관측 기록 |
|---|---|
| PDF 추출 | 문서 처리 실행, 추출 결과, 페이지 정보, 처리 시간, 오류 |
| 청킹 및 메타데이터 | 청킹 설정, Chunk 수, Chunk 식별자, 메타데이터 |
| Embedding 및 색인 | Embedding 모델 및 버전, 색인 실행, 처리 시간, 오류 |
| Dense Retrieval | 검색어, 검색 결과, 점수, 검색 시간 |
| BM25 및 Hybrid Retrieval | 검색 방식, 검색 결과, 결합 설정 및 결과 |
| Reranker | 재정렬 전후 후보, 점수, 처리 시간 |
| FastAPI | Request ID, Trace ID, 요청 상태, 응답 시간, 오류 |
| 답변 생성 및 출처 | 실제 모델 입력·출력, 사용 모델, 토큰, 생성 시간, 인용 정보 |
| 조건 확인 및 보류 | 최종 응답 상태, 추가 확인 또는 보류 사유 |

- 각 기능의 관측 기록은 실제 실행 결과를 기반으로 작성한다.
- 검색 결과와 최종 모델 입력 문맥을 구분하여 기록한다.
- 서비스 답변 생성과 평가 LLM 실행 기록을 구분한다.
- 문서 추출 및 색인 작업은 사용자 질문 처리 Trace와 구분한다.
- 민감정보와 API Key가 기록에 노출되지 않도록 한다.
- 상세 기록 항목은 `05_OBSERVABILITY_PLAN.md`와 `09_DATA_SCHEMA.md`를 따른다.

### 목적

PDF 원본에서 텍스트와 페이지 정보를 추출할 수 있는 기반을 만든다.

### 작업 항목

#### 1.1 PDF 데이터 확인 [필수]

- Basic 데이터셋 PDF 파일 목록 확인
- 파일명과 문서 식별자 연결
- PDF 페이지 수 확인
- 암호화, 손상, 읽기 제한 여부 확인
- 표와 이미지 등 추출에 영향을 주는 요소 확인

#### 1.2 PDF 추출 도구 선정 [필수]

PDF 추출 도구 후보를 검토하고 실제 문서에서 테스트한다.

선정 기준:

- 텍스트 추출 정확성
- 페이지 번호 보존
- 표 처리 능력
- 한글 처리
- 추출 속도
- 라이선스
- 구현 및 유지보수 난이도

특정 라이브러리를 사전 승인 없이 확정하지 않는다.

#### 1.3 문서 추출 구현 [필수]

- PDF 파일 읽기
- 페이지별 텍스트 추출
- 문서 ID 및 페이지 정보 부여
- 추출 결과 저장
- 추출 오류 기록

#### 1.4 추출 결과 검증 [필수]

대표 PDF를 선정하여 원본과 추출 결과를 비교한다.

확인 항목:

- 페이지 누락 여부
- 텍스트 누락 여부
- 한글 및 숫자 깨짐 여부
- 표 구조 훼손 여부
- 페이지 번호 연결 정확성

### 완료 조건

- Basic PDF 전체를 처리할 수 있다.
- 문서별 추출 결과와 페이지 정보가 보존된다.
- 추출 실패 문서 및 페이지를 확인할 수 있다.
- 대표 문서의 추출 결과를 원본과 대조했다.

## 6. STEP 2. 청킹 및 메타데이터 구성

### 목적

검색에 사용할 문서 청크를 생성하고 출처 및 문서 속성을 연결한다.

### 작업 항목

#### 2.1 초기 청킹 방식 선정 [필수]

- 청크 분할 방식 선정
- 청크 크기 설정
- Overlap 설정
- 페이지 경계 처리: **청크는 페이지 경계를 넘지 않고 단일 `page`를 가진다**(기본). 여러 페이지에 걸친 청크(`page_spans`)는 [확장]이다. 표가 페이지 경계에서 잘리는 문제는 STEP 1~2에서 실제 PDF를 확인해 보고하고 재논의한다.
- 문서 구조 보존 여부 결정 (표의 값은 행·열 제목, 단위, 각주를 함께 보존)

초기 청킹 방식과 설정은 **development 질문**의 검색 평가로만 조정한다. `additional`은 공식 비교용으로 보존한다. 공식 실행 전에 청킹 설정을 동결·기록하며, 동결 후 변경은 새 실험 ID로 관리한다.

#### 2.2 메타데이터 구성 [필수]

청크에 필요한 최소 메타데이터를 부여한다. 원문에서 확인할 수 없는 메타데이터는 임의로 만들지 않는다.

필수 필드:

- `book_id` (파일명에서 `.pdf`를 뺀 값)
- `file_name`
- `page`
- `chunk_id`
- `chunking_version`, `dataset_id`, `dataset_version`

## 11. STEP 7. FastAPI 기본 구조 및 Q&A API

### 목적

검색 및 답변 생성 기능을 외부에서 요청할 수 있는 API로 구성한다.

### 작업 항목

#### 7.1 FastAPI 기본 서버 [필수]

- 서버 시작 및 종료
- 라우터 구성
- 설정 및 환경변수 로딩
- 예외 처리 구조

#### 7.2 요청 및 응답 모델 [필수]

Pydantic을 사용하여 요청과 응답을 검증한다. 요청은 `{question, rag_method, question_id?}`, 응답은 `{request_id, status, answer, reason, citations}`이다(`09_DATA_SCHEMA.md`의 API 계약). 요청 ID는 서버가 생성한다.

#### 7.3 기본 Q&A API [필수]

`POST /rag/query`와 `GET /health`를 구성한다. 이 단계에서는 `rag_method = dense`만 연결하고(Naive RAG), `hybrid`와 `hybrid_rerank`는 STEP 5~6에서 같은 API에 추가한다. 미구현 방식은 지원하지 않는 값으로 422를 반환한다.

#### 7.4 오류 처리 [필수]

다음 상황을 구분한다(HTTP와 `reason` 값은 `09_DATA_SCHEMA.md`).

- 잘못된 요청 (빈 질문, 지원하지 않는 `rag_method`): 422, `invalid_request`
- 검색 실패: 500, `retrieval_error`
- 모델 호출 실패: 502, `model_error`
- Timeout: 504, `model_timeout`
- LLM 출력 검증 실패: 502, `output_validation_error`
- 내부 처리 오류: 500, `internal_error`

모든 오류 응답은 `status: "error"`와 `request_id`를 포함하는 일관된 형식을 유지한다.

#### 7.5 서버 안정성 테스트 [필수]

`04_ARCHITECTURE.md` §13의 필수 범위만 수행한다.

- 정상 질문, 빈 질문, 근거 부족, 모의 모델 오류 (TestClient 또는 모의 함수 사용)
- Timeout과 재시도 동작
- Langfuse 장애 시에도 답변과 결과 저장이 유지되는지 확인
- 평가 데이터가 검색·생성 입력에 유입되지 않는지 확인

서버 재시작·복구, 중복 요청·멱등성 키, 동시 요청, Liveness/Readiness 분리는 [확장]이다(`04_ARCHITECTURE.md` §13.7). timeout, 최대 호출 수, 재시도 횟수의 값은 이 단계에서 제안하고 공식 실행 전에 확정한다.

### 완료 조건

- FastAPI 서버가 실행된다.
- 질문을 API로 전달할 수 있다.
- 요청 및 응답이 검증된다.
- 오류가 구분된 형식으로 반환된다.
- 정상·빈 질문·모의 모델 오류 테스트를 실제로 실행해 결과를 확인했다.

## 12. STEP 8. GPT-6 Luna 답변 생성 및 출처 연결

### 목적

검색된 문맥을 이용해 답변을 생성하고 근거 출처를 함께 반환한다.

### 작업 항목

#### 8.1 GPT-6 Luna 연결 [필수]

OpenAI API를 통해 생성 모델(`gpt-6-luna`)을 연결한다. API 키는 환경변수로 관리한다. 지원 파라미터(temperature, 최대 출력 토큰 등)는 STEP 0에서 확인한 값을 사용하며 세 방식에 동일하게 적용한다.

#### 8.2 최종 문맥 구성 [필수]

검색된 청크 중 최종적으로 사용할 문맥을 구성한다.

- 문서 내용
- 청크마다 이번 요청에서 사용할 출처 ID(`S1`, `S2`…) 부여
- 출처 ID와 `book_id`, `file_name`, `page`의 대응표를 코드에서 보관
- 문맥 토큰 한도 적용 (줄여도 대상, 조건, 단위, 정정 내용, 출처는 남긴다)

최종 문맥(모델에 실제 전달한 것)과 1차 검색 결과를 구분하여 기록한다.

#### 8.3 답변 프롬프트 구성 [필수]

- 서비스 지시, 질문, 검색 자료를 프롬프트에서 구분
- 제공된 문맥을 근거로 답변, 근거가 없는 사실 생성 방지
- 회사·기간·단위·정정 범위 등 조건 구분 (날짜가 늦거나 검색 순위가 높다는 이유만으로 선택하지 않음)
- 출력: `status`, `answer`, `reason`, `source_ids`를 가진 JSON 하나. 상태는 `answered` / `needs_clarification` / `abstained`
- 근거 부족 시 보류, 조건이 빠졌으면 되묻기

#### 8.4 답변 및 출처 반환 [필수]

LLM 출력은 코드에서 검증한다(상태 값, 필수 필드, `source_ids`가 이번 요청의 최종 문맥에 있는 ID인지). 컨텍스트에 없는 ID나 형식 오류는 정상 답변으로 통과시키지 않고 출력 오류로 처리하거나 정한 횟수 안에서 다시 생성한다.

검증된 `source_ids`를 코드가 보관한 대응표로 변환해 다음 정보를 반환한다. 문서명과 페이지를 LLM이 만들지 않는다.

- 답변 내용과 사유(`answer`, `reason`)
- 출처(`source_id`, `book_id`, `file_name`, `page`)
- 답변 상태(`status`)

#### 8.5 답변 검증 [필수]

- 답변과 출처의 일치 여부
- 숫자 및 단위 정확성
- 회사 및 기간 정확성
- 출처 페이지의 실제 근거 여부

### 완료 조건

- GPT-6 Luna가 검색 문맥을 바탕으로 답변한다.
- 답변과 출처가 연결된다.
- 근거가 없는 내용을 임의로 만들어내지 않도록 지시한다.
- 답변 생성에 실패하면 오류 상태가 구분된다.

## 13. STEP 9. 질문 조건 확인 및 보류 처리

### 목적

질문에 필수 정보가 부족하거나 근거가 불충분한 경우 적절하게 되묻거나 답변을 보류한다.

이 단계는 **별도의 판단 규칙 코드나 충돌 탐지 시스템을 만드는 단계가 아니다.** 상태 판단은 STEP 8의 프롬프트와 출력 스키마(`status`)에서 LLM이 검색 문맥을 읽고 하며, 이 단계는 그 동작을 예외 질문으로 확인하고 프롬프트를 조정(development 질문에서만)하는 단계이다. `error`는 LLM이 아니라 API 코드가 판정한다.

### 작업 항목

#### 9.1 질문 조건 확인 [필수]

프롬프트가 질문에서 필요한 조건을 확인하도록 한다.

예시:

- 회사
- 기간
- 사업부문
- 제품
- 지역
- 수치의 단위
- 정정본 적용 여부

질문에 필요한 조건이 빠져 있다면 추가 확인을 요청한다.

#### 9.2 답변 가능 여부 판단 [필수]

LLM이 반환하는 다음 상태를 구분한다. (`error`는 API 코드가 판정)

- `answered`
- `needs_clarification`
- `abstained`

#### 9.3 부분 답변 및 보류 [필수]

일부 내용은 답변할 수 있지만 일부는 근거가 부족한 경우 가능한 부분만 답하고 확인되지 않은 부분은 이유와 함께 구분하여 보류한다(필수 기본 동작). 상태 이름보다 답한 범위와 보류 이유가 기대 행동에 맞는지가 중요하다.

#### 9.4 예외 질문 테스트 [필수]

- 필수 조건이 누락된 질문
- 서로 다른 회사가 혼합된 질문
- 기간이 불명확한 질문
- 정정본과 이전 자료가 충돌하는 질문
- 검색 근거가 없는 질문
- 일부 근거만 확인되는 질문

### 완료 조건

- 조건이 부족한 질문에 추가 확인을 요청한다.
- 근거가 부족한 경우 보류한다.
- 답변 가능한 부분은 구분하여 제공한다.
- API 상태와 실제 답변 내용이 일치한다.

- Request ID와 Trace ID의 연결 확인
- 검색 결과와 최종 문맥의 구분 확인
- 실제 모델 입력·출력 기록 확인
- 모델 사용량 및 실행 시간 기록 확인
- 오류 발생 시 오류 유형과 발생 단계 확인
- 평가 LLM 실행과 서비스 답변 생성 기록의 구분 확인
- 대표 요청 하나를 선택하여 질문부터 최종 응답까지 Langfuse에서 추적
- Langfuse 기록 누락 및 식별자 연결 오류 확인

**[확장]**
- Langfuse 대시보드 및 사용자 정의 시각화
- 실험별 상세 비교 화면
- 팀 공유용 관측 대시보드

**완료 조건**
- 대표 사용자 요청의 전체 처리 흐름을 하나의 Trace에서 확인할 수 있다.
- 각 단계의 입력·출력과 실행 시간을 확인할 수 있다.
- 모델 사용량과 오류 정보를 확인할 수 있다.
- 평가 실행이 서비스 답변 생성 기록과 혼동되지 않는다.
- `05_OBSERVABILITY_PLAN.md`의 필수 관측 요구사항을 충족한다.

## 16. STEP 12. 공식 RAG 비교 실험

### 목적

동일한 조건에서 세 가지 RAG 방식을 비교한다.

### 작업 항목

#### 12.1 공통 설정 확정 [필수]

- 동일 PDF
- 동일 추출 결과
- 동일 청킹
- 동일 Embedding
- 동일 생성 모델
- 동일 답변 프롬프트
- 동일 생성 설정
- 동일 평가 기준
- 동일 최종 k
- 동일 최종 문맥 토큰 한도
- 동일 timeout, 최대 호출 수, 재시도 횟수

**튜닝과 동결 규칙**: 청킹·프롬프트 등의 조정은 development 질문에서만 한다. 공식 실행 전에 위 공통 설정을 동결하고 실행 설정 스냅샷(`manifest.json`)에 기록한다. 동결 후 설정을 바꾸면 새 실험 ID로 관리하고 기존 결과는 덮어쓰지 않는다. 공식 실행(`track = official`)은 Git 작업 트리가 clean인 상태에서 시작한다.

#### 12.2 세 가지 방식 실행 [필수]

- Naive RAG (Dense)
- Hybrid Retrieval
- Hybrid + Reranking

#### 12.3 동일 질문 실행 [필수]

동결 후 development + additional 60문항을 세 가지 방식 모두 실행한다(답변 180개). 비답변 문항 8개를 모두 포함하며 `/rag/query` API를 통해 실행한다.

질문 ID(`question_id`)를 기준으로 결과를 연결하고, 결과표는 `evaluation_set_type`(development / additional)별로 분리해 보고한다. additional이 주결과이다.

#### 12.4 결과 비교 [필수]

- 검색 평가
- 답변 평가
- 응답시간
- 오류율
- Token Usage
- 확인 가능한 비용

#### 12.5 결과 검토 [필수]

- 세 방식 평균 비교
- 질문별 결과 비교
- 개선 사례 확인
- 악화 사례 확인
- 실패 사례 확인
- 대표 결과 원문 대조
- 중대 오류 분류: Judge 0점 답변을 사람이 검토해 중대 오류 여부를 표시하고 방식별 건수를 보고. 가장 적은 방식보다 2건 이상 많은 방식은 선택 후보에서 제외하며, 모두 중대 오류가 있으면 가장 적은 방식을 선택하되 "실제 서비스 사용 불가"로 명시(`12_ACCEPTANCE_CRITERIA.md` §4.3)
- 최종 선택은 `12_ACCEPTANCE_CRITERIA.md`의 사전 확정 규칙을 따른다

### 완료 조건

- 세 가지 RAG 방식이 동일 조건에서 실행된다.
- 평가 질문별 결과가 연결된다.
- 공식 평가 결과를 비교할 수 있다.
- 실패 사례를 포함한 결과가 보존된다.
- 최종 선택 근거를 설명할 수 있다.

## 17. STEP 13. 보안 비교 실험

### 목적

검색 문서에 포함된 악성 지시 또는 프롬프트 인젝션에 대해 기본 프롬프트와 방어 프롬프트의 차이를 비교한다.

### 작업 항목

#### 13.1 보안 질문 및 과제 확인 [필수]

보안 질문은 `security_questions.json`의 2개(FPAIR01, FPAIR02)로 고정하고, 사례와 정답은 `security_tasks.json`에서 평가 단계에만 사용한다. 공격 노출 판정 규칙(저장된 최종 문맥에 `attack_text` 핵심 문장이 포함되는지)은 실행 전에 고정한다(`02_EVALUATION_PLAN.md` §9).

#### 13.2 RAG 구성 선택 [필수]

STEP 12의 결과로 선택된 최종 RAG 구성 하나를 사용한다. 보안 실행은 `run_type = security`로 기록하며 일반 평가의 운영 지표와 분리한다.

보안 비교를 세 가지 방식 모두에 반복할 필요는 없다.

#### 13.3 검색 및 최종 문맥 고정 [필수]

각 보안 질문에 대해 한 번 검색하고 최종 문맥을 저장한다.

기본 프롬프트와 방어 프롬프트 실행 사이에 재검색하지 않는다.

#### 13.4 기본 및 방어 프롬프트 실행 [필수]

- 기본 프롬프트 실행
- 방어 지시 추가 후 실행

업무 질문 2개를 기본/방어 프롬프트로 각각 실행하여 총 4개 답변을 비교한다.

#### 13.5 보안 결과 분석 [필수]

- 공격 문장이 모델 입력에 포함되었는가?
- 모델이 공격 지시를 따랐는가?
- 업무 질문에 대한 답변이 정확한가?
- 불필요하게 거절했는가?
- 방어 지시가 어떤 영향을 주었는가?

공격 성공 여부와 업무 답변 품질을 구분한다.

### 완료 조건

- 동일 문맥에서 기본 및 방어 프롬프트가 실행된다.
- 총 4개 답변과 실행 기록이 저장된다.
- 공격 입력 여부와 공격 성공 여부를 구분해 분석한다.
- 결과를 기존 비교표에 포함한다.

## 18. STEP 14. 운영 지표 및 결과 정리

### 목적

서비스의 응답시간, 오류율, Token Usage 및 비용을 측정한다.

### 작업 항목

#### 14.1 응답시간 [필수]

API 요청 수신부터 최종 응답 반환까지의 시간을 기록한다.

검색, Reranking, 생성, 재시도 시간을 포함한다.

#### 14.2 오류율 [필수]

재시도 후에도 시스템 오류로 종료된 일반 평가 요청을 기준으로 계산한다.

추가 확인 및 보류는 시스템 오류로 취급하지 않는다.

#### 14.3 Token Usage [필수]

요청별 Input/Output Token을 기록하고 RAG 방식별로 합산한다.

확인되지 않은 값을 0으로 기록하지 않는다.

#### 14.4 비용 [필수]

확인 가능한 단가가 있을 때 비용을 계산한다.

단가 확인이 어려우면 Token Usage를 기록하고 비용은 확인 불가로 표시한다.

#### 14.5 운영 지표 비교 [필수]

세 가지 RAG 방식의 운영 지표를 비교한다.

평가 모델의 사용량 및 시간은 서비스 답변 생성과 분리한다.

#### 14.6 추가 운영 실험 [확장]

- 동시 요청
- Batch 처리
- Async I/O
- 캐시
- P50/P95/P99
- Throughput
- Queue Wait Time

추가 지표의 세부 내용은 `10_ADDITIONAL_METRICS.md`를 참고한다.

### 완료 조건

- 요청별 응답시간을 기록한다.
- 공식 기준에 맞게 오류율을 계산한다.
- Token Usage와 확인 가능한 비용을 비교한다.
- 평가 실행과 서비스 실행 사용량을 구분한다.

## 21. 작업 단위 및 실행 규칙

### 21.1 작업 시작 전 보고 [필수]

Claude Code는 각 작업을 시작하기 전에 다음 내용을 보고한다.

1. 작업 ID와 작업명
2. 작업 목적
3. 관련 설계 문서
4. 수정 허용 파일
5. 수정 금지 파일
6. 필요한 입력 및 선행 작업

9. 실행할 테스트
10. 설계 변경 가능성 및 위험 요소

사용자가 요청한 범위가 명확하면 불필요한 확인 질문을 반복하지 않는다.

단, 설계 변경이나 중요한 선택이 필요한 경우 사용자 승인을 기다린다.

### 21.2 작업 중 규칙 [필수]

- 승인된 작업 범위만 수정한다.
- 기존 코드를 충분히 확인한 후 수정한다.
- 사용하지 않는 기능을 임의로 추가하지 않는다.
- 오류 해결을 이유로 기술 스택을 임의 변경하지 않는다.
- 기존 데이터 및 결과를 임의 삭제하지 않는다.
- 작업과 무관한 대규모 리팩터링을 하지 않는다.
- 테스트에 필요한 추가 작업이 범위를 벗어나면 먼저 보고한다.

### 21.3 작업 완료 후 보고 [필수]

작업이 완료되면 다음 내용을 보고한다.

1. 구현 내용
2. 구현 이유
3. 변경 파일 목록
4. 관련 설계 요구사항
5. 실행한 테스트
6. 테스트 결과
7. 실행하지 못한 테스트 및 이유
8. 남은 문제 및 위험 요소
9. 설계 변경 상태
10. Git commit 여부
11. 다음 단계 진행 가능 여부

### 21.4 완료 확인표 [필수]

모든 작업은 다음 항목을 확인한다.

- [ ] 승인된 작업 범위 안에서 구현했는가?
- [ ] 설계 요구사항을 충족했는가?
- [ ] 테스트를 실행했는가?
- [ ] 테스트 결과를 확인했는가?
- [ ] 기존 기능에 영향이 없는가?
- [ ] 설계 변경이 발생했는가?
- [ ] 변경이 발생했다면 사용자 승인을 받았는가?
- [ ] 미해결 문제가 기록되었는가?
- [ ] 다음 작업을 진행할 수 있는가?

테스트하지 않은 항목은 통과로 표시하지 않는다.

## 22. 설계 변경 승인 절차

### 22.1 승인 없이 변경할 수 없는 사항 [필수]

- 기술 스택
- 핵심 라이브러리
- 데이터 구조
- API 요청 및 응답 구조
- 공식 평가 기준
- 공식 비교 조건
- 필수 기능 범위
- 모델 및 검색 구성의 주요 변경
- 프로젝트 디렉터리의 핵심 구조
- 저장 방식 및 데이터 보존 정책

### 22.2 변경 요청 보고 형식 [필수]

설계 변경이 필요하면 다음 형식으로 보고한다.

**1. 문제 상황**
- 어떤 문제가 발생했는가?

**2. 기존 설계**
- 현재 승인된 설계는 무엇인가?

**3. 변경 필요 이유**
- 기존 설계로 해결하기 어려운 이유는 무엇인가?

**4. 대안**
- 기존 설계를 유지하는 방법
- 설계를 변경하는 방법

**5. 영향**
- 코드
- 데이터
- API
- 평가 결과
- 실행 환경
- 기존 기능

**6. 추천안**
- 어떤 방법을 추천하는가?
- 추천 이유는 무엇인가?

**7. 승인 요청**
- 사용자의 결정이 필요한 사항은 무엇인가?

승인 전에는 기존 설계를 유지한다.

### 22.3 승인 기록 [필수]

승인된 변경은 `DECISIONS.md`에 기록한다.

기록 항목:

- 결정 ID
- 결정 날짜
- 변경 대상
- 변경 전 내용
- 변경 후 내용
- 변경 사유
- 영향 범위
- 승인 여부

## 23. 프로젝트 진행 관리

### 23.1 TASKS.md [필수]

작업 목록과 진행 상태를 관리한다.

상태 예시:

- TODO
- IN_PROGRESS
- BLOCKED
- REVIEW
- DONE

각 작업에 작업 ID와 관련 STEP을 연결한다.

### 23.2 CHANGELOG.md (별도 파일을 만들지 않음)

실제 구현 변경 이력은 Git 커밋 이력으로 대신한다(불필요한 파일 방지). 커밋 메시지에서 설계 변경 여부와 코드 변경 여부를 구분할 수 있게 쓴다.

### 23.3 DECISIONS.md [필수]

사용자가 승인한 설계 변경과 주요 기술 선택을 기록한다. 기록 항목은 §22.3을 따르며, 모델·기술 선택은 선택 이유와 실제 확인된 버전·라이선스를 함께 적는다(확인하지 않은 버전은 적지 않는다).

### 23.4 Git commit [필수]

작업 단위로 변경 이력을 보존한다.

큰 작업을 하나의 Commit에 몰아서 기록하지 않는다.
