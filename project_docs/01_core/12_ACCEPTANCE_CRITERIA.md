# 12. ACCEPTANCE_CRITERIA.md
# 최종 선택 규칙 (사전 확정)

## 1. 목적과 범위

세 가지 RAG 방식(Dense / Hybrid / Hybrid + Reranking) 중 **하나를 최종 구성으로 선택하는 규칙을 공식 비교 실행 전에 확정**한다. 과제 원본(STEP 2)은 선택 기준을 "답변 품질, 시간, 토큰과 오류"로 하고, 실행할 질문과 평가 기준을 비교 전에 정하라고 요구한다.

- 이 문서는 **합격/불합격 문턱(게이트)이 아니다.** 과제 원본은 점수 합격선을 두지 않으며, 지표가 나빠졌을 때는 이유와 한계를 설명하면 된다고 한다.
- **어떤 방식도 목표 수준에 못 미쳐도 반드시 하나를 선택**하고 그 이유와 한계를 기록한다.
- 실제 서비스 단계의 합격 기준(합격선, p95, 오류율 1%, 동등성 검정, Holdout 0건 등)은 `10_ADDITIONAL_METRICS.md` §11의 [확장] 서비스 준비도 게이트로 분리했다.

## 2. 비교 입력

- 대상: `dense`, `hybrid`, `hybrid_rerank`
- 질문: 설정 동결 후 development 30 + additional 30 = 60문항을 세 방식에 동일하게 실행(답변 180개). 비답변(clarify 4, abstain 4) 8개 포함. 질문 범위는 `02_EVALUATION_PLAN.md` §4.1을 따른다.
- 결과는 `evaluation_set_type`별로 분리 보고한다. **additional을 주결과**로, development는 튜닝에 사용한 문항이므로 참고 결과로 본다.
- 비교 조건(PDF, 추출, 청킹, 임베딩, 생성 모델, 프롬프트, 생성 설정, 최종 k, 문맥 토큰 한도, 평가 모델·프롬프트, timeout·재시도)은 모두 동일하게 유지하며, 방식 고유 설정(후보 수, 결합, 리랭킹)은 기록한다.
- 단일 점수로 합산하지 않는다. 검색 지표, RAGAS Faithfulness, Judge 네 항목은 각각 보고한다.

## 3. 비교 지표

**품질** (정의는 `02_EVALUATION_PLAN.md`)
- 검색: Hit@k, Recall@k
- 답변: RAGAS Faithfulness, Judge 사실·조건·근거·판단의 충족률(1의 비율)
- 기대 행동(`expected_action`)과 응답 상태의 일치 여부
- 중대 오류 건수(§5) — 선택에는 §4.3 2의 규칙으로만 반영

**운영** (일반 평가 `run_type = general_eval` 요청만, 평가 호출·보안·모의 오류 제외)
- 정상 처리된 요청의 평균 응답시간과 건수
- 오류율(재시도 후에도 시스템 오류로 끝난 요청 수 / 전체 일반 평가 요청 수)과 실패 건수
- 입력·출력 토큰 합계와 사용량을 확인한 요청 수
- 모델 호출 비용(단가를 확인할 수 있을 때만)

해당 없음(`not_applicable`)과 평가 불가(`not_evaluated`)는 평균에서 제외하고 0점은 포함하며, 평균 옆에 평가 대상 수·해당 없음·평가 불가·오류 건수를 적는다. 사용량을 확인하지 못한 값은 0이 아니라 확인 불가로 적는다.

## 4. 비교 방법과 선택 순서

### 4.1 비교 방법

- 같은 질문의 방식별 결과를 짝지어 질문별 차이를 본다. 방식 쌍(Dense↔Hybrid, Hybrid↔Hybrid+Rerank, Dense↔Hybrid+Rerank)마다 평균 차이와 **좋아진·나빠진·같은 문항 수**를 표로 낸다.
- 평균 차이의 95% 신뢰구간(부트스트랩 등)은 **참고용으로 함께 보고**하되 선택의 문턱으로 쓰지 않는다. 60문항으로는 구간이 넓으므로 한 지표의 작은 차이를 근거로 방식이 항상 우월하다고 결론 내리지 않는다.
- 전체 평균뿐 아니라 `evaluation_set_type`별, `expected_action`별로 따로 본다. 평균이 좋아도 중요한 질문이 나빠졌다면 원문과 대조해 이유를 설명한다.
- 개선·악화 대표 사례와 실패 사례는 PDF 원문과 대조한다.

### 4.2 "품질이 비슷하다"의 정의

주요 품질 지표(Hit@k, Recall@k, Faithfulness, Judge 4항목)의 **평균 차이가 모두 ±0.05 이내**이면 품질이 비슷한 것으로 본다. 이는 설명을 위한 기준이며 통계적 동등성 검정이 아니다.

근거: 주결과인 additional은 30문항이라 0/1 지표는 한 문제 차이가 0.033이다. ±0.05는 한 문제 차이의 우연은 걸러내고 두 문제 이상의 차이(0.067~)는 차이로 인정하는 값이다. 30문항의 평균 차이 95% 신뢰구간은 대략 ±0.1 수준이므로 이 기준보다 작은 차이는 우연과 구분되지 않을 수 있으며, 신뢰구간을 함께 보고해 이 한계를 드러낸다.

### 4.3 선택 순서 (실행 전 고정)

1. **품질 비교**: additional을 주결과로 비교한다. 한 방식이 다른 방식보다 핵심 품질 지표에서 ±0.05를 넘어 높으면 그 방식이 품질에서 우세하다. 핵심 지표는 우선순위 순으로 ① Judge 사실·조건·판단 ② Faithfulness·Judge 근거 ③ Hit@k·Recall@k이다. 지표가 엇갈리면 높은 우선순위의 지표를 따르고 이유를 설명한다. 한 지표의 하락은 다른 지표의 상승으로 상쇄하지 않는다.
   - 우선순위의 근거: ①은 사용자가 받는 답의 정확성을 직접 재는 지표이다. ②는 답이 문맥·출처에 근거하는지 보지만, 정정 전 값을 충실히 따라도 높게 나올 수 있다(과제 안내). ③은 중간 단계 지표이며, 문서를 찾아도 문맥이 잘리거나 잘못 읽으면 답이 틀리고 한 문서만으로 충분히 답할 수도 있다.
2. **중대 오류(§5)**:
   - 중대 오류 건수가 가장 적은 방식보다 **2건 이상 많은 방식은 점수가 높아도 선택 후보에서 제외**한다. 1건 차이는 사람 판정의 오차일 수 있으므로 불리하게만 반영한다(품질이 비슷할 때 우선 고려).
   - 모든 방식에서 중대 오류가 발견되면, 가장 적은 방식을 선택하되 결과 문서에 **"실제 서비스 사용 불가"** 로 명시한다. 과제의 "반드시 하나 선택" 요구를 지키면서 서비스 사용 가능 여부를 분리하는 규칙이다.
   - 중대 오류 0건을 요구하는 "서비스 사용 가능" 판정은 서비스 준비도 게이트(`10_ADDITIONAL_METRICS.md` §11.6)에서 한다.
   - 중대 오류는 평균 점수로 상쇄하지 않는다.
3. **품질이 비슷하면**: 응답시간, 토큰 사용량, 오류율, 구현 복잡도를 함께 보고 고른다. 추가 단계가 필요 없는 단순한 구성(Dense < Hybrid < Hybrid + Reranking 순)을 우선하되, 실제 측정에서 더 복잡한 구성이 시간·사용량에서 유리하면 그 근거를 함께 적는다.
4. **품질이 뚜렷이 다르면**: 비용·속도가 유리하다는 이유만으로 낮은 품질의 방식을 선택하지 않는다.
5. **항상 하나를 선택한다.** 모든 방식의 점수가 낮아도 가장 적절한 구성을 선택하고, 선택 이유와 남은 한계(점수가 낮은 영역, 표본 크기, 자기 평가 편향 가능성, 공개 데이터 사용)를 기록한다. 결과를 보고 이 규칙을 바꾸지 않는다.

±0.05(비슷함 기준), 지표 우선순위, 중대 오류 제외 기준(2건)은 사용자 승인으로 확정한 값이며, 공식 실행 후에는 바꾸지 않는다(§7).

## 5. 중대 오류 (분류, 선택 규칙에 제한적으로 반영)

평균 점수에 묻히는 위험한 오답에 별도 표시를 단다. 선택 순서(§4.3 2)에서 건수 차이가 크면 후보에서 제외되지만, 합격/불합격 판정은 아니다. 다음에 해당하면 중대 오류로 분류한다.

- 금액, 비율, 날짜, 기간, 단위 등 핵심 수치를 잘못 답한 경우(정정 전 값을 답한 경우 포함)
- 문서에 없는 사실이나 근거를 만들어 낸 경우, 평가 데이터의 `forbidden_claims`를 단정한 경우
- 기업, 제품, 사업부문, 실적 정보를 서로 혼동한 경우
- 근거가 부족하거나 충돌하는데 확정적으로 답한 경우, 보류·되묻기가 필요한데 하지 못한 경우
- 질문의 핵심 조건을 위반해 잘못된 판단을 제시한 경우

절차:
- **검토 방식 (사용자 승인 2026-11-10, DECISIONS D-045)**: Judge(3회 다수결)가 0점을 준 항목이 하나라도 있는 모든 답변을 **AI가 전수 사전 분류**한다(위 다섯 기준 해당 여부, 원문 근거, 원인). **사람이 원문과 대조**하는 대상은 ① AI가 기준 중 하나라도 해당할 가능성을 본 답변(조금이라도 비슷하면 후보. **방식별 후보가 10건 이하면 전부, 넘으면 방식마다 같은 10건을 seed 고정 무작위로 뽑아 확인하며**, 이 경우 표본 확인이고 전수가 아님을 보고하고 후보 전체 수와 확인한 수를 함께 적는다. 사용자 승인 2026-11-10)와 ② "중대 아님"으로 분류한 답변 중 방식별 무작위 표본(제안: 방식별 max(5건, 20%), seed 고정)이다. 표본에서 AI가 "중대 아님"으로 분류했는데 사람이 중대로 판정한 건이 하나라도 나오면 그 방식의 나머지 "중대 아님" 분류를 전부 사람이 확인한다. 결과는 `evaluations.jsonl`의 `critical_error`에 유형·사유·원문 근거와 함께 `reviewed_by`(human/ai)를 기록한다.
- 방식별 건수는 **사람이 확인한 중대 오류와 AI만 분류한 중대 오류를 나누어** 보고하고, 선택 규칙(§4.3 2)의 건수 차이는 **사람이 확인한 중대 오류 건수**로 적용한다. AI 사전 분류는 평가 모델과 같은 모델이라 자기 평가 편향 가능성이 있고 표본 검토는 전수 확인이 아니라는 한계를 함께 기록한다.
- 방식별·세트별 건수를 표로 보고하고, 각 사례의 원인(검색 실패, 문맥 절단, 생성 오류 등)을 분석한다.
- 이 분류는 "건수가 많은 방식을 후보에서 제외"하는 데만 쓰이며 별도의 합격/불합격 점수 기준은 없다. 건수가 0이어도 실제 서비스에서 오류가 없다는 뜻이 아니다.
- 판정이 선택에 영향을 주므로 중대 오류로 표시한 모든 사례는 원문 근거와 판정 이유를 함께 남긴다.

## 6. 평가 신뢰성

- LLM Judge와 RAGAS의 평가 모델, 프롬프트, 출력 형식, 설정을 고정하고 세 방식에 동일하게 적용한다. 평가 모델이 생성 모델과 같으므로(GPT-6 Luna) 자기 평가 편향 가능성을 한계로 기록한다.
- 대표 사례(좋아진·나빠진 사례, 중대 오류 후보)는 사람이 원문과 정답을 대조해 확인한다. 자동 채점 오류를 발견하면 원래 점수와 수정 이유를 함께 남기며(`human_review`), 사람이 확인한 결과만으로 두 자동 평가를 대신하지 않는다.
- 질문별 점수와 오류 유형을 보존하고 평균만으로 판단하지 않는다. 실패한 실행도 결과에 포함하며 좋은 결과만 골라 쓰지 않는다.
- 평가 질문·정답·근거·`expected_action`은 검색·색인·생성 입력에 넣지 않는다.
- 제공 질문과 정답은 공개되어 있으므로 결과를 비공개 테스트 성능으로 표현하지 않는다.
- 평가 데이터나 절차의 결함으로 유효한 평가가 불가능하면 결과를 유효한 공식 결과로 취급하지 않고 원인을 수정해 다시 실행한다(새 실험 ID).

## 7. 기준 확정과 변경 관리

- 공식 실험 전에 이 문서의 비교 지표, "비슷하다"의 정의, 선택 순서를 확정하고, 확정 시점을 `DECISIONS.md`에 기록한다.
- 결과를 본 뒤 특정 방식에 유리하도록 기준을 조정하지 않는다.
- 기준을 바꿔야 하면 기존 결과와 구분되는 새 실험으로 관리하고 변경 사유·시점·영향받는 실험·재실험 여부를 기록한다.
- 측정하지 않은 항목은 추정값으로 채우지 않고 미측정으로 표시한다.

## 8. 결과 보고

- 방식별 품질 지표(검색, Faithfulness, Judge 네 항목)와 질문별 점수, 세트별·기대 행동별 분리 결과
- 방식 쌍별 평균 차이, 좋아진·나빠진·같은 문항 수, 신뢰구간(참고)
- 중대 오류 유형과 방식별 건수, 원인 분석
- 응답시간(평균·정상 건수), 오류율(실패 건수), 토큰 합계(확인 요청 수), 확인 가능한 비용
- 대표 사례의 원문 대조 결과
- 보안 비교 4개 답변과 결과(일반 평가 지표와 분리)
- 최종 선택 방식, 선택 근거(§4.3의 어느 단계에서 결정되었는지), 남은 한계, 미측정·평가 불가 항목
