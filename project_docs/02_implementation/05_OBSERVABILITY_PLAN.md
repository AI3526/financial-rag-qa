# 05. OBSERVABILITY_PLAN.md

## 1. 문서 목적

본 문서는 Financial Document Intelligence 프로젝트의 실행 과정을 관측하고 기록하기 위한 기준을 정의한다.

Langfuse를 중심으로 사용자 질문부터 검색, 문맥 구성, GPT-6 Luna 답변 생성 및 최종 응답까지의 과정을 연결하여 추적할 수 있도록 한다.

단순히 모델 호출 기록을 남기는 것이 아니라, 특정 질문의 실행 결과를 선택했을 때 다음 내용을 확인할 수 있어야 한다.

- 어떤 질문이 실행되었는가?
- 어떤 데이터셋과 RAG 방식으로 실행되었는가?
- 어떤 문서와 청크가 검색되었는가?
- 실제 모델에 전달된 문맥은 무엇인가?
- 모델에 전달한 입력과 모델이 반환한 출력은 무엇인가?
- 최종 답변과 인용 정보는 무엇인가?
- 각 단계에 소요된 시간은 얼마인가?
- 모델 사용량과 토큰은 얼마인가?
- 오류 또는 재시도가 발생했는가?

### 1.1 설계 원칙

1. 하나의 사용자 요청을 하나의 Trace로 추적한다.
2. 하나의 Trace 안에서 주요 처리 단계를 Observation으로 연결한다.
3. 요청 ID를 기준으로 API 실행 결과, 평가 결과 및 Langfuse 기록을 연결한다.
4. 검색 결과와 실제 모델에 전달한 최종 문맥을 구분한다.
5. 서비스 답변 생성과 평가용 LLM 호출을 구분한다.
6. 공식 평가 실행과 개인 확장 실험을 구분한다.
7. 실제 확인되지 않은 토큰 사용량이나 비용을 임의로 기록하지 않는다.
8. API Key 및 불필요한 개인정보가 관측 기록에 저장되지 않도록 한다.
9. 기존 실행 기록을 덮어쓰지 않고 실행별로 보존한다.

## 2. 관측 시스템 구성

### 2.1 기본 구성

| 구성요소 | 역할 | 구분 |
|---|---|---|
| Langfuse (Cloud) | Trace 및 Observation 기록과 조회 | [필수] |
| LangChain | RAG 및 LLM 실행 과정의 연결 | [필수] |
| FastAPI | 요청 ID 및 실행 흐름 관리 | [필수] |
| GPT-6 Luna | 답변 생성 | [필수] |
| 벡터 저장소 | 검색 결과 및 검색 과정 기록에 필요한 데이터 제공 | [필수] |
| Evaluation Module | 평가 결과 생성 및 연결 | [필수] |
| Result Storage (JSON/JSONL) | 실행 및 평가 결과 보존. 비교표의 기준 데이터 | [필수] |
| Dashboard UI | 실험 결과 공유 화면 | [확장] |

### 2.2 Langfuse의 역할

Langfuse는 프로젝트의 실행 과정을 관측하는 시스템이다.

주요 활용 목적:

- 요청별 실행 과정 추적
- 검색 및 생성 단계별 입출력 확인
- 모델 호출 시간과 토큰 사용량 확인
- 오류 및 재시도 기록
- 실험별 실행 결과 비교
- 대표 질문의 전체 처리 과정 시연

Langfuse는 Langfuse Cloud를 사용한다(Docker 불필요). 계정과 API 키(Public/Secret)는 STEP 0에서 직접 발급해 `.env`에 입력하며, SDK 버전은 구현 시작 시 공식 문서로 확인한다.

Langfuse는 질문별 추적과 시연용이다. 모든 데이터를 영구적으로 관리하거나 비교표의 기준 데이터로 쓰지 않는다. 비교표의 기준 데이터는 결과 JSON이며(§11), 평가 결과와 실험 결과의 저장 구조는 `09_DATA_SCHEMA.md`에서 정의한다.

## 3. Trace 및 Observation 설계

### 3.1 Trace 기본 원칙

하나의 사용자 질문 실행을 하나의 Trace로 관리한다.

예를 들어 사용자가 다음 질문을 입력했다고 가정한다.

> 해온솔루션의 상반기 매출과 영업이익이 모두 증가했는가?

이 요청에 대해 검색, 문맥 구성, 답변 생성 및 응답 반환 과정이 하나의 Trace에 연결되어야 한다.

하나의 질문을 세 가지 RAG 방식으로 각각 실행했다면 실행별로 별도의 Trace를 생성한다.

따라서 동일한 평가 질문 ID를 가진 Trace가 여러 개 존재할 수 있다.

### 3.2 Observation 구성

Trace 안에서 주요 처리 단계를 Observation으로 관리한다.

기본 구조:

```text
Trace: rag-query
 |
 +-- request-validation
 |
 +-- retrieval
 |    |
 |    +-- dense-retrieval
 |    |
 |    +-- sparse-retrieval
 |    |
 |    +-- reranking
 |
 +-- context-construction
 |
 +-- answer-generation
 |
 +-- citation-and-status
 |
 +-- response
```

위 구조는 논리적인 예시다.

실제 구현에서는 선택한 RAG 방식에 따라 필요한 Observation만 생성한다.

예를 들어 Naive RAG에서는 Sparse Retrieval과 Reranking Observation이 발생하지 않는다.

### 3.3 Observation 유형

Langfuse Observation 유형은 실제 작업의 성격에 맞게 사용한다.

| 작업 | 권장 유형 | 설명 |
|---|---|---|
| 전체 요청 | Trace | 사용자 요청 전체 |
| 일반적인 처리 단계 | Span | 검증, 검색, 문맥 구성 등 |
| GPT 답변 생성 | Generation | LLM 호출 및 생성 결과 |
| 평가 모델 호출 | Generation | 평가용 LLM 호출 |
| 검색 작업 | Span 또는 적절한 검색 Observation | 검색 결과와 실행 정보 기록 |

Langfuse SDK의 Observation API와 사용 중인 버전에 맞춰 실제 구현 시 유형을 확정한다.

### 3.4 Observation 이름 규칙

Observation 이름은 역할을 명확하게 알 수 있도록 일관되게 지정한다.

예시:

| 이름 | 역할 |
|---|---|
| `rag-query` | 전체 요청 |
| `request-validation` | 요청 검증 |
| `retrieval` | 검색 전체 |
| `dense-retrieval` | Dense 검색 |
| `sparse-retrieval` | Sparse 검색 |
| `reranking` | 검색 후보 재정렬 |
| `context-construction` | 최종 문맥 구성 |
| `answer-generation` | 답변 생성 |
| `citation-and-status` | 출력 검증, 출처 변환, 상태 처리 |
| `response` | 최종 응답 |
| `evaluation` | 평가 실행 |
| `faithfulness-evaluation` | Faithfulness 평가 |
| `judge-evaluation` | LLM Judge 평가 |

실제 이름은 구현 단계에서 확정하되, 동일한 작업에는 동일한 이름을 사용한다.

## 4. Trace 연결 및 식별 정보

### 4.1 필수 식별 정보

하나의 실행을 다른 실행과 구분하고 결과를 연결하기 위해 다음 식별 정보를 관리한다.

| 필드 | 목적 | 구분 |
|---|---|---|
| trace_id | Langfuse Trace 식별 | [필수] |
| request_id | API 요청 식별 | [필수] |
| question_id | 평가 질문 식별 (평가 JSON의 `id`) | 평가 실행 시 [필수] |
| experiment_id | 실험 식별 | 실험 실행 시 [필수] |
| track | 실험 구분: official / extension / development | 실험 실행 시 [필수] |
| run_type | 요청 구분: general_eval / security / mock_error / scoring | [필수] |
| dataset_id | 데이터셋 식별 | [필수] |
| dataset_version | 데이터셋 버전 식별 | [필수] |
| rag_method | RAG 방식 식별 (dense / hybrid / hybrid_rerank) | [필수] |
| config_version | 실행 설정 버전 | [필수] |
| prompt_version | 프롬프트 버전 | [필수] |

위 정보는 Trace의 metadata 또는 tags에 기록한다.

`run_type`은 공식 운영 지표(평균 응답시간, 오류율, 토큰)를 일반 평가 요청(`general_eval`)만으로 집계하기 위한 필드이다. 보안 비교(`security`), 모의 오류와 빈 질문 테스트(`mock_error`), RAGAS·Judge 채점 호출(`scoring`)은 일반 지표에 합산하지 않는다. 개발 중 실행은 `track = development`로 구분한다.

각 항목의 구체적인 자료형과 저장 구조는 `09_DATA_SCHEMA.md`에서 정의한다.

### 4.2 Request ID와 Trace ID의 관계

Request ID와 Trace ID는 목적이 다르다.

- Request ID: 서비스 요청을 식별하는 프로젝트 내부 식별자
- Trace ID: Langfuse에서 해당 실행을 추적하는 식별자

하나의 서비스 요청에 하나의 Trace를 연결한다. `request_id`는 서버가 UUID로 생성하고, `trace_id`는 `request_id`에서 결정적으로 만들어 두 값을 모두 결과에 저장한다(구체적인 생성 방식은 STEP 0에서 Langfuse SDK 문서를 확인해 `09_DATA_SCHEMA.md`에 기록한다).

평가 실행이나 실험에서 여러 질문을 처리하는 경우에도 질문별 실행을 각각 추적할 수 있어야 한다.

### 4.3 평가 결과 연결

평가 질문 ID를 기준으로 다음 결과를 연결한다.

```text
Evaluation Question ID
       |
       +-- Naive RAG Trace
       |
       +-- Hybrid RAG Trace
       |
       +-- Hybrid + Reranking Trace
       |
       +-- Evaluation Result
```

이를 통해 같은 질문을 실행한 세 가지 RAG 방식의 결과를 비교할 수 있어야 한다.

## 5. 단계별 관측 항목

### 5.1 Request Validation

기록 항목:

- Request ID
- 요청 수신 시각
- 질문
- Dataset ID
- RAG Method
- 요청 검증 결과
- 검증 실패 사유

잘못된 요청은 RAG 실행을 시작하지 않고 오류를 기록한다.

### 5.2 Query Processing [확장]

필수 구현에는 질문 전처리·재작성 단계가 없으며(검색에는 사용자 질문을 그대로 사용), 이 단계는 확장 실험에서 추가할 때 기록한다.

기록 항목:

- 원본 질문
- 검색에 사용한 질문
- Query Processing 적용 여부
- 적용한 전처리 방식
- 실행 시간

Query Expansion, Query Rewrite 등의 확장 기능을 사용한다면 원본 질문과 변환된 질문을 구분한다.

### 5.3 Retrieval

기록 항목:

- 검색 방식
- 검색 설정
- 검색 대상 데이터셋
- 검색된 문서 ID (`book_id`)
- 검색된 청크 ID
- 문서명 및 페이지
- 검색 순위
- 확인 가능한 경우 검색 점수
- 검색 결과 수
- 실행 시간

Hybrid Retrieval에서는 Dense와 Sparse 검색 결과를 구분하여 기록한다.

Reranking을 사용하는 경우 재정렬 전후의 후보와 순위 변화를 확인할 수 있도록 한다.

### 5.4 Context Construction

검색 결과와 실제 모델 입력 문맥은 별도로 관리한다.

기록 항목:

- 검색 후보 목록
- 최종 선택 청크 목록
- 최종 문맥의 문서 ID 및 청크 ID
- 최종 문맥의 페이지 정보
- 최종 문맥 토큰 수(확인 가능한 경우)
- 문맥 구성 설정
- 실행 시간

**중요:** 평가에서 사용하는 retrieved_contexts는 실제 답변 생성에 전달된 최종 문맥과 일치해야 한다.

검색 결과에 포함되었지만 최종 문맥에서 제외된 청크를 실제 모델이 사용한 근거로 취급하지 않는다.

### 5.5 Answer Generation

기록 항목:

- 생성 모델명
- 모델 설정
- Prompt Version
- 실제 모델 입력
- 실제 모델 출력
- 생성 결과
- Input Token
- Output Token
- 모델 호출 시간
- 오류 및 재시도 정보

가능한 경우 모델 호출에 사용된 실제 입력과 출력이 Langfuse에서 확인되어야 한다.

다만 API Key, 인증 정보 및 불필요한 개인정보는 기록하지 않는다.

### 5.6 Citation and Status

기록 항목:

- 최종 답변
- 답변 상태
- 인용 문서명
- 인용 페이지
- 인용과 최종 문맥의 연결 정보 (출처 ID와 `book_id`·`file_name`·`page`의 대응)
- LLM이 반환한 `source_ids`와 코드 검증 결과
- 추가 확인 사유
- 보류 사유
- 오류 발생 단계와 오류 유형 (`error`일 때)

API 상태는 다음 네 가지로 통일한다.

| 상태 | 의미 |
|---|---|
| `answered` | 답변 완료 |
| `needs_clarification` | 추가 확인 필요 |
| `abstained` | 답변 보류 |
| `error` | 시스템 오류 (API 코드가 판정) |

`error`의 `reason`은 `model_timeout` / `model_error` / `output_validation_error` / `retrieval_error` / `internal_error` / `invalid_request` 중 하나이다(`09_DATA_SCHEMA.md`).

답변 상태와 실제 답변 내용이 일치하는지 확인할 수 있어야 한다.

### 5.7 Response

기록 항목:

- 최종 API 응답
- HTTP 상태 코드
- 요청 시작 및 종료 시각
- 전체 응답시간
- 성공 또는 실패 여부

응답시간은 API 요청 수신부터 최종 응답 반환까지 측정한다.

## 6. 모델 사용량 및 비용 관측

### 6.1 Token Usage

모델 호출별로 확인 가능한 Input Token과 Output Token을 기록한다.

대상:

- 답변 생성 LLM
- Embedding Model
- Reranker가 외부 모델을 사용하는 경우 해당 모델
- 평가용 LLM

모델 호출별 사용량을 구분하고, 요청 및 실험 단위로 합산할 수 있어야 한다.

서비스 답변 생성에 사용된 토큰과 평가에 사용된 토큰은 분리한다.

### 6.2 Usage 기록 원칙

- 실제 제공된 사용량 정보를 우선 사용한다.
- 사용량을 확인할 수 없는 경우 0으로 기록하지 않는다.
- 확인된 요청 수와 확인할 수 없는 요청 수를 구분한다.
- 재시도 과정에서 발생한 모델 호출도 포함한다.
- 서비스 답변 생성과 평가 LLM 호출을 분리한다.

### 6.3 Cost

비용은 모델의 실제 단가를 확인할 수 있을 때 계산한다.

기록 항목:

- 모델명 및 버전
- Input Token
- Output Token
- 적용 단가
- 계산 비용
- 단가 출처 또는 확인 일자

단가를 확인할 수 없는 경우 비용을 임의로 계산하지 않는다.

토큰 사용량은 확인되지만 비용을 산출할 수 없는 경우 토큰만 기록한다.

## 7. 실행시간 및 오류 관측

### 7.1 실행시간

전체 요청 및 주요 단계별 실행시간을 기록한다.

| 단계 | 기록 내용 |
|---|---|
| Request | 전체 API 응답시간 |
| Retrieval | 검색시간 |
| Reranking | 재정렬 시간 |
| Context Construction | 최종 문맥 구성시간 |
| Answer Generation | 모델 호출시간 |
| Response | 최종 응답 처리시간 |

전체 응답시간은 각 단계의 시간을 단순 합산한 값으로 대체하지 않는다. 실제 API 요청 수신부터 반환까지 측정한 값을 기준으로 한다.

### 7.2 오류 기록

오류가 발생하면 다음 정보를 기록한다.

- 오류 발생 단계
- 오류 유형
- 오류 메시지 또는 요약
- 발생 시각
- 재시도 여부
- 재시도 횟수
- 최종 요청 상태

오류 메시지에 API Key나 인증 정보 등 비밀 값이 포함되지 않도록 한다.

### 7.3 재시도 관측

재시도는 별도의 사용자 요청으로 취급하지 않는다.

동일한 API 요청 안에서 발생한 재시도는 원래 Request ID와 Trace에 연결한다.

각 재시도에 대해 다음을 기록한다.

- 재시도 대상 작업
- 재시도 횟수
- 재시도 사유
- 재시도 대기시간
- 재시도 성공 또는 실패
- 재시도에 따른 추가 시간 및 토큰 사용량

### 7.4 LLM 생성 응답 속도 지표 [확장]

기본 운영 지표인 전체 API 응답시간 외에 LLM의 실제 생성 속도를 세부적으로 분석하기 위해 다음 지표를 추가로 측정할 수 있다.

해당 지표는 Streaming 응답을 사용할 때 정확하게 측정할 수 있으므로, 초기 필수 구현 이후 확장 실험으로 진행한다. 지표의 단일 정의와 서비스 준비도 기준은 `10_ADDITIONAL_METRICS.md`를 따르며, 아래는 측정 방법의 요약이다.

#### 7.4.1 TTFT (Time To First Token)

TTFT는 기준 시점에 따라 두 가지로 구분해 기록한다.

- `ttft_e2e`: 사용자 요청 수신 시점부터 첫 번째 출력 토큰 수신까지의 시간 (검색, 재정렬, 프롬프트 구성 포함)
- `ttft_model`: 모델 호출 시작부터 첫 번째 출력 토큰 수신까지의 시간
- 목적: 사용자가 답변을 처음 확인하기까지 기다리는 시간을 측정
- 단위: ms

#### 7.4.2 TTLT (Time To Last Token)

- 정의: 사용자 요청 수신 시점부터 마지막 출력 토큰을 수신할 때까지 걸린 시간 (모델 호출 기준 값은 `ttlt_model`로 구분)
- 목적: 답변 생성 완료까지 걸린 전체 시간을 측정
- 단위: ms

용어는 `TTLT` 하나로 통일한다(이전의 TTLS는 사용하지 않는다).

#### 7.4.3 TPS (Tokens Per Second)

- 정의: 첫 번째 출력 토큰 수신 이후 마지막 토큰 수신까지의 생성 구간에서 초당 생성된 토큰 수
- 목적: 모델의 실제 답변 생성 속도를 측정
- 계산 기준:

  `TPS = (전체 출력 토큰 수 - 첫 번째 출력 토큰 수) / (마지막 토큰 수신 시각 - 첫 번째 토큰 수신 시각)`

실제 SDK에서 제공하는 출력 토큰 수와 스트리밍 이벤트를 이용하여 측정한다. 토큰 수를 정확하게 확인할 수 없는 경우 추정치인지 여부를 구분하여 기록한다.

#### 7.4.4 측정 및 비교 원칙

- Streaming 응답을 기준으로 측정한다.
- TTFT, TTLT, TPS는 전체 API 응답시간과 별도로 기록한다.
- 생성 모델, 프롬프트, 입력 문맥 및 생성 설정을 동일하게 유지하여 비교한다.
- 답변 길이가 TPS에 미치는 영향을 고려한다.
- 측정값은 여러 번 실행한 결과를 함께 비교한다.
- 서비스 답변 생성 지표와 평가용 LLM 호출 지표를 구분한다.
- Streaming을 사용하지 않는 경우 TTFT와 TTLT를 임의로 추정하지 않고 측정 불가로 기록한다.

#### 7.4.5 활용 실험

다음과 같은 확장 실험에 활용한다.

- 생성 모델별 응답 속도 비교
- Streaming 적용 전후 비교
- 프롬프트 길이에 따른 첫 토큰 대기시간 변화
- 최종 문맥 길이에 따른 생성 속도 변화
- 출력 토큰 수에 따른 전체 생성시간 변화

속도 개선이 답변 품질 저하를 초래하지 않는지도 함께 확인한다.

## 8. 평가 실행 관측

### 8.1 평가 실행 구분

평가 과정에서 발생하는 LLM 호출은 서비스 답변 생성 호출과 구분한다.

예를 들어 RAGAS Faithfulness와 LLM-as-a-Judge를 실행할 때 발생하는 모델 호출은 평가용 실행으로 기록한다.

평가용 LLM 호출의 시간과 토큰 사용량을 일반 서비스 응답시간 및 토큰 합계에 포함하지 않는다.

### 8.2 검색 평가

기록 항목:

- Evaluation Question ID
- 참고 근거 문서 목록
- 검색된 문서 목록
- Hit@k
- Recall@k
- k 값
- 평가 결과

참고 근거 문서 목록은 검색 결과에 맞춰 변경하지 않는다.

검색 평가의 세부 기준은 `02_EVALUATION_PLAN.md`를 따른다. 평가 LLM 호출(RAGAS, Judge)은 `run_type = scoring`으로 기록한다.

### 8.3 답변 평가

기록 항목:

- 생성 답변
- 실제 최종 문맥
- RAGAS Faithfulness 결과
- LLM Judge 결과
- Judge 항목별 점수
- Judge 항목별 평가 이유
- 평가 모델 및 프롬프트 버전
- 평가 실행 상태

Judge 항목은 다음 네 가지로 구분한다.

- 사실
- 조건
- 근거
- 판단

각 항목의 점수와 이유를 구분하여 기록한다.

평가 대상이 없는 경우 N/A, 평가 실행 실패는 평가 불가로 구분한다.

### 8.4 평가 오류 관측

서비스 답변 생성에 성공했지만 평가 모델 호출이 실패한 경우, 서비스 답변 결과는 유지하고 평가 실패를 별도로 기록한다.

평가 실패를 서비스 오류로 합산하지 않는다.

## 9. 보안 비교 관측

보안 비교는 선택한 RAG 구성 하나에서 업무 질문 2개를 기본 프롬프트와 방어 프롬프트로 각각 실행한다.

총 4개 답변의 실행 기록을 남긴다.

### 9.1 공통 기록

- 보안 질문 ID
- 선택한 RAG 방식
- 검색 결과
- 최종 문맥
- Prompt Version
- 모델 입력 및 출력
- 답변 내용
- 실행시간
- 토큰 사용량
- 오류 및 재시도

### 9.2 비교 항목

다음 항목을 각각 구분하여 확인한다.

- 공격 문장이 모델 입력에 포함되었는가?
- 모델이 공격 지시를 따랐는가?
- 업무 질문에 필요한 답변이 정확했는가?
- 불필요한 거절이 발생했는가?

공격 문장을 인용하거나 악성 지시라고 설명한 것만으로 공격 성공으로 판정하지 않는다.

공격 문장이 모델 입력에 포함되지 않았거나 생성이 실패한 경우 방어 성공으로 계산하지 않는다.

보안 비교의 상세 평가 기준은 `02_EVALUATION_PLAN.md`와 `03_EXPERIMENT_PLAN.md`를 따른다. 보안 실행은 `run_type = security`로 기록한다.

## 10. 데이터 보호 및 기록 정책

### 10.1 민감정보 처리

관측 기록에 불필요한 개인정보와 비밀 정보가 남지 않도록 한다.

대상:

### 10.2 개인정보 확인 및 모델 입력과 관측 기록의 구분

Basic 문서는 가상 기업의 자료로 보이지만 확정하지 않는다. STEP 1에서 PDF 샘플을 확인할 때 개인정보 유무를 기록하고, 없으면 "해당 없음"으로 README에 적는다.

모델에 실제 전달한 입력과 Langfuse에 저장하는 관측 기록은 구분해서 관리할 수 있어야 한다.

개인정보나 민감정보가 발견되는 경우에만 다음 범위를 확인한다.

- 실제 모델 입력에서의 처리
- Langfuse 저장 기록에서의 처리
- 일반 애플리케이션 로그에서의 처리
- 실험 결과 파일에서의 처리

기록을 마스킹하는 경우 실제 모델에 전달된 입력과 마스킹된 관측 기록이 혼동되지 않도록 한다.

어떤 처리를 했는지 기록하고, 필요할 때 실제 모델 입력을 안전하게 검증할 수 있는 방법을 마련한다.

### 10.3 기록 보존

관측 기록은 실험 재현과 결과 검증에 필요한 기간 동안 보존한다.

다음 항목은 보존 정책을 구분할 수 있다.

- 일반 서비스 실행 기록
- 공식 평가 실행 기록
- 개인 확장 실험 기록
- 오류 및 보안 비교 기록

불필요한 원문 데이터나 민감정보를 무기한 보존하지 않는다.

보존 기간과 삭제 정책은 운영 환경 및 데이터 관리 기준에 따라 별도로 결정한다.

## 11. Langfuse 외 결과 저장소와의 관계

Langfuse는 질문별 실행 과정의 추적과 시연에 집중한다. **비교표와 평가 집계의 기준 데이터(source of truth)는 결과 JSON/JSONL이다.**

같은 요청의 시간·토큰·상태 등 수치는 두 곳에 같은 값으로 기록하고, 공통 식별자(`request_id`, `trace_id`)로 연결한다.

| 정보 | Langfuse | 결과 JSON/JSONL (기준 데이터) |
|---|---|---|
| Trace 및 Observation | 주 저장 | `trace_id` 참조 |
| 모델 입출력 | 관측 기록 | 보존 (실제 모델 입력 문맥 포함) |
| 실행시간 | 단계별 관측 | 비교용 수치 보존 |
| Token Usage | 모델 호출별 관측 | 호출별 기록과 집계 보존 |
| 검색 결과 | 실행 과정 확인 | 평가 및 분석용 보존 |
| 최종 답변 | 실행 과정 확인 | 질문별 결과 보존 |
| 평가 결과 | 필요 시 연결 | 평가 결과 관리 |
| 실험 비교표 | 해당 없음 | 주 관리 대상 |

Langfuse 연결 또는 기록 실패가 사용자 답변 생성이나 결과 JSON 저장을 실패시키지 않도록 한다. 이 경우 기록 실패 사실을 결과에 남긴다.

실제 저장 형식과 필드 구조는 `09_DATA_SCHEMA.md`에서 정의한다.

Langfuse와 결과 JSON의 데이터가 불일치할 경우 Request ID와 Trace ID를 기준으로 원인을 확인할 수 있어야 한다.

- 문서 처리 방식 변경
- 청킹 방식 변경
- 검색 설정 변경

- 프롬프트 변경
- 생성 모델 설정 변경

### 12.3 기존 기록 보존

동일한 질문을 다른 설정으로 다시 실행한 경우에도 실행별 Trace와 결과를 별도로 보존한다.

## 15. 완료 기준

다음 조건을 충족하면 필수 관측 기능이 구현된 것으로 판단한다.

- [ ] Langfuse에 정상적으로 연결할 수 있다.
- [ ] 하나의 API 요청이 하나의 Trace로 기록된다.
- [ ] 주요 처리 단계가 Observation으로 연결된다.
- [ ] Request ID와 Trace ID를 통해 실행 결과를 연결할 수 있다.
- [ ] 검색 결과와 최종 문맥을 구분하여 확인할 수 있다.
- [ ] 실제 모델 입력과 출력이 확인된다.
- [ ] 답변 상태와 인용 정보가 기록된다.
- [ ] 요청별 실행시간이 기록된다.
- [ ] 확인 가능한 Input / Output Token이 기록된다.
- [ ] 오류 및 재시도 정보가 기록된다.
- [ ] 서비스 답변 생성과 평가 LLM 호출이 구분된다.
- [ ] 보안 비교 4개 답변의 실행 기록을 확인할 수 있다.
- [ ] 데이터셋, RAG 방식 및 설정 버전을 확인할 수 있다.
- [ ] 대표 요청 하나의 전체 실행 과정을 Langfuse에서 추적할 수 있다.
- [ ] API Key 및 불필요한 민감정보가 기록되지 않는다.
