# 06. MODEL_SELECTION.md
# 모델 선정 및 비교 계획

## 1. 문서 목적

본 문서는 금융 PDF 기반 RAG 프로젝트에서 사용하는 생성 모델, Embedding 모델, Sparse Retrieval 구성 요소, Reranker 및 평가 모델의 선정 기준과 비교 방법을 정의한다.

본 프로젝트는 하나의 통합 RAG 시스템에서 세 가지 검색 방식을 비교한다.

- Naive RAG (Dense Retrieval)
- Hybrid Retrieval
- Hybrid + Reranking

모델 및 구성 요소는 각 기능의 목적에 맞게 선정하며, 공식 RAG 방식 비교를 시작하기 전에 공통으로 사용할 모델과 설정을 확정한다.

본 문서는 특정 모델을 무조건 도입하는 것을 목적으로 하지 않는다. 실제 사용 가능 여부, 한국어 및 금융 문서 처리 성능, 검색 품질, 응답시간, 비용, 기술적 호환성을 확인한 후 선정한다.

### 1.1 기본 원칙

1. 생성 모델은 GPT-6 Luna를 사용한다.
2. 세 가지 RAG 방식의 공식 비교에서는 동일한 Embedding 모델을 사용한다.
3. 세 가지 RAG 방식의 공식 비교에서는 동일한 생성 모델과 답변 프롬프트를 사용한다.
4. Sparse Retrieval과 Reranker는 각 검색 방식에 필요한 구성 요소로 구분한다.
5. 평가 모델은 생성 모델과 동일할 필요가 없으며, 예산과 이용 가능성을 고려하여 선정한다.
6. 공식 비교를 시작한 이후에는 공통 비교 조건을 임의로 변경하지 않는다.
7. 모델 변경 및 설정 변경 실험은 기존 공식 비교 설정을 보존한 별도 실험으로 수행한다.
8. 초기 Basic 구현에서는 불필요하게 많은 모델을 도입하지 않는다.
9. 모델의 이름이나 벤치마크 점수만으로 선정하지 않고 실제 프로젝트 데이터와 질문을 활용하여 확인한다.

### 1.2 필수와 확장 구분

- **[필수]**: 공식 과제 수행 및 세 가지 RAG 방식의 공정한 비교를 위해 필요한 모델 선정과 설정
- **[확장]**: 모델 종류별 성능 비교, 추가 임베딩 실험, 리랭커 비교 및 최적화 실험

본 문서에서 [확장]으로 표시한 항목은 모두 구현할 필요가 없다. 프로젝트의 기본 기능을 완성한 이후 필요에 따라 진행한다.

## 2. 프로젝트 모델 구성

### 2.1 모델 및 구성 요소

| 구분 | 역할 | 선정 방향 |
|---|---|---|
| Generation Model | 검색된 근거를 바탕으로 답변 생성 | GPT-6 Luna 고정 |
| Embedding Model | 문서와 질문을 벡터로 변환 | 공통 모델 1개 선정 (§11.2 소규모 확인) |
| Sparse Retrieval | 키워드 및 용어 기반 검색 | BM25 (Hybrid Retrieval 구성에 사용) |
| Reranker | 검색 후보의 관련성 재평가 및 순위 조정 | bge-reranker-v2-m3 (Hybrid + Reranking에 사용) |
| Evaluation Model | 생성 답변의 품질 평가 | GPT-6 Luna (초기값) |

구체적인 초기값은 §11.1에서 정의한다.

### 2.2 모델 선정 순서

다음 순서로 선정한다.

1. 생성 모델 확정 (GPT-6 Luna, STEP 0에서 연결·파라미터 확인)
2. Embedding 모델 1개 선정: 근거를 가진 후보 2개를 1회 소규모 확인(§11.2)한 뒤 동결
3. Sparse Retrieval 기술 및 검색 설정 확정 (BM25, RRF)
4. Reranker 확정 (bge-reranker-v2-m3). 후보 간 비교는 [확장]
5. 평가 모델 확정 (GPT-6 Luna)
6. 공식 RAG 방식 비교에 사용할 공통 설정 동결

Embedding 모델은 검색 결과에 직접 영향을 주므로 공식 비교 전에 선정해야 한다.

Reranker는 Hybrid Retrieval 결과를 재정렬하는 데 사용하므로, 검색 후보 수와 최종 선택 개수 등 관련 설정을 함께 확정한다.

평가 모델은 답변 생성 모델과 별도로 선정할 수 있으며, 평가 비용과 결과의 일관성을 고려한다.

## 3. Generation Model

### 3.1 선정 모델 [필수]

본 프로젝트의 답변 생성 모델은 GPT-6 Luna로 고정한다.

**선정 원칙**

- 답변 생성 모델은 GPT-6 Luna 하나만 사용한다.
- 세 가지 RAG 방식에 동일한 모델을 적용한다.
- 생성 모델 간 성능 비교는 필수 과제 및 기본 실험 범위에 포함하지 않는다.
- 호출 방식은 OpenAI API이며 실제 API 식별자는 `gpt-6-luna`로 한다. API 키는 환경변수로 관리하고, 연결과 지원 파라미터는 STEP 0에서 확인한다.
- 실제 API에서 사용하는 모델 식별자와 사용자에게 표시하는 모델 이름을 구분하여 관리한다.

### 3.2 생성 모델의 역할

생성 모델은 다음 작업을 수행한다.

1. 사용자 질문과 검색된 최종 문맥을 입력받는다.
2. 문맥에 포함된 근거를 바탕으로 답변을 생성한다.
3. 필요한 조건이 누락되었으면 추가 확인을 요청한다.
4. 근거가 부족하면 답변을 보류하고 이유를 설명한다.
5. 답변에 사용한 문서명과 페이지 정보를 연결한다.
6. 검색 문서에 포함된 지시문을 사용자 또는 시스템의 지시와 혼동하지 않도록 방어 프롬프트를 적용한다.

### 3.3 생성 설정 관리 [필수]

다음 설정을 기록하고 관리한다.

- 실제 모델 식별자
- API 제공자 및 호출 방식
- Temperature
- 최대 출력 토큰
- 기타 생성 파라미터
- 답변 프롬프트 버전
- 보안 방어 프롬프트 버전
- 요청별 Input/Output Token
- 모델 호출 시간
- 모델 호출 오류 및 재시도 정보

실제 지원 여부가 확인되지 않은 파라미터는 임의로 사용하지 않는다.

**STEP 0 확인 결과 (`gpt-6-luna`, `DECISIONS.md` §1.2)**: 추론 모델이며 `temperature`는 기본값(1)만, `top_p`는 지원하지 않는다. `max_tokens` 대신 `max_completion_tokens`를 쓰고 출력 토큰에 추론 토큰이 포함된다. `reasoning_effort`(`none`/`low`/`medium`/`high`/`xhigh`), `seed`, `response_format`(`json_schema` strict 포함)은 사용할 수 있다. 따라서 이 모델의 "Temperature" 설정은 고정이며, 세 방식에 동일하게 고정할 값은 `reasoning_effort`, `max_completion_tokens`, (필요하면) `seed`이다. 응답이 실행마다 달라질 수 있는 점은 한계로 기록한다.

세 가지 RAG 방식의 공식 비교에서는 동일한 생성 설정을 사용한다.

### 3.4 생성 모델 관련 확장 실험 [확장]

생성 모델은 기본적으로 고정하므로 모델 자체를 바꾸는 비교 실험은 진행하지 않는다.

다만 다음 항목은 필요에 따라 실험할 수 있다.

- 생성 Temperature 변경
- 최대 출력 토큰 변경
- 답변 프롬프트 개선
- 문맥 길이에 따른 답변 품질 변화
- Streaming 응답 적용
- 출력 형식 및 구조화 응답 방식 비교

이러한 실험은 공식 비교 설정을 보존한 별도 실험으로 진행한다.

## 4. Embedding Model

### 4.1 역할 [필수]

Embedding 모델은 PDF에서 추출한 청크와 사용자 질문을 벡터로 변환한다.

변환된 벡터는 Qdrant에 저장하거나 검색에 사용한다.

문서와 질문을 동일한 Embedding 공간에서 비교할 수 있어야 하며, 모델이 변경되면 기존 벡터와의 호환성을 확인해야 한다.

### 4.2 선정 기준 [필수]

다음 기준을 중심으로 후보 모델을 검토한다.

#### 4.2.1 한국어 및 다국어 처리 성능

- 한국어 문장과 질문을 적절하게 표현할 수 있는가?
- 한글과 영문이 섞인 기업명, 제품명, 기술 용어를 처리할 수 있는가?
- 영문 약어 및 숫자와 단위가 포함된 문장을 처리할 수 있는가?
- 문서와 질문의 표현이 다르더라도 의미적으로 관련된 내용을 찾을 수 있는가?

**선정 이유**

본 프로젝트의 PDF에는 기업명, 사업부문, 제품명, 회계 및 경영 용어 등이 포함될 수 있다.

질문과 문서가 동일한 단어를 사용하지 않더라도 의미적으로 관련된 정보를 검색해야 하므로 한국어 처리 성능이 중요하다.

#### 4.2.2 금융 문서 및 수치 처리 성능

- 매출액, 영업이익, 비용 등 금융 용어를 구분할 수 있는가?
- 연도, 반기, 분기 등 기간 표현을 처리할 수 있는가?
- 회사명, 제품명, 사업부문, 지역을 구분하는 데 적절한가?
- 숫자와 단위가 포함된 문장에서 의미적 유사성을 적절하게 표현하는가?

**선정 이유**

금융 문서에서는 일반적인 문장 의미뿐 아니라 회사, 기간, 단위 및 사업 범위가 중요하다.

다만 Embedding만으로 숫자나 기간의 정확한 일치 여부를 보장할 수는 없다. 이러한 조건은 메타데이터 필터, Sparse Retrieval, 문맥 구성 및 답변 검증과 함께 처리한다.

#### 4.2.3 검색 품질

- 실제 프로젝트 질문에서 관련 근거를 검색할 수 있는가?
- Hit@k와 Recall@k가 적절한가?
- 확장 실험에서 MRR, Precision@k 등을 비교할 수 있는가?
- 질문 유형에 따라 검색 결과가 지나치게 편향되지 않는가?

**선정 이유**

Embedding 모델의 주요 목적은 문서와 질문 사이의 의미적 관련성을 벡터로 표현하는 것이다.

따라서 일반적인 공개 벤치마크 점수보다 실제 프로젝트의 질문과 문서를 활용한 검색 결과가 중요하다.

#### 4.2.4 벡터 차원 및 저장소 호환성

- 출력 벡터 차원은 얼마인가?
- Qdrant에서 해당 벡터를 저장하고 검색할 수 있는가?
- 사용하려는 거리 계산 방식과 호환되는가?
- 모델 변경 시 기존 벡터를 재생성해야 하는가?

**선정 이유**

Qdrant에 저장된 벡터와 검색 시 생성되는 질문 벡터는 동일한 차원과 호환되는 표현을 사용해야 한다.

Embedding 모델이나 출력 차원이 변경되면 기존 벡터를 그대로 재사용할 수 없을 수 있으므로 모델 버전과 벡터 설정을 관리해야 한다.

#### 4.2.5 속도 및 비용

- 문서 전체를 임베딩하는 데 걸리는 시간은 얼마인가?
- 질문 하나를 임베딩하는 데 걸리는 시간은 얼마인가?
- API 호출 비용 또는 로컬 실행에 필요한 자원은 얼마인가?
- 요청 제한과 배치 처리 지원 여부는 어떠한가?
- 대량 문서 처리 시 처리량은 적절한가?

**선정 이유**

Basic 데이터셋뿐 아니라 Intermediate 및 Advanced 데이터셋으로 확장하면 문서와 청크 수가 증가한다.

따라서 검색 품질뿐 아니라 색인 속도와 운영 비용도 함께 고려한다.

### 4.3 후보 모델 비교 [확장]

Embedding 모델 후보는 다음과 같은 유형에서 검토할 수 있다.

- OpenAI 등 API 기반 Embedding 모델
- 한국어 및 다국어 처리에 강점을 가진 공개 Embedding 모델
- 로컬에서 실행할 수 있는 다국어 Embedding 모델

특정 제공자나 모델을 사전에 필수로 지정하지 않는다.

후보 모델은 실제 사용 가능 여부와 프로젝트 환경에 따라 선정한다.

처음부터 많은 후보를 비교하지 않고, 서로 다른 특성을 가진 소수의 후보부터 비교한다.

### 4.4 Embedding 모델 비교 실험 [확장]

동일한 문서와 질문을 사용하여 후보 모델을 비교한다.

**통제 조건**

- 동일 PDF
- 동일 텍스트 추출 결과
- 동일 청킹 결과
- 동일 검색 방식
- 동일 검색 후보 수
- 동일 평가 질문
- 동일 검색 평가 기준

**비교 항목**

| 항목 | 측정 내용 |
|---|---|
| Hit@k | 관련 근거 검색 여부 |
| Recall@k | 참고 근거 검색 비율 |
| MRR | 첫 관련 근거의 검색 순위 |
| Precision@k | 검색 결과의 관련 청크 비율 |
| Indexing Time | 전체 문서 색인 시간 |
| Query Embedding Time | 질문 임베딩 시간 |
| Embedding Cost | 확인 가능한 임베딩 비용 |
| Vector Dimension | 출력 벡터 차원 |

공식 필수 지표와 추가 확장 지표를 구분하여 기록한다.

### 4.5 Embedding 모델 확정 [필수]

공식 RAG 방식 비교를 시작하기 전에 Embedding 모델을 하나 선정한다. 필수 범위의 선정 방식은 근거를 가진 후보에 대한 **1회 소규모 확인 + 기록**이다(§11.2: e5-large vs BGE-M3, development 30문항, Dense, Hit@5/Recall@5). 후보 간 정량 비교 실험(§4.3, §4.4)은 [확장]이다.

확정한 모델은 세 가지 RAG 방식에서 공통으로 사용한다.

모델 변경이 필요한 경우 기존 공식 비교 설정을 보존하고 별도의 모델 변경 실험으로 수행한다.

### 4.6 Embedding 변경 시 주의사항 [필수]

Embedding 모델 또는 벡터 차원이 변경되면 기존 벡터와의 호환성을 확인한다.

호환되지 않는 경우 기존 벡터를 그대로 사용하지 않고 재색인해야 한다.

다음 정보를 버전으로 관리한다.

- Embedding 모델 식별자
- 모델 버전
- 벡터 차원
- 거리 계산 방식
- 정규화 설정
- 청킹 설정
- 색인 버전

## 5. Sparse Retrieval

### 5.1 역할 [필수]

Sparse Retrieval은 문서와 질문에서 단어 및 용어의 일치 정도를 활용하는 검색 방식이다.

Dense Retrieval이 문장의 의미적 유사성을 중심으로 검색한다면, Sparse Retrieval은 특정 단어와 용어가 실제로 포함되어 있는지를 검색에 반영한다.

본 프로젝트에서는 Hybrid Retrieval을 구성하기 위한 검색 방식으로 사용한다.

### 5.2 선정 기준 [필수]

다음 사항을 검토한다.

- 한국어 문서의 형태소 및 토큰 처리
- 영문 기업명과 제품명 처리
- 숫자, 날짜, 단위 및 약어 처리
- 검색 결과의 관련성
- 검색 속도
- Qdrant와의 연동 가능성
- LangChain과의 연동 가능성
- 구현 및 유지보수 복잡성

**선정 이유**

금융 문서에서는 매출, 영업이익, 특정 기업명, 제품명, 지역명 등 정확한 용어가 중요할 수 있다.

Dense Retrieval만으로는 특정 용어의 일치 여부가 충분히 반영되지 않을 수 있으므로 Sparse Retrieval을 결합하여 검색 범위를 보완한다.

### 5.3 후보 기술 검토 [확장]

다음과 같은 기술 및 방식을 후보로 검토할 수 있다.

- BM25
- Qdrant의 Sparse Vector 검색 기능
- 별도 검색 엔진 기반 Sparse Retrieval
- 한국어 형태소 분석 또는 토큰화 방식

초기 Basic 구현에서는 별도의 검색 엔진을 추가하지 않고, 같은 청크 목록(`chunks.jsonl`)으로 메모리에서 색인하는 BM25(`rank_bm25`) + 한국어 토큰화(`kiwipiepy`)를 사용한다. 청크가 1~2천 개 수준이라 메모리 색인으로 충분하고 Qdrant 희소 벡터보다 단순하다. 세 방식이 같은 청크를 사용하므로 입력 조건은 동일하다.

BM25 토큰화의 세부 설정은 STEP 5에서 소수 질문으로 확인한다. 다른 Sparse 방식은 [확장]이다.

### 5.4 Hybrid Retrieval 구성 [필수]

Hybrid Retrieval은 Dense Retrieval과 Sparse Retrieval의 검색 결과를 결합한다.

두 검색 결과의 점수 체계가 다를 수 있으므로 결합 방식과 관련 설정을 명확하게 기록한다.

검토할 설정은 다음과 같다.

- Dense 검색 후보 수
- Sparse 검색 후보 수
- 검색 결과 결합 방식
- 점수 정규화 또는 순위 기반 결합 여부
- 최종 검색 후보 수
- 검색 필터 및 메타데이터 조건

초기값: 순위 기반 RRF(k=60), Dense 후보 20 + BM25 후보 20 → 결합 상위 20 → 최종 k=5 (§11.1). 검색 필터와 메타데이터 조건은 사용하지 않는다.

### 5.5 Sparse Retrieval 확장 실험 [확장]

필요하면 다음 실험을 수행할 수 있다.

- BM25 설정 변경
- 한국어 형태소 분석 방식 변경
- Dense와 Sparse 검색 비중 변경
- 검색 후보 수 변경
- 검색 결과 결합 방식 변경
- 특정 용어 및 숫자 중심 질문의 검색 성능 비교

이러한 실험은 공식 비교 설정과 분리하여 수행한다.

## 6. Reranker

### 6.1 역할 [필수]

Reranker는 1차 검색으로 확보한 후보 문서 또는 청크를 질문과 비교하여 관련성을 다시 평가하고 순위를 조정하는 구성 요소다.

본 프로젝트에서는 Hybrid Retrieval의 검색 결과를 재정렬하여 최종 문맥에 포함할 근거를 개선하는 용도로 사용한다.

### 6.2 적용 위치 [필수]

Hybrid + Reranking 방식의 기본 흐름은 다음과 같다.

1. Dense Retrieval 수행
2. Sparse Retrieval 수행
3. 검색 결과 결합
4. Reranker에 검색 후보와 질문 전달
5. 관련성에 따라 순위 재정렬
6. 상위 청크 선택
7. 최종 문맥 구성
8. GPT-6 Luna에 전달하여 답변 생성

Reranker는 문서 전체를 대상으로 처음부터 검색하는 것이 아니라, 1차 검색에서 확보한 후보를 재평가하는 역할을 한다.

### 6.3 선정 기준 [필수]

#### 6.3.1 관련성 평가 성능

- 한국어 질문과 문서의 관련성을 적절하게 판단하는가?
- 금융 용어와 수치가 포함된 문장을 처리할 수 있는가?
- 회사명, 제품명, 사업부문, 기간 등의 차이를 구분하는 데 도움이 되는가?
- 1차 검색 결과에서 중요한 근거를 상위로 올리는가?

**선정 이유**

Reranker의 목적은 검색 후보 중 실제 질문과 관련성이 높은 청크를 더 높은 순위로 배치하는 것이다.

따라서 모델의 일반적인 성능보다 실제 프로젝트의 검색 후보를 사용했을 때 순위가 개선되는지 확인해야 한다.

#### 6.3.2 한국어 및 다국어 처리

- 한국어 질문과 한국어 문서 처리
- 영문 및 한글 혼합 표현 처리
- 숫자와 금융 용어 처리
- 기업명 및 제품명 처리

**선정 이유**

프로젝트 문서의 특성에 맞지 않는 Reranker는 검색 결과의 순위를 오히려 악화시킬 수 있다.

#### 6.3.3 속도 및 비용

- 후보 청크 수에 따른 처리 시간
- 질문당 Reranking 시간
- API 호출 비용 또는 로컬 실행 자원
- 대량 요청 처리 가능 여부
- 입력 길이 제한

**선정 이유**

Reranker를 적용하면 검색 품질이 개선될 수 있지만 추가 처리 시간이 발생한다.

검색 품질의 개선 폭과 추가 지연시간 및 비용을 함께 비교해야 한다.

#### 6.3.4 기술적 호환성

- LangChain과 연동 가능한가?
- Qdrant 검색 결과와 연결하기 쉬운가?
- API 기반 또는 로컬 실행이 가능한가?
- 모델 입력 및 출력 형식이 적절한가?
- 운영 및 오류 처리가 단순한가?

**선정 이유**

모델 성능이 우수하더라도 기존 시스템과 연동하기 어렵다면 구현 복잡성이 커질 수 있다.

초기 구현에서는 기존 기술 스택과 쉽게 연동할 수 있는 방식을 우선 검토한다.

### 6.4 후보 모델 비교 [확장]

다음 유형을 검토할 수 있다.

- API 기반 Reranker
- 로컬에서 실행할 수 있는 공개 Reranker
- 한국어 또는 다국어 처리에 강점을 가진 Reranker

처음부터 여러 모델을 모두 도입하지 않는다.

서로 다른 실행 방식이나 특성을 가진 소수의 후보를 비교하고 실제 프로젝트 데이터에 적합한 모델을 선정한다.

### 6.5 Reranker 비교 실험 [확장]

**통제 조건**

- 동일 질문
- 동일 PDF
- 동일 청킹 결과
- 동일 Embedding 모델
- 동일 Dense 및 Sparse 검색 설정
- 동일 1차 검색 후보
- 동일 최종 문맥 개수
- 동일 최종 문맥 토큰 한도

**비교 항목**

| 항목 | 측정 내용 |
|---|---|
| Hit@k | 관련 근거 검색 여부 |
| Recall@k | 참고 근거 검색 비율 |
| MRR | 첫 관련 근거의 순위 |
| Precision@k | 검색 결과의 관련 청크 비율 |
| nDCG@k | 검색 순위 및 관련성 |
| Reranking Time | 재정렬 소요 시간 |
| Reranker Cost | 확인 가능한 호출 비용 |
| Failure Rate | Reranking 실패 비율 |

Reranker 적용 전후를 비교하여 검색 순위와 최종 문맥의 품질이 개선되는지 확인한다.

### 6.6 Reranker 설정 관리 [필수]

다음 설정을 기록한다.

- Reranker 모델 식별자 및 버전
- 1차 검색 후보 수
- Reranker 입력 후보 수
- 최종 선택 청크 수
- 관련성 점수 및 순위
- Reranking 처리 시간
- 모델 호출 비용
- 오류 및 재시도 정보

Reranker 적용 여부와 설정은 실험별로 구분한다.

## 7. Evaluation Model

### 7.1 역할 [필수]

Evaluation Model은 생성된 답변의 품질을 평가하는 데 사용한다.

본 프로젝트의 공식 평가에서는 다음 항목을 평가한다.

- RAGAS Faithfulness
- LLM-as-a-Judge의 사실
- LLM-as-a-Judge의 조건
- LLM-as-a-Judge의 근거
- LLM-as-a-Judge의 판단

Evaluation Model은 사용자에게 답변을 제공하는 Generation Model과 역할이 다르다.

### 7.2 선정 원칙 [필수]

- 평가 모델은 생성 모델과 동일할 필요가 없다.
- 예산과 실제 이용 가능한 모델을 고려한다.
- 생성 모델인 GPT-6 Luna를 평가 모델로 사용하는 것도 가능하다.
- 평가 모델을 별도로 선택하는 경우 평가 비용과 품질을 함께 검토한다.
- 세 가지 RAG 방식에 동일한 평가 모델을 사용한다.
- 동일한 평가 프롬프트와 생성 설정을 사용한다.
- 평가 모델 변경은 별도의 실험으로 관리한다.

### 7.3 선정 기준 [필수]

#### 7.3.1 평가 일관성

- 동일한 답변에 대해 일관된 평가를 제공하는가?
- 사실과 조건을 구분하여 판단할 수 있는가?
- 근거 문맥과 답변의 일치 여부를 평가할 수 있는가?
- 답변, 추가 확인, 보류의 적절성을 구분할 수 있는가?

**선정 이유**

평가 모델의 판단이 불안정하면 RAG 방식별 결과를 공정하게 비교하기 어렵다.

따라서 평가 모델 자체의 일반적인 성능뿐 아니라 동일한 평가 조건에서 일관된 결과를 제공하는지가 중요하다.

#### 7.3.2 평가 비용

- 질문당 평가 비용
- 전체 평가셋 실행 시 예상 비용
- RAGAS 평가 호출 비용
- LLM-as-a-Judge 호출 비용
- 평가 재실행에 따른 추가 비용

**선정 이유**

평가 대상 질문이 많아지면 평가 LLM 호출 비용도 증가한다.

Basic뿐 아니라 Intermediate 및 Advanced까지 확장할 가능성을 고려하여 평가 비용을 확인한다.

#### 7.3.3 평가 속도 및 안정성

- 평가 응답 시간
- API 호출 제한
- 오류 및 재시도 가능 여부
- 출력 형식의 안정성
- 구조화된 평가 결과 생성 가능 여부

**선정 이유**

평가 과정이 실패하면 결과를 비교하기 어렵고 전체 실험 시간이 길어질 수 있다.

평가 결과는 정해진 형식으로 저장할 수 있어야 한다.

#### 7.3.4 평가 결과의 검증 가능성

- 평가 이유를 짧게 설명할 수 있는가?
- 평가 결과와 근거를 함께 저장할 수 있는가?
- 평가 기준을 따르지 않은 결과를 식별할 수 있는가?
- 대표 사례를 사람이 원문과 대조할 수 있는가?

**선정 이유**

LLM-as-a-Judge는 자동 평가를 지원하는 도구이지, 최종적인 정답 판정자가 아니다.

대표 평가 결과는 원문과 대조하여 자동 평가의 오류 여부를 확인해야 한다.

### 7.4 평가 모델 비교 [확장]

필요하면 소수의 후보 모델을 동일한 평가 데이터로 비교한다.

**비교 항목**

- 평가 결과 일관성
- 사람의 원문 검토 결과와의 일치 정도
- 평가 이유의 적절성
- 평가 실패율
- 평가 시간
- 평가 비용

평가 모델 비교를 위해 별도의 정답을 임의로 만들지 않는다.

기존 평가 데이터와 사람이 검토한 대표 사례를 활용한다.

### 7.5 평가 실행 원칙 [필수]

- 생성된 답변과 실제 최종 문맥을 평가 입력으로 사용한다.
- 평가용 정답과 채점 기준은 평가 단계에서만 전달한다.
- 정답 및 채점 기준을 검색이나 답변 생성 입력에 포함하지 않는다.
- 같은 생성 답변을 RAGAS와 Judge 평가에 사용한다.
- 평가 LLM의 사용량과 시간은 서비스 답변 생성과 분리하여 기록한다.
- 평가 모델 오류 및 평가 불가 결과를 정상적인 0점으로 처리하지 않는다.

## 8. 공통 모델 및 설정 관리

### 8.1 공식 RAG 비교의 공통 조건 [필수]

세 가지 RAG 방식의 공식 비교에서는 다음 조건을 동일하게 유지한다.

| 항목 | Naive RAG | Hybrid Retrieval | Hybrid + Reranking |
|---|---|---|---|
| Generation Model | 동일 | 동일 | 동일 |
| Embedding Model | 동일 | 동일 | 동일 |
| PDF 추출 결과 | 동일 | 동일 | 동일 |
| 청킹 결과 | 동일 | 동일 | 동일 |
| 답변 프롬프트 | 동일 | 동일 | 동일 |
| 생성 설정 | 동일 | 동일 | 동일 |
| 최종 문맥 토큰 한도 | 동일 | 동일 | 동일 |
| 최종 선택 청크 수 k | 동일 | 동일 | 동일 |
| Evaluation Model | 동일 | 동일 | 동일 |
| 평가 프롬프트 | 동일 | 동일 | 동일 |
| timeout, 최대 호출 수, 재시도 횟수 | 동일 | 동일 | 동일 |

Sparse Retrieval과 Reranker는 각 방식의 정의에 따라 적용 여부가 다르다.

각 방식의 검색 후보 수, 검색 결합 설정, Reranking 설정 등은 별도로 기록한다.

### 8.2 모델 및 설정 버전 관리 [필수]

다음 정보를 실험 결과와 연결한다.

- Generation Model ID 및 버전
- Embedding Model ID 및 버전
- Sparse Retrieval 방식 및 설정
- Reranker Model ID 및 버전
- Evaluation Model ID 및 버전
- 모델 호출 파라미터
- 모델 관련 설정 버전
- 답변 프롬프트 버전
- 평가 프롬프트 버전
- 데이터셋 및 색인 버전

모델 또는 설정이 변경되면 기존 실험 결과와 구분할 수 있어야 한다.

### 8.3 모델 변경 실험 [확장]

공식 비교가 완료된 후 필요에 따라 다음 실험을 진행할 수 있다.

- Embedding 모델 변경
- Sparse Retrieval 방식 변경
- Reranker 모델 변경
- 평가 모델 변경
- 모델별 응답시간 및 비용 비교
- 모델 변경에 따른 검색 및 답변 품질 변화

모델 변경 실험은 기존 공식 비교 결과를 덮어쓰지 않는다.

## 9. 모델 선정 실험 및 기록

### 9.1 선정 절차 [필수]

모델 선정은 다음 순서로 진행한다. 필수 범위에서 정량 확인은 임베딩 소규모 확인(§11.2)뿐이며, 나머지 구성 요소는 초기값을 연결 테스트로 확인한다.

1. 사용 가능한 후보와 기술적 제약 확인
2. 선정 근거 정리 (초기값 §11.1)
3. development 질문으로 소규모 확인 (임베딩)
4. 검색 품질 및 처리 성능 측정
5. 최종 모델 선정
6. 선정 모델, 설정 및 확인된 버전·라이선스를 `DECISIONS.md`에 기록
7. 공식 RAG 비교에 사용할 설정 동결

초기에는 Basic 데이터셋의 development 질문을 활용한다(`additional`은 공식 비교용으로 보존).

Intermediate 및 Advanced 데이터셋을 위한 추가 모델 비교는 확장 단계에서 진행한다.

### 9.2 모델 선정 기록 형식

실험 기록의 기준 양식은 `03_EXPERIMENT_PLAN.md` §13이다. 모델 선정 실험은 그 양식을 따르고 아래의 모델 전용 항목을 추가로 기록한다.

| 항목 | 내용 |
|---|---|
| Model Type | Generation / Embedding / Reranker / Evaluation |
| License | 모델 카드에서 확인한 라이선스 (확인 전에는 비워 둠) |
| Model ID | 실제 모델 식별자 |
| Model Version | 모델 버전 |
| Test Dataset | 사용한 데이터셋 |
| Test Configuration | 실험 설정 |
| Evaluation Metrics | 측정 지표 |
| Latency | 처리 시간 |
| Token Usage | 확인 가능한 토큰 사용량 |
| Cost | 확인 가능한 비용 |

| Result | 실험 결과 |
| Decision | 채택 / 보류 / 제외 |

### 9.3 모델 선정 결과 보존 [필수]

최종 선정된 모델뿐 아니라 비교에 사용한 후보와 실험 결과도 보존한다.

선정되지 않은 모델의 결과를 삭제하지 않는다.

선정 이유와 제외 이유를 기록하여 이후 모델 변경 실험에서 참고할 수 있도록 한다.

## 10. 비용 및 사용량 관리

### 10.1 기록 대상 [필수]

모델 사용량은 다음과 같이 구분한다.

- Generation Model의 Input Token
- Generation Model의 Output Token
- Embedding Model의 사용량
- Reranker의 호출 횟수 및 사용량
- Evaluation Model의 Input/Output Token
- 재시도 과정에서 발생한 추가 사용량

### 10.2 비용 계산 원칙 [필수]

- 실제 확인 가능한 단가를 사용한다.
- 모델 및 서비스별 단가 기준을 기록한다.
- 확인할 수 없는 비용은 임의로 계산하지 않는다.
- 비용 확인이 불가능한 경우 토큰 및 호출량만 기록한다.
- 서비스 답변 생성과 평가 LLM 사용량을 구분한다.
- 재시도로 발생한 사용량도 포함한다.

### 10.3 모델별 비용 비교 [확장]

Embedding 및 Reranker 후보를 비교할 때는 품질뿐 아니라 실제 운영에 필요한 비용을 함께 비교한다.

단순히 호출 단가가 낮다는 이유만으로 모델을 선택하지 않는다.

검색 품질, 답변 품질, 응답시간, 유지보수 부담을 함께 검토한다.

## 11. 초기 구현 및 확장 우선순위

### 11.1 초기 Basic 구현 [필수]

아래 값은 **초기값**이다. STEP 3~6에서 소규모 확인을 거쳐 공식 비교 실행 전에 동결하고, 동결 후 변경은 새 실험 ID로 관리한다. 선택 이유와 확인된 버전은 `DECISIONS.md`에 기록한다.

| 구성 요소 | 초기값 | 비고 |
|---|---|---|
| Generation Model | GPT-6 Luna (`gpt-6-luna`), OpenAI API | 고정. 지원 파라미터(temperature, 최대 출력 토큰 등)는 STEP 0 연결 테스트에서 확인 후 기록 |
| Embedding Model | `intfloat/multilingual-e5-large` vs `BAAI/bge-m3` 1회 비교 후 승자 동결 | 로컬 실행. 아래 11.2 참조 |
| Sparse Retrieval | BM25 (`rank_bm25`) + 한국어 토큰화 (`kiwipiepy`) | 같은 `chunks.jsonl`로 메모리에서 색인. 토큰화 차이는 STEP 5에서 소수 질문으로 확인 |
| 결과 결합 | RRF (k=60), 코드로 구현 | 점수 정규화 없이 순위 기반 |
| Reranker | `BAAI/bge-reranker-v2-m3` (로컬) | |
| 후보 수 / 최종 k | Dense 후보 20, BM25 후보 20 → RRF 상위 20 → (리랭크) → 최종 k=5 | Naive는 Dense 상위 5, Hybrid는 RRF 상위 5 |
| 문맥 토큰 한도 | 4,000 토큰 (초기값) | 청크 크기 확정 후 재확인. 줄여도 대상·조건·단위·정정 내용·출처는 남김 |
| Vector Store | Qdrant, 로컬(내장) 모드 | 설정값으로 서버 모드 전환 가능하게 작성. 서버 전환(Docker)은 [확장] |
| Evaluation Model | `gpt-6-luna` (RAGAS와 Judge 동일) | 생성 모델과 같은 모델이므로 자기 평가 편향 가능성을 한계로 기록 |

초기 구현에서 모델 후보를 지나치게 많이 도입하지 않는다. 각 구성 요소가 실제로 동작하고 실험 결과를 기록할 수 있는 최소 구성을 먼저 완성한다.

### 11.2 임베딩 모델 소규모 확인 (STEP 3) [필수]

임베딩 모델은 후보 비교 실험이 아니라 **선정을 위한 1회 소규모 확인**으로 정한다. 후보 간 정량 비교 실험은 [확장]이다(§4.4).

- 후보: `multilingual-e5-large`(원본 권장 계열, 로컬)와 `BGE-M3`(입력 길이가 길어 표가 포함된 청크에 유리할 수 있음). 2개로 제한한다.
- 질문: `development` 30문항 (튜닝용 세트). `additional`은 사용하지 않는다.
- 방식: Dense 검색만 사용, 검색 지표(Hit@5, Recall@5)만 측정한다. LLM 호출 비용은 없다.
- 고정 조건: 동일 PDF, 추출 결과, 청킹, 질문, k. 모델별 별도 인덱스(컬렉션)를 만들고 벡터를 섞지 않는다. E5는 `query:` / `passage:` 접두어를 사용한다.
- 선정 규칙(실행 전 고정): Recall@5가 더 높은 모델, 같으면 Hit@5, 그래도 같으면 색인·질문 임베딩 시간이 짧은 모델.
- 실행은 `track = development`로 기록하고 결과는 보존한다. 승자를 공식 설정으로 동결하고 수치와 이유를 `DECISIONS.md`에 기록한다.
- 사용하는 모델의 라이선스는 모델 카드에서 확인해 `DECISIONS.md`에 기록한다(확인 전에는 적지 않는다).

### 11.3 확장 실험 [확장]

초기 구현 완료 이후 다음 항목을 선택적으로 진행한다. 후보와 기준은 `11_MODEL_SELECTION_GUIDE.md`를 따른다.

- Embedding 모델 후보 추가 비교
- Sparse Retrieval 기술 및 설정 비교
- Reranker 후보 추가 비교
- 평가 모델 비교
- 모델별 속도 및 비용 비교
- 데이터셋 크기에 따른 모델 성능 변화
- 모델 변경에 따른 검색 품질 및 답변 품질 변화

확장 실험은 기존 Basic 구현을 보존하고 별도 설정으로 수행한다.

## 12. 미확정 사항

초기값은 §11.1에서 정했다. 아래 항목은 해당 단계에서 실제 확인 후 확정한다.

1. Embedding 모델의 최종 선택과 정확한 모델 버전 (STEP 3, §11.2)
2. 생성 모델 `gpt-6-luna`의 지원 파라미터와 호출 방식 상세 (STEP 0)
3. 모델·패키지의 정확한 버전과 라이선스 (실제 설치·다운로드 시점에 `DECISIONS.md`에 기록)
4. BM25 한국어 토큰화 방식의 세부 설정 (STEP 5)
5. Reranker의 세부 설정과 입력 길이 처리 (STEP 6)
6. 모델별 사용량 및 비용 확인 방법과 단가 (확인 불가 시 토큰만 기록)
7. 문맥 토큰 한도의 최종값 (청크 크기 확정 후)
8. timeout, 최대 호출 수, 재시도 횟수의 값 (STEP 7~8에서 제안, 공식 실행 전 확정)

미확정 사항을 이유로 초기 설계를 불필요하게 복잡하게 만들지 않는다.

기술적으로 구현이 불가능하거나 기존 설계와 충돌하는 문제가 발생하면, 임의로 다른 모델이나 기술로 변경하지 않고 원인과 대안을 먼저 보고한다.
