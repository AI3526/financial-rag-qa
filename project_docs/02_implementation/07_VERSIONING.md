# 07. VERSIONING.md
# 버전 관리 설계

## 1. 문서 목적

본 문서는 RAG 프로젝트에서 사용하는 데이터, 문서 처리 결과, 청킹, Embedding, 검색 설정, 모델, 프롬프트, 평가 기준, 실험 결과 및 코드를 체계적으로 버전 관리하기 위한 원칙을 정의한다.

주요 목적은 다음과 같다.

1. 특정 실험이 어떤 데이터와 설정으로 실행되었는지 추적한다.
2. 이전 실험 결과를 보존하고 재현할 수 있도록 한다.
3. 모델이나 설정 변경으로 기존 결과가 덮어쓰이는 것을 방지한다.
4. Basic, Intermediate, Advanced 데이터셋과 확장 실험을 구분한다.
5. 공식 비교 결과와 개인 확장 실험 결과를 구분한다.
6. Langfuse Trace 및 평가 결과를 해당 실험과 연결한다.

본 문서는 버전 관리 원칙을 정의한다. 실제 저장 구조와 데이터 필드의 상세 정의는 `09_DATA_SCHEMA.md`에서 다룬다.

---

## 2. 버전 관리 기본 원칙

### 2.1 기본 원칙

1. 실험 결과를 재현할 수 있도록 실행 조건을 기록한다.
2. 기존 결과를 덮어쓰지 않고 새로운 버전 또는 실험 결과로 저장한다.
3. 버전이 변경된 대상과 변경 사유를 기록한다.
4. 데이터와 설정의 버전을 구분해서 관리한다.
5. 공식 필수 과제 결과와 확장 실험 결과를 구분한다.
6. 모델, 데이터, 프롬프트, 청킹, 검색 설정의 변경 이력을 추적한다.
7. 결과와 연결된 버전 정보가 누락되지 않도록 한다.
8. 불필요하게 복잡한 버전 관리 시스템을 처음부터 구축하지 않는다.

### 2.2 필수와 확장 구분

| 구분 | 내용 |
|---|---|
| [필수] | 데이터셋 버전 관리 |
| [필수] | PDF 원본 및 추출 결과의 식별 (파일 sha256 해시 포함) |
| [필수] | 청킹 및 Embedding 설정 버전 관리 |
| [필수] | 검색 및 Reranker 설정 버전 관리 |
| [필수] | 생성 모델 및 프롬프트 버전 관리 |
| [필수] | 평가 기준 및 평가 데이터 버전 관리 |
| [필수] | 실험 ID와 실행 결과 연결 |
| [필수] | Git을 이용한 코드 변경 이력 관리 (실행 시점의 commit과 변경 여부 기록) |
| [필수] | 실행 설정 스냅샷(manifest) 1개로 구성요소별 버전을 함께 저장 |
| [확장] | 설정의 자동 해시 생성 (PDF·추출 결과 해시는 필수) |
| [확장] | 실험 간 변경점 자동 비교 |
| [확장] | 모델 및 설정 변경에 대한 자동 재현 도구 |
| [확장] | 실험 관리 플랫폼과의 연동 |

## 3. 버전 관리 대상

프로젝트에서 관리할 버전은 다음과 같이 구분한다. 구분은 개념적 분류이며, **별도의 버전 관리 시스템을 대상별로 만들지 않는다.** 각 대상의 버전은 문자열(예: `chunk-v1`)로 두고, 실행마다 §9.2의 실행 설정 스냅샷 1개에 함께 저장한다.

| 대상 | 관리 내용 | 변경 시 영향 |
|---|---|---|
| Dataset | PDF 원본 및 데이터셋 구성 | 문서 처리 및 색인 결과 변경 |
| Extraction | PDF 추출 결과와 추출 도구 설정 | 청킹 및 검색 결과 변경 가능 |
| Chunking | 청킹 방식과 설정 | 청크 및 검색 결과 변경 |
| Embedding | 모델 및 임베딩 설정 | 벡터 재생성 및 재색인 |
| Retrieval | Dense/Sparse 검색 및 결합 설정 | 검색 결과 변경 |
| Reranker | 모델 및 적용 설정 | 검색 순위 변경 |
| Prompt | 시스템 및 답변 프롬프트 | 답변 결과 변경 |
| Generation | 생성 모델 및 생성 설정 | 답변 결과 변경 |
| Evaluation | 평가 질문, 정답, 기준 및 평가 설정 | 평가 결과 변경 |
| Code | 애플리케이션 코드 | 실행 로직 변경 |
| Experiment | 전체 실행 조건 및 결과 | 비교 및 재현 기준 |

각 대상의 상세 데이터 필드는 `09_DATA_SCHEMA.md`에서 정의한다.

## 4. 데이터셋 및 문서 버전 관리

### 4.1 데이터셋 버전 [필수]

Basic, Intermediate, Advanced 데이터셋을 서로 구분하여 관리한다.

초기 데이터셋 구분:

- Basic
- Intermediate
- Advanced

각 데이터셋에는 고유한 `dataset_id`와 `dataset_version`을 부여한다.

예시:

- `basic-v1`
- `intermediate-v1`
- `advanced-v1`

데이터셋 버전은 문서 구성이나 원본 파일이 변경되었을 때 새로 부여한다.

### 4.2 PDF 원본 관리 [필수]

각 PDF에 다음 정보를 기록한다.

- `book_id` (파일명에서 `.pdf`를 뺀 값)
- 파일명 (`file_name`)
- 소속 데이터셋
- 파일 버전
- 파일 크기
- 파일 형식
- 원본 파일의 해시값
- 등록 시점
- 문서 변경 여부

동일한 파일명이라도 실제 내용이 달라질 수 있으므로 파일명만으로 동일 문서를 판단하지 않는다.

원본 PDF는 가능한 한 변경하지 않고 보존한다.

PDF 파일 자체가 수정되거나 새 파일로 교체되면 기존 파일을 덮어쓰지 않고 새 버전으로 관리한다. 이 규칙은 **파일 교체 이력**에 대한 것이다.

문서 내용에 포함된 정정 공지가 어떤 값을 바꾸는지는 LLM이 검색한 문맥과 프롬프트로 판단한다. 문서 간 정정 관계를 식별하는 메타데이터나 충돌 탐지 시스템은 필수 범위에 포함하지 않는다(없는 메타데이터를 임의로 만들지 않는다).

원본 PDF의 sha256 해시는 한 번 계산해 매니페스트에 저장하며, 데이터 확인 시 비교한다.

### 4.3 PDF 추출 결과 버전 [필수]

PDF 원본이 같더라도 추출 라이브러리나 설정이 변경되면 추출 결과가 달라질 수 있다.

따라서 다음 정보를 기록한다.

- 추출 도구 및 버전
- 추출 설정
- 페이지 수
- 추출 성공 및 실패 여부
- 페이지별 추출 결과
- 표 및 이미지 처리 여부
- 추출 결과의 식별 정보 또는 해시값

추출 결과가 달라지면 이후 청킹 및 색인 결과에 영향을 줄 수 있으므로 새로운 처리 버전으로 관리한다.

## 5. 청킹 및 Embedding 버전 관리

### 5.1 청킹 설정 버전 [필수]

청킹 설정은 검색 결과에 직접적인 영향을 주므로 별도 버전으로 관리한다.

기록 항목:

- `chunking_version`
- 청킹 방식
- 청크 크기
- Overlap
- 분할 기준
- 페이지 경계 처리
- 표 처리 방식
- 문서 구조 및 제목 보존 방식
- 메타데이터 부여 방식

청킹 설정이 변경되면 새 청킹 버전을 생성한다.

기존 청크를 새 설정으로 덮어쓰지 않는다.

### 5.2 청크 식별 및 관리 [필수]

각 청크에는 고유한 `chunk_id`를 부여한다.

청크는 다음 정보와 연결되어야 한다.

- 원본 `book_id`
- 데이터셋 버전
- PDF 추출 버전
- 청킹 버전
- 페이지 정보
- 청크 내용
- 청크 순서
- 관련 메타데이터

청크 내용이나 분할 범위가 변경되면 새로운 청크로 취급한다.

### 5.3 Embedding 모델 및 설정 버전 [필수]

Embedding 모델은 모델명만 기록해서는 안 된다.

다음 정보를 기록한다.

- 모델 ID
- 모델 버전 또는 체크포인트
- 임베딩 차원
- 입력 형식
- Query/Document 전처리 방식
- 정규화 설정
- 라이브러리 버전
- 임베딩 생성 시점

Embedding 모델이나 중요한 설정이 변경되면 새 Embedding 버전을 생성한다.

서로 다른 Embedding 모델로 생성된 벡터를 같은 인덱스에서 혼합하지 않는다.

### 5.4 재색인 원칙 [필수]

다음과 같은 변경이 발생하면 필요한 범위의 재색인을 수행한다.

- Embedding 모델 변경
- 임베딩 차원 변경
- 청킹 결과 변경
- 문서 원본 변경
- PDF 추출 결과 변경
- 벡터 저장 설정 변경

재색인 시 기존 색인을 즉시 삭제하지 않는다.

새 색인을 생성하고 정상 여부를 확인한 후 사용할 색인을 전환한다.

이전 색인과 연결된 실험 결과는 보존한다.

**컬렉션 이름 규칙**: Qdrant 컬렉션 이름에 데이터셋, 청킹 버전, 임베딩 버전을 포함한다(예: `basic__chunk-v1__e5large-v1`). 버전이 바뀌면 새 컬렉션을 만들고 기존 컬렉션은 삭제하지 않는다. 임베딩 소규모 확인(`06_MODEL_SELECTION.md` §11.2)의 후보별 컬렉션도 같은 규칙으로 보존한다.

## 6. 검색 및 Reranker 설정 버전 관리

### 6.1 Retrieval 설정 [필수]

검색 방식 및 설정을 별도로 관리한다.

기록 항목:

- `retrieval_config_version`
- RAG 방식
- Dense 검색 설정
- Sparse 검색 설정
- Sparse Retrieval 방식
- 검색 후보 수
- 검색 필터
- 검색 결과 결합 방식
- RRF 등 결합 설정
- 최종 검색 결과 수 k

Naive RAG, Hybrid Retrieval, Hybrid + Reranking은 각각 구분할 수 있어야 한다.

공식 비교에서는 공통 조건을 유지하고, 방식별로 달라지는 검색 단계와 설정을 명확하게 기록한다.

### 6.2 Reranker 설정 [필수]

기록 항목:

- Reranker 모델 ID
- 모델 버전
- 입력 형식
- 1차 검색 후보 수
- Reranking 적용 여부
- 최종 후보 수
- 관련 설정 및 라이브러리 버전

Reranker 모델이나 설정을 변경하면 새로운 설정 버전을 생성한다.

### 6.3 검색 결과 보존 [필수]

각 실험의 검색 결과는 다음 정보와 연결한다.

- 질문 ID
- 실험 ID
- 검색 방식
- 검색된 청크 ID
- 검색 순위
- 검색 점수
- Reranking 전후 순위
- 최종 선택된 문맥

검색 결과와 최종 문맥은 구분한다.

이후 모델 비교에서 같은 검색 문맥을 재사용할 수 있도록 필요한 결과를 보존한다.

## 7. 프롬프트 및 생성 모델 버전 관리

### 7.1 프롬프트 버전 [필수]

시스템 프롬프트, 답변 프롬프트, 보안 방어 프롬프트, 평가 프롬프트 등을 구분하여 관리한다.

기록 항목:

- `prompt_id`
- `prompt_version`
- 프롬프트 유형
- 실제 프롬프트 내용
- 변경 사유
- 변경 시점
- 관련 실험 ID

프롬프트의 문구나 지시사항이 변경되면 새로운 버전을 부여한다.

기존 프롬프트를 덮어쓰지 않는다.

구현: 프롬프트 원본은 Git의 `prompts/*.json`이며(예: `answer_v1.json`) 파일의 sha256과 `prompt_version`을 run 레코드의 `versions`에 기록한다(D-032). Langfuse Prompt Management 연결은 STEP 9 이후다.

### 7.2 생성 모델 버전 [필수]

생성 모델과 생성 설정을 함께 기록한다.

기록 항목:

- 모델 제공자
- 모델 ID
- 모델 버전 또는 스냅샷(확인 가능한 경우)
- Temperature
- Top-p
- 최대 출력 토큰
- 기타 생성 설정
- API 또는 실행 방식

공식 비교에서는 GPT-6 Luna를 고정한다.

오픈 웨이트 생성 모델 비교는 별도의 확장 실험으로 관리한다.

### 7.3 모델 비교 실험 [확장]

생성 모델 비교 시 각 실행에 사용된 검색 결과와 최종 문맥을 동일하게 유지한다.

각 모델의 결과는 서로 다른 실행 결과로 저장한다.

모델별 프롬프트 호환성 조정이나 입력 형식 차이가 있다면 기록한다.

모델 비교 결과를 공식 RAG 방식 비교 결과에 혼합하지 않는다.

## 8. 평가 데이터 및 평가 기준 버전 관리

### 8.1 평가 데이터 [필수]

평가 질문, 참고 정답, 근거 문서, 채점 기준을 버전 관리한다.

대상:

- 개발 질문
- 추가 질문
- 확장 검증 질문
- 보안 질문
- 평가 정답 및 근거
- expected_action
- Judge 채점 기준

평가 질문이나 정답, 근거가 변경되면 새로운 평가 데이터 버전을 생성한다.

### 8.2 평가 기준 [필수]

다음 항목의 변경 이력을 관리한다.

- Hit@k 및 Recall@k 계산 기준
- RAGAS Faithfulness 설정
- LLM-as-a-Judge 평가 항목
- 평가 모델
- 평가 프롬프트
- 평가 실행 설정
- N/A 및 평가 불가 처리 기준

평가 기준이 변경된 경우 이전 평가 결과를 새로운 기준의 결과로 취급하지 않는다.

필요하다면 기존 생성 답변과 최종 문맥을 이용해 새로운 기준으로 재평가할 수 있다.

이때 기존 생성 결과와 새 평가 결과를 구분한다.

### 8.3 평가 결과 연결 [필수]

평가 결과는 다음 정보와 연결한다.

- `question_id`
- `experiment_id`
- `dataset_id`
- `dataset_version`
- `evaluation_version`
- 생성 답변 식별 정보
- 실제 최종 문맥
- 평가 모델 및 프롬프트 버전
- 평가 결과 및 사유

## 9. 실험 및 실행 버전 관리

### 9.1 Experiment ID [필수]

각 실험에는 고유한 `experiment_id`를 부여한다.

실험 ID는 데이터셋, RAG 방식, 모델, 설정 및 평가 결과를 연결하는 기준으로 사용한다.

예시:

- `exp-basic-dense-001`
- `exp-basic-hybrid-001`
- `exp-basic-rerank-001`
- `exp-basic-generation-<모델명>-001` ([확장]: 생성 모델 비교 실험 예시)

예시 이름은 식별을 위한 규칙이며, 실제 ID 생성 방식은 구현 단계에서 확정한다.

### 9.2 실험 설정 스냅샷 (manifest) [필수]

실험 실행 시점의 주요 설정을 **스냅샷 1개**(`results/{experiment_id}/manifest.json`)로 함께 저장한다. 구성요소별 버전은 이 스냅샷 안의 문자열 필드로 관리한다.

포함 정보:

- 데이터셋 및 버전
- PDF 및 추출 버전
- 청킹 버전
- Embedding 모델 및 설정
- Retrieval 설정
- Reranker 설정
- 생성 모델 및 설정
- 프롬프트 버전
- 평가 데이터 및 평가 기준 버전
- 코드 버전: `git_commit`과 작업 트리 변경 여부(`git_dirty`)
- 프롬프트 내용의 해시(파일 변경 확인용)
- timeout, 최대 호출 수, 재시도 횟수, 최종 k, 문맥 토큰 한도
- 실행 환경 (Python, 주요 패키지, 모델 버전)

공식 실행(`track = official`)은 작업 트리가 깨끗한(clean) 상태에서만 시작한다. 변경 사항이 있으면 먼저 commit한다. 개발 실행은 `git_dirty`를 기록한 채 허용한다.

실험 실행이 끝난 후 설정 파일이 변경되더라도 당시 설정을 확인할 수 있어야 한다.

### 9.3 공식 실험과 확장 실험 구분 [필수]

실험 단위의 `track` 필드로 다음과 같이 구분한다.

- `official`: 공식 필수 과제 결과
- `extension`: 개인 확장 실험
- `development`: 개발 및 디버깅 목적의 실행 (튜닝, 임베딩 소규모 확인 포함)

요청 단위의 구분은 `run_type`(`general_eval` / `security` / `mock_error` / `scoring`)이며 `05_OBSERVABILITY_PLAN.md`와 `09_DATA_SCHEMA.md`를 따른다. 두 필드는 서로 다른 축이다.

개발 중 실행한 결과를 공식 비교 결과로 자동 포함하지 않는다.

확장 실험 결과를 공식 결과에 덮어쓰지 않는다.

### 9.4 실패한 실험 보존 [필수]

실험이 실패해도 실행 기록을 남긴다.

기록 항목:

- 실패 단계
- 오류 유형
- 오류 메시지
- 재시도 여부
- 최종 성공 또는 실패 상태
- 확인 가능한 실행시간 및 사용량

성공한 실행만 선택해서 결과를 구성하지 않는다.

평가 대상과 평가 불가 상태는 `02_EVALUATION_PLAN.md`의 기준을 따른다.

## 10. Langfuse 및 실행 기록 연결

### 10.1 실행 추적 [필수]

각 요청과 실험은 Langfuse Trace 및 Observation과 연결한다.

가능한 경우 다음 식별 정보를 기록한다.

- `trace_id`
- `request_id`
- `experiment_id`
- `question_id`
- `track`, `run_type`
- `dataset_id`
- `dataset_version`
- `rag_method`
- `config_version`
- `prompt_version`
- `model_id`

### 10.2 버전 정보 기록 원칙 [필수]

Langfuse에는 해당 실행을 식별하고 추적하는 데 필요한 버전 정보를 기록한다.

실제 설정 스냅샷과 상세 결과는 결과 JSON/JSONL(기준 데이터)에서 관리한다.

민감정보, API 키, 불필요한 원본 개인정보를 버전 정보나 실행 로그에 저장하지 않는다.

Langfuse의 구체적인 기록 구조는 `05_OBSERVABILITY_PLAN.md`를 따른다.

---

## 11. 코드 및 설정 파일 버전 관리

### 11.1 Git 관리 [필수]

코드와 프로젝트 설정은 Git으로 관리한다.

기록 대상:

- 애플리케이션 코드
- 데이터 처리 코드
- 검색 및 생성 코드
- 평가 코드
- 프롬프트 파일
- 설정 파일
- 테스트 코드
- 문서

각 실험은 실행 시점의 Git commit과 연결한다(§9.2). Git 저장소는 STEP 0에서 초기화한다. `.env`, 벡터 DB 데이터, 모델 가중치, 캐시는 Git에서 제외한다.

### 11.2 설정 파일 관리 [필수]

모델 및 실험 설정은 코드에 직접 흩어 놓지 않고 `configs/` 아래 설정 파일로 관리한다. 필수 구현에서는 공식 실험 설정 파일 1개(예: `configs/official_basic_v1.yaml`)로 시작하고, 설정 종류별 폴더 분리는 필요해질 때(확장) 한다. 프롬프트는 버전이 붙은 파일로 관리한다.

실제 파일 구조는 `04_ARCHITECTURE.md` §10 및 구현 단계에서 확정한다.

API 키와 비밀번호 등 비밀정보는 Git에 포함하지 않는다.

### 11.3 Git commit 및 변경 이력 [필수]

각 작업은 작은 단위로 나누어 수행한다.

중요한 변경이 완료되면 Git commit으로 기록한다.

Commit 메시지는 변경 내용을 알아볼 수 있도록 작성한다.

설계 변경이 승인된 경우 관련 결정 기록과 구현 변경을 연결한다.

## 12. 버전 변경 및 재실행 정책

### 12.1 변경 영향 확인 [필수]

버전 변경 전에는 영향을 받는 항목을 확인한다.

예시:

| 변경 대상 | 재실행 또는 재생성 필요 여부 |
|---|---|
| PDF 원본 | 추출, 청킹, 임베딩, 색인 및 평가 영향 검토 |
| PDF 추출 방식 | 청킹, 임베딩, 색인 및 평가 영향 검토 |
| 청킹 설정 | 청크 생성, 임베딩, 색인 및 평가 |
| Embedding 모델 | 임베딩 생성 및 색인 |
| Sparse 방식 | Sparse 색인 및 검색 |
| Retrieval 설정 | 검색 및 관련 평가 |
| Reranker 모델 | Reranking 및 관련 평가 |
| 답변 프롬프트 | 답변 생성 및 평가 |
| 생성 모델 | 답변 생성 및 평가 |
| 평가 질문 | 해당 평가 질문의 전체 RAG 실행 및 평가 필요성 검토 |
| 평가 기준 | 기존 답변 재평가 가능 여부 검토 |
| 코드 | 변경된 기능과 영향 범위에 따른 테스트 및 재실행 |

### 12.2 기존 결과 보존 [필수]

새로운 버전의 실험을 수행해도 기존 결과는 유지한다.

새로운 결과는 새로운 실험 ID 또는 결과 버전으로 저장한다.

기존 결과와 새로운 결과를 비교할 수 있어야 한다.

### 12.3 변경 승인 [필수]

다음 변경은 사용자 승인 후 적용한다.

- 공식 비교 조건 변경
- 생성 모델 변경
- Embedding 모델 변경
- 청킹 방식의 주요 변경
- Sparse Retrieval 방식 변경
- Reranker 변경
- 평가 기준 변경
- 데이터셋 구성 변경
- 결과 데이터 구조 변경
- 필수 기능 및 범위 변경

단순한 코드 버그 수정은 승인된 설계 범위 내에서 진행할 수 있다.

설계 변경이 필요한 문제가 발생하면 구현을 중단하고 원인, 영향, 기존 설계를 유지하는 대안, 변경 대안을 보고한다.
