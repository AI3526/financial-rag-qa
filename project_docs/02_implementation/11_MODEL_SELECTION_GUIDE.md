# 모델 및 검색 기술 선정 가이드

## 1. 문서 목적

본 문서는 필수 구현 이후의 **확장 실험**에서 검토할 생성 모델, Embedding 모델, Sparse Retrieval 방식, Reranker 모델의 후보와 비교 방법을 정리한 **확장 후보 가이드**다.

**최종 선택의 단일 기준 문서는 `06_MODEL_SELECTION.md`(초기값)와 `DECISIONS.md`(승인된 선택, 이유, 확인된 버전·라이선스)이다.** 이 문서의 후보와 추천은 제안이며, 이미 승인된 선택을 변경하지 않는다. 공식 비교의 필수 구성은 06번 §11.1에서 확정했다(GPT-6 Luna, e5-large 또는 BGE-M3, BM25+RRF, bge-reranker-v2-m3, 평가 모델 GPT-6 Luna).

### 1.1 적용 범위

- [필수] 실제로 사용하는 모델·기술의 라이선스를 모델 카드에서 확인해 `DECISIONS.md`에 기록 (§10)
- [확장] 오픈 웨이트 생성 모델 비교
- [확장] 추가 Embedding, Sparse Retrieval, Reranker 후보 비교
- [확장] 모델 크기, 양자화, 실행 방식, 추론 환경에 따른 성능 비교

공식 비교에 필요한 모델 선정(임베딩 1회 소규모 확인 포함)은 이 문서가 아니라 `06_MODEL_SELECTION.md` §11을 따른다.

### 1.2 기존 문서와의 관계

- `06_MODEL_SELECTION.md`: 모델 선정 원칙, 초기값, 공통 관리 (최종 선택의 기준)

- `03_EXPERIMENT_PLAN.md`: 전체 실험 범위와 실험 기록 양식(§13, 기준 양식)
- `02_EVALUATION_PLAN.md`: 검색 및 답변 평가 기준
- `04_ARCHITECTURE.md`: 실제 시스템 구성과 모듈 책임
- `07_VERSIONING.md`: 모델·설정·실험 버전 관리

## 2. 모델 선정 공통 원칙

### 2.1 기본 원칙

1. 유명세나 공개 벤치마크 순위만으로 모델을 선정하지 않는다.
2. 프로젝트의 실제 PDF와 평가 질문을 사용해 비교한다.
3. 한국어, 영어, 숫자, 기업명, 제품명, 회계 및 금융 용어에 대한 처리 능력을 확인한다.
4. 검색 품질, 답변 품질, 응답시간, 사용량, 비용, 실행 가능성을 함께 고려한다.
5. 모델이나 기술을 변경할 때는 변경 대상 외의 조건을 최대한 고정한다.
6. 공식 필수 비교 결과와 확장 실험 결과를 구분한다.
7. 최종 채택 모델과 설정은 버전으로 관리한다.
8. 모델별 라이선스와 이용 조건을 확인한다.

### 2.2 필수와 확장 구분

| 구분 | 내용 |
|---|---|
| [필수] | 사용하는 모델·기술의 선정 근거, 확인된 버전, 라이선스를 `DECISIONS.md`에 기록 |
| [확장] | 추가 모델과 기술 후보 비교 (Embedding, Sparse, Reranker) |
| [확장] | 오픈 웨이트 생성 모델과 GPT-6 Luna 비교 |
| [확장] | 모델 크기, 양자화, 로컬 및 API 실행 방식 비교 |
| [확장] | 추가 Sparse Retrieval 방식과 Reranker 비교 |

공식 비교용 필수 선정은 `06_MODEL_SELECTION.md` §11을 따른다.

## 3. 생성 모델(Generation Model)

### 3.1 공식 비교용 생성 모델 [필수]

공식 RAG 비교에서는 GPT-6 Luna를 생성 모델로 고정한다.

세 가지 RAG 방식의 검색 성능 차이를 비교하는 것이 목적이므로 생성 모델을 변경해 결과에 영향을 주지 않도록 한다.

- Naive RAG (Dense)
- Hybrid Retrieval
- Hybrid + Reranking

세 방식에서 다음 조건을 동일하게 유지한다.

- 생성 모델
- 답변 프롬프트의 의미와 지시사항
- 생성 설정
- 출력 형식
- 답변에 전달하는 최종 문맥의 토큰 한도
- 평가 모델 및 평가 프롬프트

모델 API의 기술적 요구사항에 따른 차이는 별도로 기록한다.

### 3.2 오픈 웨이트 생성 모델 확장 실험 [확장]

GPT-6 Luna 외에 오픈 웨이트 생성 모델을 사용해 답변 품질과 실행 특성을 비교할 수 있다.

이 실험은 공식 RAG 비교와 분리한다.

후보를 선정할 때 특정 모델 계열에 한정하지 않는다. Qwen 및 Llama 계열은 대표적인 검토 후보이며, 다른 모델 계열도 선정 기준을 충족하면 검토할 수 있다.

'오픈 소스 모델'이라는 표현을 무조건 적용하지 않는다. 모델별로 가중치 공개 범위, 라이선스, 사용 조건이 다르므로 실제 모델의 라이선스를 확인한다.

### 3.3 생성 모델 선정 기준

| 기준 | 확인 내용 |
|---|---|
| 한국어 이해 | 한국어 질문과 문서 내용을 정확히 이해하는가 |
| 다국어 처리 | 영문 회사명, 제품명, 기술 용어 등을 처리하는가 |
| 사실 | 근거 문맥에 없는 사실이나 수치를 만들어내지 않는가 |
| 조건 | 회사, 기간, 단위, 사업부문, 지역, 정정 범위를 혼동하지 않는가 |
| 근거 기반 답변 | 실제 검색 문맥에 근거한 답변을 생성하는가 |
| 보류 판단 | 근거가 부족할 때 적절하게 답변을 보류하는가 |
| 지시사항 준수 | 추가 확인이 필요한 경우 되묻고, 답변 가능한 부분은 구분해 답하는가 |
| 실행 가능성 | 선택한 실행 환경에서 안정적으로 구동되는가 |
| 응답시간 | 실제 사용 가능한 시간 안에 답변하는가 |
| 사용량 및 비용 | 모델 호출에 필요한 사용량과 비용을 감당할 수 있는가 |
| 라이선스 | 이용 목적과 실행 방식에 적합한 라이선스인가 |

### 3.4 생성 모델 비교 방법

[확장]

첫 실험에서는 RAG 구성 하나를 선택하고 검색 결과를 고정한다.

비교 조건:

- 동일 질문
- 동일 검색 후보
- 동일한 최종 문맥
- 동일한 답변 지시사항
- 동일한 출력 형식
- 동일한 평가 기준
- 동일한 평가 모델

변경 변수는 생성 모델로 제한한다.

모델별 API 메시지 형식, 토크나이저, 컨텍스트 길이 등의 차이로 인해 기술적인 조정이 필요한 경우 그 내용을 기록한다. 답변 지시사항의 의미는 최대한 동일하게 유지한다.

평가 항목:

- 사실 (Judge)
- 조건 (Judge)
- RAGAS Faithfulness
- 근거 및 인용 적절성
- answer / clarify / abstain 판단
- 응답시간
- Input/Output Token
- 확인 가능한 비용
- 실행 안정성

평가 모델과 평가 프롬프트는 생성 모델별로 바꾸지 않는다.

### 3.5 오픈 웨이트 모델의 실행 환경

[확장]

초기에는 로컬 실행과 외부 API 실행을 동시에 구현하지 않는다.

한 가지 실행 방식으로 먼저 연결하고, 안정화 이후 다른 실행 방식을 검토한다.

검토 가능한 실행 방식 및 기술 후보:

- 로컬 추론
- 외부 호스팅 추론 API
- Ollama
- vLLM
- llama.cpp

위 기술은 후보이며 프로젝트의 확정 기술 스택이 아니다.

기록 항목:

- 모델 계열 및 정확한 모델 ID
- 모델 버전 또는 체크포인트
- 모델 크기
- 라이선스 및 이용 조건
- 실행 방식(로컬/API)
- 추론 프레임워크
- 하드웨어 및 실행 환경
- 양자화 방식 및 설정
- 최대 컨텍스트 길이
- Temperature, Top-p 등 생성 설정
- 최대 출력 토큰
- 응답시간
- 사용량 및 비용
- 실행 오류 및 제한사항

모델마다 토큰 계산 방식이 다를 수 있으므로 원시 토큰 수만으로 모델 간 효율성을 단정하지 않는다. 실제 비용, 처리 시간, 출력 품질과 함께 해석한다.

### 3.6 생성 모델 확장 실험 우선순위

1. 공식 GPT-6 Luna 기반 RAG 비교 완료
2. 오픈 웨이트 모델 후보 1개 선정 및 실행
3. 동일 문맥을 이용한 GPT-6 Luna와 비교
4. 첫 모델 실행 안정화
5. 다른 계열의 오픈 웨이트 모델 추가
6. 필요할 경우 모델 크기 및 실행 방식 비교
7. 필요할 경우 여러 RAG 구성과 생성 모델을 교차 비교

여러 RAG 구성과 여러 생성 모델을 동시에 비교하는 실험은 복잡도가 높으므로 후순위 확장으로 둔다.

## 4. Embedding 모델

### 4.1 역할 [필수]

Embedding 모델은 문서 청크와 사용자 질문을 벡터로 변환한다.

Dense Retrieval은 이 벡터 간 의미적 유사성을 이용해 관련 문서를 검색한다.

본 프로젝트는 한국어 금융 문서와 기업 사업 관련 PDF를 다루므로 다음 특성을 고려한다.

- 한국어 문장 이해
- 한국어와 영어가 혼합된 문서 처리
- 기업명 및 제품명 검색
- 금융·회계 관련 용어 처리
- 숫자와 기간이 포함된 질문 처리
- 긴 문서에서 분할된 청크의 의미 보존

### 4.2 초기 후보 모델

공식 비교용 임베딩은 `06_MODEL_SELECTION.md` §11.2의 소규모 확인(multilingual-e5-large vs BGE-M3)으로 정한다. 아래는 그 이후 확장 실험에서 검토할 후보이다. 최종 채택은 실제 데이터셋의 검색 평가를 통해 결정한다.

| 후보 | 주요 특징 | 구분 |
|---|---|---|
| multilingual-e5-large | 원본 권장 계열, 로컬 실행 | 소규모 확인 후보(필수 범위, 06번) |
| BGE-M3 | 다국어 지원, 긴 입력(약 8K 토큰), Dense 및 Sparse 관련 기능 | 소규모 확인 후보(필수 범위, 06번) |
| Qwen3-Embedding 계열 | 다국어 임베딩 모델군, 모델 크기별 선택 가능 | 확장 후보 |
| multilingual-e5-large-instruct | 다국어 검색을 위한 Instruction 기반 임베딩 | 확장 후보 |

후보 모델의 정확한 버전, 차원, 최대 입력 길이 및 라이선스는 실제로 채택하기 전에 공식 배포처에서 확인한다.

### 4.3 Embedding 선정 기준

| 기준 | 확인 내용 |
|---|---|
| 한국어 검색 | 한국어 질문과 관련 문서를 찾는가 |
| 다국어 검색 | 영문 제품명 및 혼합 언어를 처리하는가 |
| 금융 문서 적합성 | 회계, 매출, 영업이익, 거래 분류 등의 표현을 처리하는가 |
| 식별 정보 | 회사, 사업부문, 제품, 지역, 기간을 구분하는가 |
| 검색 평가 | Hit@k 및 Recall@k가 적절한가 |
| 처리 속도 | 문서 색인과 질문 임베딩에 걸리는 시간 |
| 메모리 | 로컬 실행에 필요한 메모리와 하드웨어 |
| 벡터 호환성 | Qdrant의 벡터 설정 및 차원과 호환되는가 |
| 라이선스 | 프로젝트 이용 목적에 적합한가 |

### 4.4 Embedding 비교 방법

[확장] 필수 범위의 임베딩 소규모 확인은 `06_MODEL_SELECTION.md` §11.2이다. 아래는 후보를 추가해 본격적으로 비교하는 확장 실험의 방법이다.

Embedding 모델을 비교할 때 다음 조건을 고정한다.

- 동일 PDF
- 동일 PDF 추출 결과
- 동일 청킹 결과
- 동일 평가 질문
- 동일 검색 방식
- 동일 검색 후보 수 및 k
- 동일한 평가 기준

변경 변수는 Embedding 모델이다.

각 모델로 문서 청크를 임베딩하고 별도 벡터 인덱스를 구성한다.

서로 다른 Embedding 모델의 벡터를 하나의 인덱스에서 혼합하지 않는다.

평가 지표:

- Hit@k
- Recall@k
- 검색 처리시간
- 임베딩 처리시간
- 색인에 필요한 시간
- 메모리 사용량
- 확인 가능한 사용량 및 비용

### 4.5 Embedding 모델 변경 시 주의사항

Embedding 모델을 변경하면 기존 문서 청크의 벡터를 새 모델로 다시 생성해야 한다.

다음 항목을 함께 관리한다.

- 모델 ID 및 버전
- 임베딩 차원
- 입력 전처리 방식
- Query/Document 입력 형식
- 정규화 설정
- 색인 버전
- 벡터 인덱스 식별자

## 5. Sparse Retrieval 방식

### 5.1 역할 [필수]

Sparse Retrieval은 단어와 검색어의 일치 관계를 중심으로 관련 문서를 찾는다.

Dense Retrieval이 의미적 유사성에 강점을 가진다면 Sparse Retrieval은 정확한 단어, 제품명, 기업명, 고유 표현 등에 강점을 가질 수 있다.

본 프로젝트에서 특히 중요한 검색 사례:

- 특정 회사명
- 특정 제품명
- 사업부문 명칭
- 지역명
- 특정 회계 및 거래 용어
- 정정 공지 및 승인 관련 표현
- 특정 기간과 보고 범위

### 5.2 초기 후보 방식

| 방식 | 특징 | 추천 순서 |
|---|---|---|
| BM25 | 전통적인 키워드 기반 검색, 비교적 단순하고 별도 학습 모델이 필요하지 않음 | 첫 번째 |
| SPLADE | 학습된 언어 모델을 이용해 확장된 Sparse 표현 생성 | 두 번째 |
| miniCOIL | 단어의 문맥적 표현을 반영하는 Sparse 검색 방식 | 후순위 |

### 5.3 초기 추천

BM25를 우선 구현한다.

추천 이유:

- 구현 구조가 비교적 단순하다.
- 별도의 대형 모델 추론 없이 시작할 수 있다.
- Dense Retrieval과의 차이를 이해하기 쉽다.
- Hybrid Retrieval의 기준선으로 활용하기 좋다.

초기 Hybrid 구성은 다음과 같이 제안한다.

- Dense Retrieval: 선정한 Embedding 모델
- Sparse Retrieval: BM25
- 검색 결과 결합: Reciprocal Rank Fusion(RRF)

이 구성은 초기 추천이며, RRF의 설정과 결합 방식은 실험 기록에 남긴다.

### 5.4 Sparse Retrieval 비교 기준

[확장]

BM25 외에 SPLADE 또는 miniCOIL을 추가로 검토할 수 있다.

비교 기준:

- 한국어 검색 성능
- 제품명과 기업명 검색 성능
- 숫자 및 특수 표현 검색 성능
- 금융 용어 검색 성능
- Hit@k
- Recall@k
- 검색 처리시간
- 모델 실행에 필요한 자원
- 색인 및 운영 복잡도

Sparse 방식을 비교할 때는 Embedding 모델과 청킹 결과를 고정한다.

Sparse 모델이 별도 학습이나 추론을 요구한다면 그 비용과 실행 환경도 기록한다.

## 6. Reranker 모델

### 6.1 역할 [필수]

Reranker는 1차 검색에서 가져온 후보 문서들을 질문과 비교해 관련성 순위를 다시 정렬한다.

예시:

1. Dense 및 Sparse 검색으로 후보 청크 수집
2. 검색 결과 결합
3. Reranker로 질문과 각 청크의 관련성 평가
4. 순위 재정렬
5. 상위 k개 청크를 최종 문맥으로 전달

Reranker는 검색 결과의 순위를 개선할 수 있지만, 반드시 성능이 향상되는 것은 아니다.

### 6.2 초기 후보 모델

| 후보 | 특징 | 구분 |
|---|---|---|
| BAAI/bge-reranker-v2-m3 | 다국어 Cross-Encoder 계열 Reranker | **현재 선택**(`06_MODEL_SELECTION.md`) |
| Qwen3-Reranker-0.6B | 다국어 Reranker 후보, 상대적으로 작은 모델 규모 | 확장 후보 |

후보 모델의 정확한 모델 ID, 버전, 라이선스, 입력 길이 및 실행 환경은 실제로 채택하기 전에 확인한다.

### 6.3 Reranker 선정 기준

| 기준 | 확인 내용 |
|---|---|
| 질문-문서 관련성 | 질문에 적합한 청크를 상위에 배치하는가 |
| 한국어 처리 | 한국어 문서와 질문을 정확히 비교하는가 |
| 금융 문서 적합성 | 숫자, 기간, 회사 및 제품 정보를 고려하는가 |
| 검색 품질 개선 | Reranking 전후 검색 결과가 개선되는가 |
| 처리 속도 | 후보 문서 수에 따른 지연시간 |
| 메모리 | 실행에 필요한 자원 |
| 입력 길이 | 긴 청크를 처리할 수 있는가 |
| 운영 복잡도 | 실제 프로젝트에 적용하기 쉬운가 |

### 6.4 Reranker 비교 방법

[확장]

동일한 1차 검색 결과를 사용해 Reranker 모델만 변경한다.

고정 조건:

- 동일 질문
- 동일 Embedding 모델
- 동일 Sparse Retrieval 방식
- 동일 1차 검색 후보
- 동일 후보 수
- 동일 최종 k
- 동일 최종 문맥 토큰 한도

평가 항목:

- Hit@k
- Recall@k
- 검색 결과 순위 변화
- 검색 처리시간
- Reranking 처리시간
- 최종 문맥의 관련성
- 최종 답변 품질

Reranker 적용으로 검색 지표가 개선되더라도 답변 품질이나 응답시간이 악화될 수 있으므로 함께 검토한다.

## 7. 모델 및 검색 기술 후보 구성

### 7.1 현재 선택과 확장 후보

| 구성 | **현재 선택 (`06_MODEL_SELECTION.md`)** | 확장 후보 |
|---|---|---|
| Generation | GPT-6 Luna | Qwen 또는 Llama 계열 등 오픈 웨이트 모델 |
| Embedding | multilingual-e5-large 또는 BGE-M3 (STEP 3 소규모 확인 후 동결) | 승자가 아닌 쪽, Qwen3-Embedding, multilingual-e5-large-instruct |
| Sparse Retrieval | BM25 (rank_bm25 + kiwipiepy) | SPLADE, miniCOIL, Qdrant 희소 벡터 |
| Reranker | BAAI/bge-reranker-v2-m3 | Qwen3-Reranker-0.6B |
| Search Fusion | RRF (k=60) | 다른 결합 방식은 확장 실험 |

위 "현재 선택"은 이 문서의 초기 추천(BGE-M3 기준, Qwen3-Reranker 우선)이 아니라 승인된 06번의 값이다. 확장 후보는 필수 구현과 평가를 완료한 뒤 별도 실험으로 비교한다.

### 7.2 공식 RAG 비교 구성

- Naive RAG: Dense Retrieval
- Hybrid Retrieval: Dense + BM25 (RRF)
- Hybrid + Reranking: Dense + BM25 + Reranker

공식 비교에서는 선정한 Embedding, Sparse 방식, Reranker를 공통 설정으로 사용한다. 각 구성에서 실제로 사용하는 검색 단계를 구분해 기록한다.

### 7.3 확장 실험 구성 [확장]

- Embedding 모델 교체
- Sparse Retrieval 방식 교체
- Reranker 모델 교체
- 오픈 웨이트 생성 모델 추가
- 모델 크기 및 실행 환경 비교 (이 PC의 GPU는 VRAM이 한정적이므로 소형 또는 양자화 모델 중심)
- 검색 결합 방식 비교

확장 실험은 공식 비교 결과를 덮어쓰지 않는다.

## 8. 모델 및 기술 선정 실험 설계

### 8.1 실험 분리 원칙

여러 구성 요소를 동시에 변경하지 않는다.

| 실험 | 변경 변수 | 주요 고정 조건 |
|---|---|---|
| Embedding 비교 | Embedding 모델 | PDF, 추출 결과, 청킹, 질문, 검색 방식 |
| Sparse 비교 | Sparse 방식 | Embedding, 청킹, 질문 |
| Reranker 비교 | Reranker 모델 | 1차 검색 결과, 후보 수, 질문 |
| 생성 모델 비교 | Generation 모델 | 질문, 최종 문맥, 답변 지시사항 |
| 실행 환경 비교 | 실행 방식 및 하드웨어 | 모델 ID, 질문, 입력 문맥, 생성 설정 |

### 8.2 비교 평가 기준

검색 기술:

- Hit@k
- Recall@k
- 검색 처리시간
- 색인 및 임베딩 시간

생성 모델:

- 사실 (Judge)
- 조건 (Judge)
- Faithfulness
- 근거 및 인용 적절성
- answer / clarify / abstain 판단
- 응답시간
- 사용량 및 비용

운영:

- 오류 발생 여부
- 메모리 및 하드웨어 사용량
- 실행 안정성
- 재시도 및 Timeout 발생 여부

공식 필수 평가와 추가 지표의 구분은 `02_EVALUATION_PLAN.md` 및 `10_ADDITIONAL_METRICS.md`를 따른다.

### 8.3 실험 기록 양식

실험 기록의 기준 양식은 `03_EXPERIMENT_PLAN.md` §13이다. 모델·기술 후보 비교 실험은 그 양식(`experiment_id`, `objective`, `hypothesis`, `dataset`, `rag_config`, `baseline`, `changed_variables`, `controls`, `questions`, `metrics`, `results`, `interpretation`, `decision`, `versions`, `notes`)을 따르고, 아래 모델 전용 항목만 추가로 기록한다. 같은 내용을 별도 양식으로 중복 관리하지 않는다.

| 추가 항목 | 기록 내용 |
|---|---|
| component | Generation / Embedding / Sparse / Reranker |
| model_or_method | 모델 ID 또는 기술 이름 |
| license | 라이선스 및 이용 조건 (모델 카드에서 확인한 값) |
| runtime_environment | 실행 환경(하드웨어, 프레임워크, 양자화) |
| latency, usage, cost | 처리시간, 모델 사용량, 확인 가능한 비용 |
| decision_reason | 채택 / 보류 / 미채택의 이유 |

### 8.4 최종 채택 기준

1. 프로젝트 데이터에서 평가 결과가 적절한가?
2. 기존 후보보다 실제로 개선되는가?
3. 특정 질문 유형에서 심각한 성능 저하가 발생하지 않는가?
4. 실행 환경에서 안정적으로 구동되는가?
5. 속도 및 비용이 프로젝트 범위에서 감당 가능한가?
6. 라이선스 및 이용 조건에 문제가 없는가?
7. 유지보수 및 재실행이 가능한가?

속도나 비용만 개선되고 검색 또는 답변 품질이 크게 저하되는 경우 채택하지 않는다.

## 10. 라이선스 및 이용 조건 확인

[필수: 실제로 사용하는 모델·기술에 한함]

STEP 3에서 모델을 다운로드할 때, 실제로 채택한 모델과 기술(임베딩, 리랭커, 평가·생성 모델의 API 이용약관 등)의 공식 배포처와 모델 카드를 확인하고 결과를 `DECISIONS.md`에 기록한다. 확인하지 않은 라이선스는 적지 않는다. 확장 후보는 채택하기 전에 확인한다.

- 라이선스 종류

- API 이용약관 및 데이터 처리 조건
- 모델 버전에 따른 라이선스 차이
