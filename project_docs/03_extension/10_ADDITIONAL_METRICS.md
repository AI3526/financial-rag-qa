## 1. 문서 목적

본 문서는 기존 프로젝트 설계 문서에서 다루는 공식 평가 및 운영 지표 외에, RAG 시스템의 검색 품질, 답변 품질, 문서 처리, 응답 성능 및 운영 효율을 보다 세밀하게 분석하기 위한 추가 지표를 정리한다.

현재 프로젝트의 핵심 목적은 금융 PDF 기반 RAG 시스템에서 다양한 검색 및 답변 생성 기법을 실험하고, 실험 결과를 비교·분석하는 것이다.

기존 공식 과제의 필수 평가 지표를 대체하거나 변경하는 것이 아니라, 기존 평가 체계를 보완하고 개인 확장 실험의 분석 범위를 넓히는 것을 목적으로 한다.

### 1.1 기존 설계 문서와의 관계

본 문서는 기존 설계 문서와 별도로 관리하는 추가 지표 제안서다.

- 기존 `02_EVALUATION_PLAN.md`의 공식 평가 기준을 변경하지 않는다.
- 기존 `03_EXPERIMENT_PLAN.md`의 필수 비교 조건을 변경하지 않는다.
- 기존 `05_OBSERVABILITY_PLAN.md`의 공식 운영 지표를 변경하지 않는다.
- **본 문서는 확장 지표의 기준 목록이다.** PRD, 02, 03번 문서의 확장 지표 항목은 이 문서를 참조한다.
- 본 문서의 지표를 모두 필수 구현 대상으로 간주하지 않는다. 서비스 준비도 게이트(§11)는 과제의 필수 완료 조건이 아니다.
- 기존 설계 문서와 중복되거나 충돌하는 내용이 있으면 기존 문서와 함께 검토한 후 반영 여부를 결정한다.

Claude Code는 본 문서를 참고하여 전체 설계 문서를 검토할 수 있지만, 사용자 승인 없이 기존 설계 문서를 수정하거나 새로운 기능을 구현해서는 안 된다.

본 문서에서는 추가 지표를 다음과 같이 구분한다.

- **[필수 기록]** (이전 표기: 필수 기록 제안, 채택됨): 추가 평가 알고리즘을 구현하지 않더라도 색인 매니페스트에 단순 기록하는 정보. PDF별 페이지 수·추출 성공/실패·추출 시간, 청크 수, 평균 청크 크기, 색인 시간(§9.1)

## 2. 검색 품질 추가 지표

기존 공식 검색 평가는 Hit@k와 Recall@k를 사용한다.

두 지표는 참고 근거가 검색 결과에 포함되었는지를 확인하는 데 유용하지만, 검색된 결과 중 불필요한 문서가 얼마나 포함되었는지, 중요한 근거가 얼마나 높은 순위에 배치되었는지까지 충분히 설명하지는 못한다.

따라서 다음 지표를 추가로 검토한다.

**관련성 레이블 정의**: 평가 데이터의 `evidence_groups`에는 `book_id`, `page`, `quote`가 있으므로, 청크가 `(book_id, page)`로 참고 근거와 일치하면 관련 청크로 판정한다(같은 페이지의 다른 청크는 관련 근거 페이지 안의 청크로 취급하며, 필요하면 `quote`와의 텍스트 겹침으로 더 엄격하게 판정할 수 있다). 판정 규칙은 계산 전에 고정하고 기록한다. 이 청크 단위 지표는 문서 단위의 공식 Hit@k, Recall@k와 평가 단위가 다르므로 섞지 않는다. 등급이 있는 관련성(nDCG)은 별도 기준이 필요하다.

### 2.1 Precision@k [확장]

**정의**

검색된 상위 k개 청크 중 실제로 관련성이 있는 청크의 비율이다.

**계산 방법**

Precision@k = 상위 k개 검색 청크 중 관련 청크 수 / k

**측정 목적**

검색 결과에 불필요하거나 질문과 관련성이 낮은 청크가 얼마나 포함되어 있는지 확인한다.

**추가하는 이유**

Recall이 높더라도 관련 없는 청크가 지나치게 많이 검색되면 최종 문맥에 불필요한 정보가 들어갈 수 있다.

예를 들어 정답 근거를 모두 검색했더라도 상위 10개 중 실제 관련 청크가 2개뿐이라면, 검색 결과의 효율성은 낮을 수 있다.

Precision@k를 통해 검색 결과의 정확성과 불필요한 검색 결과의 비율을 추가로 분석할 수 있다.

**측정 시 주의사항**

- 관련 청크를 판정할 기준이 필요하다.
- 문서 단위의 공식 Hit@k 및 Recall@k와 청크 단위 Precision@k의 평가 단위가 다를 수 있으므로 구분한다.
- 검색 결과가 k개 미만인 경우 계산 기준을 사전에 정한다.
- 기존 공식 지표와 혼합하거나 대체하지 않는다.

### 2.2 MRR (Mean Reciprocal Rank) [확장]

**정의**

각 질문에서 첫 번째 관련 근거가 검색 결과의 몇 번째 순위에 등장하는지 측정하고, 여러 질문의 결과를 평균한 지표다.

**계산 방법**

질문별 Reciprocal Rank:

RR = 1 / 첫 번째 관련 근거의 순위

MRR = 질문별 RR의 평균

첫 번째 관련 근거가 검색되지 않으면 해당 질문의 RR은 0으로 처리한다.

**측정 목적**

중요한 근거가 검색 결과의 상위에 배치되는지를 확인한다.

**추가하는 이유**

Recall은 관련 근거를 찾았는지 확인하지만, 검색 순위가 얼마나 좋은지는 직접 보여주지 않는다.

예를 들어 다음 두 검색 결과는 Recall 측면에서 모두 관련 근거를 찾은 것으로 평가될 수 있다.

- 검색 A: 첫 번째 정답 근거가 1위
- 검색 B: 첫 번째 정답 근거가 8위

하지만 실제 RAG 시스템에서는 상위 청크만 최종 문맥에 포함되므로 검색 A가 더 유리하다.

MRR을 활용하면 Dense Retrieval, Hybrid Retrieval, Reranking이 관련 근거를 상위 순위로 끌어올리는 데 얼마나 효과적인지 비교할 수 있다.

**측정 시 주의사항**

- 관련 근거의 판정 기준을 사전에 정한다.
- 기존 평가에서 사용하는 참고 근거 목록과 일관성을 유지한다.
- 첫 번째 관련 근거의 순위는 청크 순위를 기준으로 한다.
- 동일 문서의 여러 청크를 어떻게 판정할지 평가 규칙을 명확히 한다.

### 2.3 nDCG@k (Normalized Discounted Cumulative Gain) [확장]

**정의**

검색 결과의 관련성 정도와 검색 순위를 함께 고려하는 지표다.

관련성이 높은 청크가 상위에 배치될수록 높은 점수를 받는다.

**계산 방법**

일반적인 DCG 계산식:

DCG@k = Σ(i=1~k) [(2^rel_i - 1) / log₂(i + 1)]

nDCG@k = DCG@k / IDCG@k

- rel_i: i번째 검색 결과의 관련성 점수
- IDCG: 이상적인 검색 순서에서 계산한 DCG

관련성 점수는 프로젝트의 평가 기준에 따라 정의한다.

**측정 목적**

검색 결과의 순위와 관련성 수준을 동시에 평가한다.

**추가하는 이유**

모든 관련 청크가 동일한 중요도를 갖는 것은 아니다.

예를 들어 어떤 청크는 질문의 핵심 수치를 직접 포함하고, 다른 청크는 관련 배경 설명만 제공할 수 있다.

MRR은 첫 번째 관련 결과의 위치에 집중하지만, nDCG는 상위 검색 결과 전체의 관련성 수준과 순서를 평가할 수 있다.

따라서 Reranking 적용 전후에 검색 결과의 순위 품질이 얼마나 개선되었는지 분석하는 데 유용하다.

**측정 시 주의사항**

- 청크별 관련성 등급을 정의해야 한다.
- 관련성 등급을 평가하는 기준이 없으면 정확한 비교가 어렵다.
- 초기 구현에서 별도의 등급 평가 체계를 만들 필요는 없다.
- 평가 데이터가 충분하고 관련성 등급을 신뢰할 수 있을 때 추가한다.

---

### 2.4 MAP (Mean Average Precision) [확장]

각 질문에서 관련 청크가 나타나는 순위마다의 Precision을 평균(Average Precision)하고 질문들에 대해 평균한 지표이다. 관련 근거가 여러 개일 때 검색 순위가 전반적으로 적절한지 확인한다. 관련성 판정 기준은 위 정의를 따르며 MRR과 함께 보면 순위 개선 효과를 설명하기 쉽다.

### 2.5 Context Precision / Context Recall [확장]

RAGAS의 지표로, Context Precision은 검색된 최종 문맥 중 질문에 유용한 문맥의 비율과 순서를, Context Recall은 참고 정답에 필요한 정보가 최종 문맥에 포함된 정도를 평가한다. 평가 LLM 호출이 필요하며(`run_type = scoring`), 참고 정답은 평가 단계에서만 사용한다. 공식 지표(Hit@k, Recall@k)를 대체하지 않는다.

## 3. 답변 및 인용 품질 추가 지표

기존 공식 답변 평가는 RAGAS Faithfulness와 LLM-as-a-Judge의 사실, 조건, 근거, 판단 항목을 사용한다.

추가 지표는 답변에 포함된 출처가 실제 주장을 뒷받침하는지, 중요한 주장에 출처가 충분히 연결되었는지 등을 더 구체적으로 분석하기 위한 것이다.

### 3.1 Citation Precision [확장]

**정의**

답변에서 인용한 출처 중 실제로 해당 주장을 뒷받침하는 출처의 비율이다.

**계산 방법**

Citation Precision = 실제 주장을 뒷받침하는 인용 수 / 전체 인용 수

**측정 목적**

답변에 표시된 문서명과 페이지 번호가 실제로 해당 주장의 근거가 되는지 확인한다.

**추가하는 이유**

출처가 표시되어 있다는 사실만으로 인용이 정확하다고 볼 수는 없다.

예를 들어 답변에서 매출액을 인용하면서 해당 페이지에는 영업이익만 기록되어 있다면, 출처가 존재하더라도 해당 주장을 뒷받침하지 못한다.

Citation Precision을 통해 다음과 같은 문제를 확인할 수 있다.

- 잘못된 페이지 인용
- 관련 없는 문서 인용
- 주장과 출처 내용의 불일치
- 다른 회사나 다른 사업부문의 자료를 잘못 인용
- 기간이나 정정 범위가 다른 자료를 인용

**측정 시 주의사항**

- 하나의 출처가 여러 주장을 뒷받침할 수 있다.
- 인용 단위와 주장 단위를 어떻게 연결할지 정해야 한다.
- 답변의 모든 문장에 인용이 필요한 것은 아니다.
- 실제 주장을 뒷받침하는지를 원문과 대조하는 것이 중요하다.

### 3.2 Citation Coverage [확장]

**정의**

답변에서 출처가 필요한 주요 주장 중 실제 근거가 연결된 주장의 비율이다.

**계산 방법**

Citation Coverage = 근거가 연결된 주요 주장 수 / 출처가 필요한 전체 주요 주장 수

**측정 목적**

중요한 사실이나 수치가 출처 없이 제시되는 문제를 확인한다.

**추가하는 이유**

Citation Precision이 인용한 출처의 정확성을 평가한다면, Citation Coverage는 출처가 필요한 주장에 충분히 인용이 제공되었는지 평가한다.

예를 들어 답변에 중요한 수치와 판단이 5개 포함되어 있는데 그중 2개에만 출처가 연결되었다면 Citation Coverage가 낮다.

특히 금융 문서에서는 다음 내용의 출처 연결 여부가 중요하다.

- 매출액 및 영업이익
- 전년 동기 대비 증감
- 회사 및 사업부문
- 제품 및 지역
- 적용 기간
- 정정 전후 수치
- 거래 및 회계 처리 기준

**측정 시 주의사항**

- 모든 문장에 출처를 요구하지 않는다.
- 출처가 필요한 주요 사실과 수치 중심으로 평가한다.
- 근거가 필요한 주장과 일반적인 설명을 구분한다.
- Citation Precision과 함께 확인해야 인용의 정확성과 충분성을 모두 분석할 수 있다.

### 3.3 Answer Relevancy [확장]

**정의**

생성된 답변이 사용자의 질문에 얼마나 직접적이고 적절하게 대응하는지를 평가한다.

**측정 목적**

답변이 사실적으로 정확하더라도 질문의 핵심을 놓치거나 불필요한 설명만 제공하는 문제를 확인한다.

**추가하는 이유**

Faithfulness는 답변이 검색 문맥에 충실한지를 평가하지만, 검색 문맥에 충실한 답변이 반드시 질문에 적절한 답변인 것은 아니다.

예를 들어 매출과 영업이익의 증가 여부를 물었는데 기업의 일반적인 사업 개요만 길게 설명한다면, 검색 문맥에 없는 내용을 만들어내지는 않았더라도 질문에 적절하게 답했다고 보기 어렵다.

**측정 시 주의사항**

- 기존 Judge 평가의 사실 및 판단 항목과 일부 중복될 수 있다.
- 별도의 자동 평가 지표를 반드시 구현할 필요는 없다.
- 필요하면 별도 분석 항목으로 활용한다.

### 3.4 Answer Correctness / Factual Correctness [확장]

생성 답변을 참고 정답과 비교해 사실이 얼마나 일치하는지 평가한다(RAGAS의 Factual Correctness 등, 과제 원본의 도전 실습 A가 언급하는 지표). 적용 대상(`expected_action = answer`인 질문), 입력(질문, 답변, `reference_answer`), 계산 기준을 정한 뒤 기존 비교표에 함께 적는다. 평가 LLM 호출이 필요하며 기존 Judge의 사실 항목과 일부 중복될 수 있다. 참고 정답은 서비스 입력에 넣지 않는다.

### 3.5 Abstention Accuracy [기존 Judge 판단 항목 활용]

**정의**

답변, 추가 확인 요청, 보류 중 어떤 행동을 선택했는지가 질문과 실제 근거에 적절한지 평가한다.

**측정 목적**

근거가 부족한 상황에서 잘못된 답변을 생성하거나, 답변 가능한 상황에서 불필요하게 보류하는 문제를 확인한다.

**추가하는 이유**

RAG 서비스는 단순히 정답을 많이 생성하는 것만으로 충분하지 않다.

필수 조건이 누락되었다면 추가로 질문해야 하고, 근거가 부족하다면 답변을 보류해야 한다.

반대로 충분한 근거가 있는데도 무조건 보류한다면 서비스의 유용성이 떨어진다.

**측정 시 주의사항**

- 기존 공식 LLM-as-a-Judge의 판단 항목을 활용한다.
- 별도 점수 체계를 만들지 않는다.
- API 상태 이름만으로 정확성을 판정하지 않는다.
- 실제 답변 범위와 보류 이유가 기대 동작에 맞는지 평가한다.
- 기존 expected_action의 answer, clarify, abstain 구분과 일관성을 유지한다.

## 4. 응답시간 및 지연시간 추가 지표

기존 공식 운영 지표는 전체 API 응답시간이다.

전체 응답시간 평균만으로는 일부 요청이 지나치게 느린 현상이나 응답시간의 분포를 파악하기 어렵다.

따라서 다음 지표를 추가로 검토한다.

### 4.1 P50 Latency [확장]

**정의**

전체 요청의 응답시간을 정렬했을 때 중앙에 위치하는 값이다.

전체 요청 중 약 50%가 해당 시간 이내에 완료된다.

**측정 목적**

일반적인 사용자가 경험하는 대표적인 응답시간을 파악한다.

**추가하는 이유**

평균은 일부 매우 느린 요청의 영향을 받을 수 있다.

P50을 함께 측정하면 일반적인 요청의 응답시간을 보다 직관적으로 확인할 수 있다.

### 4.2 P95 Latency [확장]

**정의**

전체 요청의 95%가 해당 시간 이내에 완료되는 응답시간이다.

**측정 목적**

일반적인 요청보다 느린 요청이 어느 정도의 지연을 경험하는지 파악한다.

**추가하는 이유**

평균 응답시간이 짧더라도 일부 요청이 지나치게 오래 걸릴 수 있다.

예를 들어 다음과 같은 결과가 나왔다고 가정한다.

- 평균 응답시간: 3초
- P50: 2초
- P95: 9초

대부분의 요청은 빠르게 처리되지만 일부 요청은 9초까지 기다려야 할 수 있다.

P95는 이런 지연 문제를 파악하는 데 유용하다.

### 4.3 P99 Latency [확장]

**정의**

전체 요청의 99%가 해당 시간 이내에 완료되는 응답시간이다.

**측정 목적**

매우 느린 요청이 발생하는 극단적인 지연 구간을 확인한다.

**추가하는 이유**

사용자가 많거나 요청량이 증가하는 환경에서는 일부 요청의 심각한 지연이 전체 서비스 경험에 영향을 줄 수 있다.

P99를 활용하면 극단적인 지연 문제를 분석할 수 있다.

**측정 시 주의사항**

- P50, P95, P99는 모두 동일한 시간 측정 기준을 사용한다.
- 전체 API 응답시간을 기준으로 계산한다.
- 정상 요청과 실패 요청의 포함 여부를 명확하게 구분한다.
- 요청 수가 적으면 P99는 통계적으로 불안정할 수 있다.
- 초기에는 P50과 P95를 우선 측정하고, P99는 충분한 요청이 쌓였을 때 추가한다.

---

### 4.4 스트리밍 지표: TTFT, TTLT, TPS [확장]

스트리밍 응답을 사용할 때만 정확히 측정할 수 있으므로 필수 구현 이후 확장 실험에서 진행한다. 이 절이 정의의 단일 기준이다(`05_OBSERVABILITY_PLAN.md` §7.4는 측정 방법 요약).

| 지표 | 정의 |
|---|---|
| `ttft_e2e` | 사용자 요청 수신부터 첫 번째 출력 토큰 수신까지의 시간. 질문 임베딩, 검색, 재정렬, 프롬프트 구성, 첫 토큰 생성 대기 포함 |
| `ttft_model` | 모델 호출 시작부터 첫 번째 출력 토큰 수신까지의 시간 |
| `ttlt_e2e` | 사용자 요청 수신부터 마지막 출력 토큰 수신까지의 시간 (용어는 TTLT 하나로 통일. 이전의 TTLS는 사용하지 않음) |
| `ttlt_model` | 모델 호출 시작부터 마지막 출력 토큰 수신까지의 시간 |
| `tps` | 첫 토큰 이후 마지막 토큰까지의 생성 구간에서 초당 생성된 토큰 수 = (전체 출력 토큰 수 − 첫 토큰 수) / (마지막 토큰 수신 시각 − 첫 토큰 수신 시각) |

- 스트리밍을 사용하지 않으면 TTFT와 TTLT를 추정하지 않고 측정 불가로 기록한다.
- 토큰 수를 정확히 확인할 수 없으면 추정치인지 구분해 기록한다. TPS는 글자 수로 환산하지 않는다.
- 전체 API 응답시간(필수 운영 지표)과 별도로 기록하고, 서비스 호출과 평가 호출을 구분한다.
- 답변 길이를 짧은 답변(1~2문장) / 일반 답변(여러 문장) / 긴 답변으로 나누어 집계한다.

## 5. 처리량 및 동시성 추가 지표

기존 실험 계획에는 Batch, Concurrent, Async I/O 등의 성능 실험이 포함되어 있다.

이러한 실험의 결과를 구체적으로 비교하기 위해 다음 지표를 추가한다.

### 5.1 Throughput (RPS: Requests Per Second) [확장]

**정의**

초당 정상적으로 처리한 요청 수다.

**계산 방법**

RPS = 측정 구간에서 처리 완료된 요청 수 / 측정 시간(초)

**측정 목적**

시스템이 일정 시간 동안 얼마나 많은 요청을 처리할 수 있는지 확인한다.

**추가하는 이유**

응답시간이 짧다고 해서 반드시 처리량이 높은 것은 아니다.

동시 요청이 늘어났을 때 처리 능력이 어떻게 변하는지 확인할 수 있다.

### 5.2 Concurrent Requests [확장]

**정의**

특정 시점에 동시에 처리 중인 요청 수다.

**측정 목적**

동시 요청 수에 따라 응답시간과 오류율이 어떻게 변하는지 확인한다.

**추가하는 이유**

단일 요청에서는 문제가 없더라도 여러 요청이 동시에 들어오면 API, 검색, 모델 호출 등의 병목이 발생할 수 있다.

동시 요청 수를 기록하면 성능 저하가 발생하는 조건을 분석할 수 있다.

### 5.3 Queue Wait Time [확장]

**정의**

요청이 접수된 시점부터 실제 처리 작업을 시작할 때까지 대기한 시간이다.

**측정 목적**

요청 처리 자체가 느린 것인지, 처리 시작 전 대기가 발생하는 것인지 구분한다.

**추가하는 이유**

동시 요청이 증가하면 모델 호출 제한, 작업자 수, 내부 처리 대기 등으로 인해 요청이 처리되기 전부터 지연될 수 있다.

전체 응답시간만으로는 이러한 대기 시간을 별도로 파악하기 어렵다.

**측정 시 주의사항**

별도의 작업 큐나 대기 구조를 도입한 경우에 특히 유용하다. 초기 구조에서 별도 대기 구간이 없다면 구현할 필요가 없다.

### 5.4 Timeout Rate [확장]

**정의**

전체 측정 요청 중 Timeout으로 종료된 요청의 비율이다.

**계산 방법**

Timeout Rate = Timeout 발생 요청 수 / 전체 측정 요청 수 × 100

**측정 목적**

처리 제한 시간 내에 완료하지 못하는 요청이 얼마나 발생하는지 확인한다.

**추가하는 이유**

전체 오류율만으로는 Timeout이 주요 문제인지 파악하기 어렵다.

검색 지연, 모델 응답 지연, 외부 API 문제 등 Timeout의 발생 원인을 별도로 분석할 수 있다.

**측정 시 주의사항**

- 재시도 전후의 Timeout을 구분해 기록한다.
- 최종 요청 실패와 개별 시도 실패를 혼동하지 않는다.
- 기존 공식 오류율 계산 규칙을 변경하지 않는다.
- 일반 평가 요청과 모의 오류 및 보안 비교 요청의 구분을 유지한다.

## 6. 문서 추출 및 색인 추가 지표

RAG 시스템의 검색 품질은 PDF에서 텍스트와 표를 얼마나 정확하게 추출하고, 이를 어떻게 청크로 분리하여 색인했는지에 영향을 받는다.

기존 설계에서는 문서 처리와 색인 과정을 다루지만, 처리 결과를 비교할 수 있는 지표를 보다 명확하게 기록할 필요가 있다.

### 6.1 PDF Extraction Success Rate [필수 기록 + 비율 계산은 확장]

PDF별 추출 성공/실패는 `documents.jsonl`에 필수로 기록한다(과제 원본: 빠진 문서와 처리 실패를 기록). 아래 비율의 집계와 비교는 확장이다.

**정의**

전체 PDF 중 텍스트 추출이 정상적으로 완료된 PDF의 비율이다.

**계산 방법**

PDF Extraction Success Rate = 정상 추출된 PDF 수 / 전체 PDF 수 × 100

**측정 목적**

PDF 추출 단계에서 발생하는 실패를 확인한다.

**추가하는 이유**

PDF 파일이 정상적으로 열리더라도 텍스트가 제대로 추출되지 않을 수 있다.

특히 다음과 같은 문서에서 문제가 발생할 수 있다.

- 이미지로 저장된 PDF
- 표와 숫자가 많은 PDF
- 복잡한 레이아웃의 PDF
- 페이지 번호와 본문 위치가 일치하지 않는 PDF
- 글자 인코딩이나 폰트 문제가 있는 PDF

추출 실패가 발생하면 검색 품질이 낮아지는 원인이 될 수 있으므로 문서 처리 단계의 안정성을 확인할 필요가 있다.

### 6.2 Extraction Time [필수 기록 + 방식 간 비교는 확장]

PDF별 추출 시간과 페이지 수는 `documents.jsonl`에 필수로 기록한다. 추출 방식 간 속도 비교는 확장이다.

**정의**

PDF 파일 또는 페이지의 텍스트와 구조를 추출하는 데 걸린 시간이다.

**측정 목적**

문서 추출 과정의 처리 속도를 확인한다.

**추가하는 이유**

문서 수와 페이지 수가 증가하면 추출 시간이 길어질 수 있다.

PDF 추출 라이브러리나 처리 방식을 변경했을 때 속도 차이를 비교할 수 있다.

**측정 시 주의사항**

- 파일별 추출 시간과 전체 추출 시간을 구분할 수 있다.
- 문서 페이지 수에 따라 처리 시간이 달라질 수 있으므로 페이지 수도 함께 기록한다.
- 추출 품질을 확인하지 않고 속도만으로 방식을 선택하지 않는다.

### 6.3 Chunk Count [필수 기록]

**정의**

문서 또는 데이터셋에서 생성된 청크의 총개수다.

**측정 목적**

청킹 설정에 따라 생성되는 청크 수가 어떻게 달라지는지 확인한다.

**추가하는 이유**

청크 크기, 청크 중첩, 분할 방식이 달라지면 전체 청크 수가 달라진다.

청크 수는 임베딩 처리량, 벡터 저장 공간, 검색 결과, 색인 시간 등에 영향을 줄 수 있다.

따라서 청킹 실험을 진행할 때 결과를 비교하기 위한 기본 정보로 기록한다.

**측정 시 주의사항**

- 데이터셋별 청크 수를 기록한다.
- 문서별 청크 수도 필요하면 확인할 수 있어야 한다.
- 청킹 설정 및 버전과 함께 기록한다.

### 6.4 Average Chunk Size [필수 기록]

**정의**

생성된 청크의 평균 크기다.

**측정 목적**

청크 크기 설정에 따른 데이터 구조의 차이를 확인한다.

**추가하는 이유**

청크가 지나치게 작으면 문맥이 분리되어 의미가 손실될 수 있다.

반대로 청크가 지나치게 크면 검색 결과에 불필요한 내용이 포함되고, 최종 문맥의 토큰 사용량이 증가할 수 있다.

평균 청크 크기를 기록하면 검색 품질, 문맥 길이, 토큰 사용량의 변화를 함께 분석할 수 있다.

**측정 시 주의사항**

- 가능하면 토큰 기준 평균 크기를 기록한다.
- 문자 수 기준 크기를 사용한다면 토큰 기준과 구분한다.
- 평균뿐 아니라 필요할 경우 최소·최대 크기도 확인한다.
- 청크 크기 산정 방식과 tokenizer를 기록한다.

### 6.5 Indexing Time [필수 기록]

**정의**

문서에서 생성한 청크를 임베딩하고 벡터 저장소에 등록하는 데 걸린 시간이다.

**측정 목적**

문서 색인 과정의 처리 속도를 확인한다.

**추가하는 이유**

PDF 추출, 청킹, 임베딩, 벡터 저장 과정은 각각 다른 시간이 소요된다.

전체 색인 시간만 기록하면 어느 단계에서 병목이 발생하는지 파악하기 어렵다.

색인 시간을 기록하면 다음을 비교할 수 있다.

- 문서 수와 페이지 수 증가에 따른 처리 시간
- 청킹 방식 변경 전후
- 임베딩 모델 변경 전후
- 배치 크기 변경 전후
- 색인 처리 방식 변경 전후

**측정 시 주의사항**

- 가능하면 PDF 추출, 청킹, 임베딩, 벡터 저장 시간을 구분한다.
- 전체 색인 시간과 단계별 시간을 구분한다.
- 기존 데이터 삭제 및 재색인 시간과 최초 색인 시간을 구분할 수 있다면 기록한다.

### 6.6 Embedding Failure Rate [확장]

**정의**

임베딩 요청 중 실패한 요청의 비율이다.

**계산 방법**

Embedding Failure Rate = 임베딩 실패 요청 수 / 전체 임베딩 요청 수 × 100

**측정 목적**

임베딩 과정에서 발생하는 오류를 확인한다.

**추가하는 이유**

임베딩 API의 오류, 요청 제한, 입력 크기 제한, 네트워크 문제 등으로 일부 청크가 임베딩되지 않을 수 있다.

일부 청크의 색인이 누락되면 해당 정보가 검색되지 않을 수 있으므로 색인 완료 여부를 확인하는 데 유용하다.

**측정 시 주의사항**

- 재시도 전후의 실패를 구분한다.
- 최종적으로 색인에 성공하지 못한 청크 수를 확인한다.
- 일부 청크만 실패한 경우 전체 색인 성공으로 잘못 처리하지 않는다.

## 7. 캐시 관련 추가 지표

Redis를 도입하는 경우 캐시의 효율과 잘못된 재사용 가능성을 함께 확인한다.

Redis는 본 프로젝트에서 Qdrant를 대체하는 벡터 저장소가 아니라 선택적인 캐시 구성 요소다.

### 7.1 Cache Hit Rate [확장]

**정의**

캐시를 조회한 전체 요청 중 캐시에서 결과를 찾은 비율이다.

**계산 방법**

Cache Hit Rate = Cache Hit 수 / 전체 캐시 조회 수 × 100

**측정 목적**

캐시가 얼마나 자주 재사용되는지 확인한다.

**추가하는 이유**

캐시를 도입하면 검색, 임베딩 또는 생성 호출을 줄일 수 있다.

Cache Hit Rate를 통해 캐시가 실제로 얼마나 활용되는지 파악할 수 있다.

### 7.2 Cache Miss Rate [확장]

**정의**

캐시를 조회했지만 저장된 결과가 없어 원래 처리 과정을 수행한 비율이다.

**계산 방법**

Cache Miss Rate = Cache Miss 수 / 전체 캐시 조회 수 × 100

**측정 목적**

캐시를 활용하지 못하고 원래 처리 과정을 다시 수행하는 비율을 확인한다.

**추가하는 이유**

Cache Hit Rate와 함께 확인하면 캐시의 활용 정도를 파악할 수 있다.

### 7.3 잘못된 캐시 재사용 비율 [확장]

**정의**

질문이나 적용 조건이 달라 캐시 결과를 재사용하면 안 되는 상황에서 잘못된 캐시 결과가 재사용된 비율이다.

**측정 목적**

캐시로 인한 답변 오류와 문맥 오염을 확인한다.

**추가하는 이유**

금융 문서에서는 질문이 비슷해 보여도 회사, 기간, 사업부문, 제품, 지역, 정정본 여부 등에 따라 정답이 달라질 수 있다.

예를 들어 다음 두 질문은 표면적으로 유사하더라도 같은 캐시 결과를 무조건 재사용해서는 안 된다.

- 해온솔루션의 2026년 상반기 매출은 얼마인가?
- 해온소재의 2026년 상반기 매출은 얼마인가?

잘못된 캐시 재사용은 응답시간을 줄이더라도 답변 정확성을 크게 떨어뜨릴 수 있다.

### 7.4 오래된 캐시 재사용 비율 [확장]

**정의**

문서나 데이터가 변경되었는데도 이전 버전의 캐시 결과가 재사용된 비율이다.

**측정 목적**

문서 변경 및 정정 이후 오래된 결과가 반환되는 문제를 확인한다.

**추가하는 이유**

금융 문서는 정정본, 최신 공시, 적용 기간 변경 등에 따라 내용이 달라질 수 있다.

따라서 캐시를 사용할 때는 문서 버전과 색인 버전 등을 고려해야 한다.

### 7.5 캐시 적용 전후 비교 항목 [확장]

캐시를 적용할 때는 Cache Hit Rate만으로 효과를 판단하지 않는다.

다음 항목을 함께 비교한다.

- 응답시간
- 검색 호출 수
- 임베딩 호출 수
- 모델 호출 수
- Input/Output Token
- 확인 가능한 비용
- 잘못된 캐시 재사용 사례
- 오래된 캐시 재사용 사례

캐시 적용으로 속도나 비용이 개선되더라도 답변 품질이나 근거 정확성이 저하되면 채택하지 않는다.

## 9. 지표 측정 및 구현 우선순위 제안

모든 지표를 한꺼번에 구현하지 않는다.

프로젝트의 기본 기능을 완성하고 공식 과제 평가를 수행하는 데 지장이 없도록 단계별로 추가한다.

### 9.1 초기 구현 단계 [필수 기록]

기존 구현에 큰 부담을 주지 않으면서 이후 실험 분석과 "빠진 문서·처리 실패 기록"(과제 원본 요구)에 필요한 정보를 기록한다. 지표 계산 알고리즘이 아니라 색인 매니페스트의 단순 기록이다.

- PDF별 페이지 수, 추출 성공/실패, 추출 시간 (§6.1, §6.2의 기록 부분)
- Chunk Count
- Average Chunk Size
- Indexing Time

위 항목은 문서 처리 및 청킹 실험의 기본 정보를 확보하기 위한 것이다.
### 9.2 기본 평가 확장 단계

**[확장]**

기존 평가 결과를 활용할 수 있는 지표부터 추가한다.

- MRR
- P50 Latency
- P95 Latency

MRR은 검색 순위 개선 여부를 확인하고, P50/P95는 평균 응답시간만으로 파악하기 어려운 지연시간 분포를 분석하는 데 활용한다.

### 9.3 검색 및 답변 품질 확장 단계

**[확장]**

- Precision@k
- nDCG@k
- Citation Precision
- Citation Coverage
- Answer Relevancy
- Answer Correctness / Factual Correctness
- MAP, Context Precision / Context Recall

관련성 판정 기준이나 인용 평가 기준을 추가로 정의해야 하므로, 초기 구현보다 후순위로 진행한다.

### 9.4 운영 성능 확장 단계

**[확장]**

- P99 Latency
- Throughput (RPS)
- Concurrent Requests
- Queue Wait Time
- Timeout Rate

동시 요청 및 부하 실험을 진행할 때 측정한다.

### 9.5 문서 처리 확장 단계

**[확장]**

- PDF Extraction Success Rate
- Extraction Time
- Embedding Failure Rate

PDF 추출 방식, 임베딩 모델 및 색인 처리 방식을 비교할 때 활용한다.

### 9.6 캐시 실험 단계

**[확장]**

- Cache Hit Rate
- Cache Miss Rate
- 잘못된 캐시 재사용 비율
- 오래된 캐시 재사용 비율

Redis를 실제 도입하고 캐시 실험을 수행할 때 측정한다. Redis를 도입하지 않는다면 해당 지표는 구현하지 않는다.

## 10. 지표 측정 공통 원칙

### 10.1 공식 평가와 확장 평가 구분

- 기존 공식 평가 지표를 유지한다.
- 추가 지표는 별도 확장 지표로 구분한다.
- 공식 과제 결과와 개인 확장 실험 결과를 혼합하지 않는다.
- 추가 지표의 측정 실패가 공식 평가 결과를 임의로 변경하지 않도록 한다.

### 10.2 비교 조건 통제

RAG 방식별 비교를 수행할 때는 기존 비교 조건을 유지한다.

- 동일 PDF
- 동일 문서 추출 결과
- 동일 청킹 설정
- 동일 임베딩 모델
- 동일 생성 모델
- 동일 답변 프롬프트
- 동일 생성 설정
- 동일 최종 문맥 토큰 한도
- 동일 평가 질문
- 동일 평가 기준

추가 지표를 적용하더라도 기존 비교 조건을 임의로 변경하지 않는다.

### 10.3 측정값 누락 및 오류 처리

- 측정하지 못한 값을 0으로 임의 기록하지 않는다.
- 측정 불가, 평가 불가, 해당 없음, 실제 0을 구분한다.
- 추정값은 실제 측정값과 구분한다.
- 지표 계산 방식과 측정 단위를 기록한다.
- 평가 LLM의 시간 및 사용량은 서비스 답변 생성과 구분한다.

### 10.4 품질과 성능의 균형

속도나 비용이 개선되었다는 이유만으로 새로운 방식을 채택하지 않는다.

다음 항목을 함께 검토한다.

- 검색 품질
- 답변 정확성
- 근거 및 인용 정확성
- 답변 보류 및 추가 확인의 적절성
- 응답시간
- 오류율
- 토큰 사용량
- 비용
- 시스템 복잡성

품질이 저하되는 경우 성능 개선만으로 채택하지 않는다.

## 11. 서비스 준비도 게이트 [확장]

실제 서비스 단계(Intermediate/Advanced 확장 포함)에서 "서비스에 사용할 수 있는 수준인가"를 판단하기 위한 합격 기준 초안이다. 이전에는 `12_ACCEPTANCE_CRITERIA.md`에 있었으나, 과제 원본에는 합격선이 없고(운영 지표 개선·통과 기준은 필수가 아님) 현재 평가 표본(60문항)으로는 통계적으로 검증할 수 없어 필수 판정에서 분리해 이곳으로 옮겼다.

- 이 게이트는 **과제 필수 완료 조건이 아니다.** Basic 공식 비교에서는 미달해도 최종 구성을 선택하고 한계로 기록한다(`12_ACCEPTANCE_CRITERIA.md`).
- 아래 수치는 임의로 정한 초안이다. 서비스 단계 진입 시 근거(사용 목적, 데이터 규모, 비용 한도)를 검토해 확정하고, 확정 후에는 결과를 보고 사후 조정하지 않는다. 변경은 새 기준 버전으로 기록한다.

### 11.1 품질 기준 (초안)

Judge 항목의 점수는 평가 대상(`evaluated`) 중 1의 비율(충족률)이며, 해당 없음과 평가 불가는 제외한다(`09_DATA_SCHEMA.md`).

| 지표 | 최소 기준 | 비고 |
|---|---:|---|
| Hit@k | 0.80 이상 | k는 동결한 최종 청크 수 |
| Recall@k | 0.80 이상 | |
| RAGAS Faithfulness | 0.90 이상 | |
| Judge 사실 | 0.90 이상 | |
| Judge 조건 | 0.95 이상 | |
| Judge 근거 | 0.90 이상 | |
| Judge 판단 | 0.95 이상 | |

평균이 기준을 넘어도 핵심 지표(사실, 조건, 판단) 하나가 미달이면 통과로 보지 않으며, 다른 지표의 상승으로 상쇄하지 않는다. 중대 오류(`12_ACCEPTANCE_CRITERIA.md` §5의 분류. 서비스 단계에서는 0건을 요구)는 평균으로 상쇄하지 않는다.

### 11.2 RAG 방식 간 품질 동등성 (초안)

- 실용적 동등성 허용 범위: 절대 점수 차이 ±0.03
- 같은 질문의 방식별 결과를 짝지어 질문별 차이의 95% 신뢰구간을 구하고, 구간 전체가 ±0.03 안에 들어올 때만 동등성이 입증된 것으로 본다. 평균 차이가 0.03 이내라는 이유만으로 동등하다고 하지 않는다.
- 이 검정은 표본이 충분할 때만 의미가 있다. 60문항 수준에서는 신뢰구간 폭이 허용 범위보다 넓어 대부분 "입증되지 않음"이 된다.

### 11.3 응답 성능 기준 (초안, 스트리밍 필요)

TTFT/TTLT/TPS 정의는 §4.4를 따른다. 사용자 체감 기준은 `ttft_e2e`, `ttlt_e2e`이다.

| 지표 | 최소 기준 | 목표 |
|---|---:|---:|
| TTFT p95 | 5초 이하 | 3초 이하 |
| 짧은 답변(1~2문장) TTLT p95 | 10초 이하 | 5~7초 |
| 일반 답변(여러 문장) TTLT p95 | 20초 이하 | 15초 이하 |
| TPS | 측정 응답의 90% 이상이 20 이상 | 30 이상 |

TPS는 토큰화 방식의 영향을 받으므로 글자 수로 환산하지 않고 같은 모델·토크나이저로 비교한다. 긴 답변에는 짧은 답변 기준을 적용하지 않고 출력 길이와 완료 시간을 함께 기록한다. 모델 제공처의 속도에 좌우되는 지표이므로 통과 여부를 해석할 때 이를 고려한다.

### 11.4 운영 안정성 기준 (초안)

| 지표 | 최소 기준 |
|---|---:|
| 요청 오류율 (시스템 오류 / 전체 일반 요청) | 1% 이하 |
| 요청 성공률 | 99% 이상 |

오류율 1% 이하를 판정하려면 후보별 최소 300회의 측정 요청을 권장한다. 이에 미달하면 수치는 보고하되 안정성 통과를 확정하지 않고 "잠정"으로 판정한다. 성능 측정은 같은 실행 환경, 동시 요청 수, 네트워크, 모델과 생성 설정에서 수행하며 후보별 측정 요청 수와 실패 건수를 함께 기록한다.

### 11.5 비용 평가

비용은 성공한 답변 1건당 비용으로 비교한다(임베딩, 외부 검색·재정렬 비용, LLM 입력·출력 토큰 비용, 전체 요청 비용). 확정된 서비스 사용량과 예산 상한이 없으므로 절대 비용 한도는 기준으로 정하지 않고, 품질·안정성 기준을 통과한 후보 사이에서 상대 비교한다. 단가를 확인할 수 없으면 토큰만 비교한다.

### 11.6 Holdout 검증

- 공식 비교에 사용하지 않은 별도 질문 집합(`expansion_validation` 12문항과 자체 추가 질문)으로 최종 후보를 검증한다. `expansion_validation`은 전부 `answer`이므로 보류·되묻기 검증에는 clarify·abstain 자체 질문을 추가해야 한다.
- 같은 품질 기준과 중대 오류 분류 규칙을 적용하고, 사전에 지정한 중요 질문 집합에서 중대 오류가 0건이어야 통과로 본다. 유한한 질문에서 0건이라는 사실이 실제 서비스에서 0이라는 뜻은 아니다.
- 공개된 정답을 사용하는 결과는 비공개 테스트 성능으로 표현하지 않는다.
- Holdout 결과에 맞춰 기존 기준을 변경하지 않는다.

### 11.7 판정

| 판정 | 조건 |
|---|---|
| 통과 | 모든 최소 기준 충족, 중대 오류 검토 완료 |
| 실패 | 핵심 기준 미달 또는 해결되지 않은 중대 오류 |
| 잠정 | 질문 수나 측정 요청 수가 부족하거나 평가 신뢰성이 부족하여 확정할 수 없음 |
| 판정 불가 | 평가 데이터, 근거 또는 평가 절차의 결함으로 유효한 평가가 불가능 |

기준을 충족하지 못한 후보는 비용·속도가 유리해도 서비스 채택 후보로 선정하지 않는다. 어떤 후보도 충족하지 못하면 점수가 가장 높은 후보를 억지로 채택하지 않고 원인을 분석해 개선한 뒤 재검증한다. 이 판정은 서비스 단계의 규칙이며, 과제 Basic 공식 비교의 최종 선택 규칙(`12_ACCEPTANCE_CRITERIA.md`)과 구분한다.

### 11.8 기준 확정과 변경 관리

- 공식 실험 전에 지표, 점수 산정 방법, 기준, 측정 시작·종료점, 답변 길이 구분, 측정 환경을 확정한다.
- 결과가 기준에 미달해도 기준을 바꾸지 않는다. 측정 오류나 중대한 설계 결함이 확인되면 결과를 유효한 것으로 취급하지 않고 수정한 뒤 다시 실행한다.
- 새로운 요구사항으로 기준을 바꾸면 기존 결과와 구분되는 새 실험으로 관리하며, 변경 사유·시점·영향받는 실험·재실험 여부를 기록한다.
- 측정하지 않은 항목은 추정값으로 채우지 않고 미측정으로 표시한다.

## 12. Claude Code 문서 검토 및 반영 지침

본 문서는 기존 설계 문서의 추가 지표 후보를 모아놓은 참고 문서다.

Claude Code는 구현 단계에 앞서 전체 설계 문서를 함께 읽고, 기존 내용과 중복되거나 누락된 부분을 검토해야 한다.

### 12.1 검토 대상

- `01_PRD.md`
- `02_EVALUATION_PLAN.md`
- `03_EXPERIMENT_PLAN.md`
- `04_ARCHITECTURE.md`
- `05_OBSERVABILITY_PLAN.md`
- `06_MODEL_SELECTION.md`
- `07_VERSIONING.md`
- `08_DEVELOPMENT_PLAN.md`
- `09_DATA_SCHEMA.md`
- `10_ADDITIONAL_METRICS.md`

### 12.2 검토 원칙

1. 기존 설계 문서의 목적과 역할을 먼저 파악한다.
2. 본 문서에 있는 지표가 기존 문서에 이미 포함되어 있는지 확인한다.
3. 기존 지표와 의미가 중복되는 경우 중복 구현하지 않는다.
4. 공식 필수 지표와 확장 지표를 구분한다.
5. 각 지표의 계산 방법과 측정 단위가 명확한지 확인한다.
6. 지표를 측정하기 위해 추가로 필요한 데이터와 로그가 무엇인지 검토한다.
7. 지표를 추가할 때 데이터 스키마, Langfuse 기록 구조, 실험 결과 저장 구조에 영향을 주는지도 확인한다.
8. 초기 구현에 불필요한 복잡성을 추가하지 않는다.
9. 실제로 측정할 수 없는 지표를 구현된 것처럼 문서화하지 않는다.

### 12.3 승인 및 문서 수정 규칙

- 본 문서만으로 기존 설계 문서의 수정 권한이 부여되는 것은 아니다.
- 기존 문서에 반영할 지표와 반영 위치를 먼저 제안한다.
- [필수 기록]과 [확장]을 구분하여 제안한다.
- 기존 설계의 범위, 기술 구조, API, 데이터 스키마, 구현 우선순위가 변경되는 경우 변경 이유와 영향을 설명하고 사용자 승인을 기다린다.
- 사용자 승인 전에는 기존 문서를 수정하거나 구현에 반영하지 않는다.
- 사용자가 승인한 항목만 해당 설계 문서에 반영한다.
- 반영하지 않은 지표는 본 문서에 남겨두어 향후 확장 시 참고할 수 있도록 한다.

### 12.4 최종 검토 결과 보고

Claude Code는 전체 문서 검토 후 다음 내용을 보고한다.

1. 기존 문서에 이미 포함된 지표
2. 기존 지표와 중복되는 지표
3. 추가 반영을 권장하는 지표
4. 초기 구현에 반영할 지표
5. 확장 실험으로 남길 지표
6. 측정에 필요한 추가 데이터 및 스키마 변경
7. 기존 설계와 충돌하거나 추가 결정이 필요한 사항
8. 사용자 승인이 필요한 변경 사항

검토 결과를 먼저 보고하고 사용자 승인 이후에 설계 문서를 수정한다.
